# MySQL 原理机制面试知识点

## 一、InnoDB 存储引擎架构

### 1.1 InnoDB 整体架构

InnoDB 由内存结构和磁盘结构组成：

```text
┌─────────────────────── InnoDB 架构 ───────────────────────┐
│  内存结构                                                  │
│  ┌─────────────┐  ┌─────────────┐  ┌──────────────────┐  │
│  │ Buffer Pool │  │ Change      │  │ AHI / 自适应哈希 │  │
│  │ (缓冲池)     │  │ Buffer      │  │ Log Buffer       │  │
│  └─────────────┘  └─────────────┘  └──────────────────┘  │
├───────────────────────────────────────────────────────────┤
│  磁盘结构                                                  │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌─────────────┐  │
│  │ 表空间    │ │ 段/区/页  │ │ redo log │ │ undo log    │  │
│  │ ibd 文件  │ │ 16KB 页   │ │ ib_logfile│ │ (回滚段)     │  │
│  └──────────┘ └──────────┘ └──────────┘ └─────────────┘  │
└───────────────────────────────────────────────────────────┘
```

**核心组件说明：**

| 组件 | 作用 |
|------|------|
| Buffer Pool | 缓存磁盘数据页，读走缓存、写先改内存页（脏页） |
| Change Buffer | 二级索引页不在缓存时，先把 DML 变更缓存起来，减少随机 IO |
| Log Buffer | redo log 的内存缓冲区，定期刷到 redo log 文件 |
| 自适应哈希索引（AHI） | InnoDB 自动为热点页建立哈希索引，加速等值查询 |
| redo log | 保证持久性，崩溃恢复 |
| undo log | 保证原子性，回滚 + MVCC |

### 1.2 一条 UPDATE 语句在 InnoDB 中怎么执行？

```text
1. 事务开始，定位到 Buffer Pool 中的数据页（不在则从磁盘加载）
2. 写 undo log（记录旧值，用于回滚和 MVCC）
3. 修改 Buffer Pool 中的数据页（该页成为脏页）
4. 写 redo log buffer（记录物理变更：某页某偏移改成了什么）
5. 事务提交时，redo log buffer 刷盘（WAL：先写日志后刷数据页）
6. 后台线程异步把脏页刷回磁盘
7. 写 binlog（Server 层日志，与 redo log 通过两阶段提交保证一致）
```

**面试回答：**

> 一条 UPDATE 先在 Buffer Pool 中定位数据页，写 undo log 记录旧值，然后修改内存中的页形成脏页，同时写 redo log buffer；提交时 redo log 先落盘（WAL 机制），binlog 通过两阶段提交与 redo log 保持一致；脏页由后台线程异步刷回磁盘。所以 MySQL 的写性能很高，因为大部分时候只需要顺序写日志，而不是随机写数据页。

### 1.3 为什么修改数据只改内存，不怕丢吗？

不怕，靠的是 **WAL（Write-Ahead Logging）** 机制：

- 修改数据页前，先把变更顺序写入 redo log 并在提交时落盘
- redo log 是顺序 IO，速度远快于随机写数据页
- 宕机后重启，用 redo log 重放（crash-safe），把未刷盘的变更恢复出来
- redo log 是物理日志（某页某位置改了什么），恢复速度快

### 1.4 Buffer Pool

**核心作用：** 缓存磁盘数据页（默认 16KB 一页），读写都优先走内存。

**管理机制：**
- 基于 LRU 变种（改进的分代 LRU）管理空闲页
- 脏页通过 checkpoint 机制异步刷盘
- 预读：线性预读（连续读 56 页触发读下一个区）、随机预读

**改进版 LRU（解决全表扫描污染问题）：**

```text
普通 LRU 问题：一次全表扫描会把整个缓存池的热点页全部挤出去

InnoDB 改进方案：LRU 链表分成两段
┌───────────── young 区（5/8）─────────────┐┌── old 区（3/8）──┐
│  热点数据，长期驻留                        ││  新加载的页先放这里 │
└───────────────────────────────────────────┘└──────────────────┘

新页进入 old 区头部，只有在 old 区停留超过 innodb_old_blocks_time（默认 1 秒）
再次被访问，才会晋升到 young 区。全表扫描的页大多停留不到 1 秒就被淘汰，
不会污染 young 区的热点数据。
```

**面试回答：**

> InnoDB 的 Buffer Pool 用改进版 LRU 管理缓存页，链表分 young 和 old 两段，新页先进 old 区，停留超过 1 秒再被访问才晋升 young 区。这样一次全表扫描或一次大查询的冷数据不会把真正的热点页挤出去，解决了缓存污染问题。

## 二、B+ 树与索引原理

### 2.1 为什么用 B+ 树而不是其他结构？

**常见候选结构对比：**

| 结构 | 查找 | 问题 |
|------|------|------|
| 哈希表 | O(1) | 不支持范围查询和排序，哈希冲突 |
| 二叉搜索树 | O(logN) | 树太高，磁盘 IO 次数 = 树高 |
| 红黑树 | O(logN) | 二叉树依然太高，百万数据 20+ 层 |
| B 树 | O(logN) | 每个节点存数据，单页存的键少，树更高 |
| B+ 树 | O(logN) | 非叶子节点只存键，叶子存数据且双向链表连接 |

**B+ 树的核心优势：**

1. **矮胖**：每个节点是一个 16KB 的页，能存大量键，3~4 层就能支撑千万级数据
2. **磁盘 IO 少**：树高即 IO 次数，千万数据 3 次 IO 内定位
3. **范围查询友好**：叶子节点双向链表连接，范围扫描顺着链表走即可
4. **查询稳定**：所有数据都在叶子节点，任何查询的 IO 次数都等于树高

**面试回答：**

> 索引选 B+ 树本质是为了减少磁盘随机 IO。哈希不支持范围查询；二叉树和红黑树太高，百万数据就要 20 层，意味着 20 次磁盘 IO；B+ 树每个节点是一个 16KB 的页，非叶子节点只存键不存数据，一页能存上千个键，千万级数据树高只有 3~4 层，也就是 3~4 次 IO。而且叶子节点用双向链表串联，范围查询和排序都能顺序读取。

### 2.2 B+ 树结构详解

```text
                        ┌────────────┐
                        │  根节点(页)  │
                        │ 15 | 56 | 77│
                        └──┬────┬──┬──┘
              ┌────────────┘    │    └────────────┐
              ▼                 ▼                  ▼
        ┌──────────┐      ┌──────────┐      ┌──────────┐
        │ 中间节点   │      │ 中间节点   │      │ 中间节点   │
        │ 15 | 20   │      │ 56 | 66  │      │ 77 | 92  │
        └─┬────┬───┘      └─┬────┬───┘      └─┬────┬───┘
          ▼    ▼            ▼    ▼            ▼    ▼
       [叶子页]⇄[叶子页]  [叶子页]⇄[叶子页]  [叶子页]⇄[叶子页]
       (数据行 + 指向前后叶子的双向链表指针)
```

**关键数字（面试加分项）：**

- InnoDB 页大小默认 16KB
- 假设主键 BIGINT（8 字节）+ 页指针（6 字节）≈ 14 字节
- 非叶子节点一页可存约 16KB / 14B ≈ 1170 个键
- 假设每行数据 1KB，叶子节点一页存 16 行
- **3 层 B+ 树可存约 1170 × 1170 × 16 ≈ 2190 万行**

### 2.3 聚簇索引与二级索引

| 对比项 | 聚簇索引 | 二级索引（辅助索引） |
|--------|----------|----------------------|
| 叶子存什么 | 完整数据行 | 索引列值 + 主键值 |
| 数量 | 一张表只有一个 | 可以有多个 |
| 查询方式 | 直接返回数据 | 先查到主键，再回聚簇索引查数据（回表） |

**回表（面试高频）：**

```text
SELECT * FROM user WHERE name = 'zhangsan';   -- name 有索引

二级索引 idx_name:                          聚簇索引:
    name -> id                                 id -> 整行数据
        │                                          ▲
        └──── 找到 id=1001 ──── 回表查询 ──────────┘
```

**面试回答：**

> InnoDB 的数据本身就是按主键组织的聚簇索引，叶子节点存整行数据。二级索引的叶子节点只存索引列和主键值，查询时如果需要的列不在索引里，就要拿着主键回到聚簇索引再查一次，这个过程叫回表。回表是随机 IO，如果一条 SQL 要回表上万次，优化器可能直接选择全表扫描。

### 2.4 覆盖索引

**定义：** 查询需要的所有列都在索引中，不需要回表。

```sql
-- 联合索引 (name, age)
-- 需要回表：SELECT 里还有索引外的列 phone
SELECT name, age, phone FROM user WHERE name = 'zhangsan';

-- 覆盖索引：name、age 都在索引里，直接返回
SELECT name, age FROM user WHERE name = 'zhangsan';

-- 覆盖索引：COUNT 也可以利用
SELECT COUNT(*) FROM user WHERE name = 'zhangsan';
```

**面试回答：**

> 覆盖索引指查询的列全部包含在索引中，在二级索引上就能拿到结果，避免回表。EXPLAIN 的 Extra 列出现 Using index 就说明用了覆盖索引。这是高频优化手段，比如把 SELECT * 改成只查索引包含的列，或者把高频查询的列扩展进联合索引。

### 2.5 索引下推（ICP，Index Condition Pushdown）

MySQL 5.6 引入，把 WHERE 条件中能用索引判断的部分下推到存储引擎层过滤。

```sql
-- 联合索引 (name, age)
SELECT * FROM user WHERE name LIKE 'zhang%' AND age = 20;
```

**无 ICP：**
1. 在索引上找到所有 name LIKE 'zhang%' 的记录，逐条回表
2. 回到 Server 层再过滤 age = 20

**有 ICP：**
1. 在索引上先判断 name LIKE 'zhang%' AND age = 20（age 也在索引里）
2. 只对同时满足的记录回表

**面试回答：**

> 索引下推是 MySQL 5.6 的优化，联合索引中某些列虽然因为前面的范围查询无法用于定位，但仍然可以在索引层先做过滤，减少回表次数。比如索引 (name, age)，条件 name LIKE 'zhang%' AND age = 20，没有 ICP 时所有姓 zhang 的都要回表再过滤 age；有 ICP 时直接在索引里把 age != 20 的过滤掉，只回表满足条件的行。EXPLAIN 的 Extra 显示 Using index condition。

### 2.6 页分裂与页合并

**页分裂：** 一个 16KB 的页写满了，再插入时 InnoDB 会把该页一分为二：

```text
分裂前：[页A: 1,2,3,4,5,6,7,8] 已满
插入 4.5：
分裂后：[页A: 1,2,3,4]  [新页B: 4.5,5,6,7,8]
同时需要更新父节点的指针，可能引发连锁分裂
```

**为什么随机主键（UUID）写入慢？**

> 自增主键总是追加到最后一页的末尾，页写满顺序分裂；UUID 随机插入会导致数据落在任意中间页，频繁触发页分裂，页分裂涉及数据搬移、父节点更新，还会产生碎片，导致写入性能下降和空间浪费。

**页合并：** 删除数据使页填充率低于 MERGE_THRESHOLD（默认 50%）时，InnoDB 尝试把该页与相邻页合并。

### 2.7 索引设计原则

1. **区分度高的列适合建索引**：区分度 = 不同值数量 / 总行数，越接近 1 越好
2. **联合索引把最常用的等值条件放最左**
3. **范围查询列放在联合索引最后**
4. **尽量构建覆盖索引，减少回表**
5. **索引列尽量 NOT NULL**：NULL 值使索引统计和优化更复杂
6. **长字符串用前缀索引**：`ALTER TABLE t ADD INDEX idx_name (name(10))`，用前 10 个字符建索引，节省空间但无法覆盖索引和排序
7. **不要滥用索引**：每个索引都是一棵 B+ 树，写入都要维护

### 2.8 唯一索引和普通索引怎么选？

**查询：** 唯一索引找到一条即停止；普通索引找到一条还要继续找下一条（性能差异极小，因为都是顺序读下一行）。

**写入：** 普通索引可以用 Change Buffer 把变更缓存起来延迟合并，唯一索引必须把页读进内存做唯一性校验，不能用 Change Buffer。

**面试回答：**

> 查询上两者差异可以忽略；写入上普通索引能利用 Change Buffer 减少随机 IO，唯一索引每次都要读页校验唯一性。如果业务上已经能保证唯一（比如代码层校验），写多读少场景可以用普通索引换性能；否则老老实实用唯一索引保证数据正确性，正确性优先。

## 三、事务与 MVCC

### 3.1 事务的 ACID 实现

| 特性 | 实现机制 |
|------|----------|
| 原子性 | undo log（逻辑日志，反向补偿） |
| 持久性 | redo log（物理日志，WAL + 崩溃恢复） |
| 隔离性 | MVCC（读）+ 锁（写） |
| 一致性 | 以上三者共同保证 |

### 3.2 并发事务问题与隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|------------|------|
| 读未提交 | 可能 | 可能 | 可能 |
| 读已提交（RC） | 避免 | 可能 | 可能 |
| 可重复读（RR，默认） | 避免 | 避免 | 基本避免 |
| 串行化 | 避免 | 避免 | 避免 |

**RC 和 RR 的本质区别（高频）：**

> RC 和 RR 在 MVCC 上的区别是生成 Read View 的时机：RC 是**每条语句执行前**都重新生成 Read View，所以能看到别的事务已提交的最新数据；RR 是**事务开始后第一条查询语句**时生成 Read View，之后整个事务复用同一个 Read View，所以多次读取结果一致。这就是"可重复读"的实现原理。

### 3.3 MVCC 多版本并发控制

**核心目标：** 读不加锁、读写不冲突，用空间换并发性能。

**三大要素：**

#### 1. 隐藏列（每行记录）

| 隐藏列 | 含义 |
|--------|------|
| DB_TRX_ID | 最近一次修改该行的事务 ID |
| DB_ROLL_PTR | 回滚指针，指向该行的上一个版本（undo log） |
| DB_ROW_ID | 隐藏主键（无主键表用） |

#### 2. undo log 版本链

```text
当前行: name='wangwu', trx_id=300, roll_ptr ──┐
                                              ▼
        undo log: name='lisi', trx_id=200, roll_ptr ──┐
                                                      ▼
                undo log: name='zhangsan', trx_id=100
```

每次修改都会把旧版本写入 undo log，通过 roll_ptr 串成版本链。

#### 3. Read View（一致性视图）

事务执行快照读时生成，包含：

| 字段 | 含义 |
|------|------|
| m_ids | 生成视图时所有活跃（未提交）事务 ID 集合 |
| min_trx_id | 活跃事务中最小的 ID |
| max_trx_id | 下一个将分配的事务 ID |
| creator_trx_id | 创建该视图的事务自己的 ID |

**可见性判断规则（顺着版本链从新到旧找第一个可见版本）：**

```text
trx_id == creator_trx_id          -> 可见（自己改的）
trx_id < min_trx_id               -> 可见（生成视图前已提交）
trx_id >= max_trx_id              -> 不可见（视图生成后才开启的事务）
min_trx_id <= trx_id < max_trx_id:
    trx_id 在 m_ids 中            -> 不可见（当时还没提交）
    trx_id 不在 m_ids 中          -> 可见（当时已提交）
```

**面试回答：**

> MVCC 由三个部分组成：行记录的隐藏字段（事务 ID 和回滚指针）、undo log 版本链、Read View 一致性视图。快照读时生成 Read View，顺着 undo log 版本链从新到旧找第一个对当前事务可见的版本。判断规则核心是：自己改的可见、视图生成前已提交的可见、生成时还没提交的不可见、生成后才开始的事务不可见。RC 每条语句生成一次视图，RR 只在第一条查询时生成一次并复用。

### 3.4 快照读与当前读

| 类型 | 含义 | 语句 |
|------|------|------|
| 快照读 | 读 MVCC 快照版本，不加锁 | 普通 SELECT |
| 当前读 | 读最新已提交版本，加锁 | UPDATE、DELETE、INSERT、SELECT ... LOCK IN SHARE MODE、SELECT ... FOR UPDATE |

**为什么 UPDATE 是当前读？**

> 更新必须基于最新数据，否则会丢失修改。比如两个事务同时给余额加 100，如果基于快照各自读旧值再写回，就会丢失一次修改。所以写操作必须当前读并加锁。

### 3.5 RR 级别如何解决幻读？

**幻读定义：** 同一事务内两次相同范围查询，第二次看到了别的事务新插入的行。

**InnoDB 的应对（两套机制配合）：**

1. **快照读**：靠 MVCC。Read View 在事务内复用，后插入的行 trx_id 必然 >= max_trx_id 或在 m_ids 中，不可见，所以不会幻读。
2. **当前读**：靠**间隙锁（Next-Key Lock = 记录锁 + 间隙锁）**。锁住已有记录及其之间的间隙，别的事务无法在范围内插入新行。

**RR 下幻读没有被完全解决的场景（面试加分）：**

```sql
-- 事务 A
BEGIN;
SELECT * FROM t WHERE id > 10;        -- 快照读，看不到 id=15
-- 事务 B 插入 id=15 并提交
UPDATE t SET name='x' WHERE id = 15;  -- A 执行 UPDATE（当前读），能改到 id=15
SELECT * FROM t WHERE id > 10;        -- 再次快照读，看到了 id=15（自己改过的行对自己可见）
```

> 先快照读后当前读的混用场景下，幻读仍可能发生。彻底避免要么一开始就 `SELECT ... FOR UPDATE`，要么用串行化隔离级别。

## 四、锁机制

### 4.1 锁的分类总览

| 分类维度 | 类型 |
|----------|------|
| 粒度 | 全局锁、表级锁、行级锁 |
| 模式 | 共享锁（S）、排他锁（X） |
| 行锁算法 | 记录锁 Record Lock、间隙锁 Gap Lock、临键锁 Next-Key Lock |
| 思想 | 乐观锁（版本号/CAS）、悲观锁（数据库锁） |

### 4.2 全局锁与表级锁

**全局锁：**

```sql
FLUSH TABLES WITH READ LOCK;   -- 全库只读，用于不支持事务的引擎做全库备份
UNLOCK TABLES;
```

InnoDB 备份不需要全局锁，用 `mysqldump --single-transaction` 在事务中拿到一致性快照。

**表级锁：**

| 锁 | 说明 |
|----|------|
| 表锁 | `LOCK TABLES t READ/WRITE`，粒度大，基本不用 |
| 元数据锁（MDL） | 访问表自动加 MDL 读锁；改表结构加 MDL 写锁。**DDL 被 MDL 写锁阻塞时，后续所有查询都会被阻塞，可能雪崩** |
| 意向锁 | 表级"占位"锁，表明表内有行锁，让表锁请求不必逐行检查 |
| AUTO-INC 锁 | 自增主键分配锁，innodb_autoinc_lock_mode 控制 |

**面试高频：为什么 DDL 加字段可能把库搞挂？**

> 长事务持有 MDL 读锁不释放，DDL 等待 MDL 写锁，而写锁请求又会阻塞之后所有的读请求，连接堆积导致雪崩。所以 DDL 前要检查长事务，或在低峰期执行，或设置 lock_wait_timeout。

### 4.3 行级锁

**前提：** 行锁加在**索引记录**上。如果 WHERE 条件没有索引，行锁会升级为对所有记录加锁（效果近似锁全表）。

| 锁类型 | 锁定范围 | 作用 |
|--------|----------|------|
| 记录锁（Record Lock） | 单条索引记录 | 锁住一行 |
| 间隙锁（Gap Lock） | 索引记录之间的开区间 | 防止插入，解决幻读 |
| 临键锁（Next-Key Lock） | 记录 + 前面的间隙（左开右闭） | RR 默认行锁算法 |
| 插入意向锁 | 插入前的一种间隙锁 | 并发插入不同间隙互不阻塞 |

**示例：**

```sql
-- 表中 id 有 10、20、30 三条记录
SELECT * FROM t WHERE id = 20 FOR UPDATE;
-- 记录锁：只锁 id=20

SELECT * FROM t WHERE id BETWEEN 10 AND 20 FOR UPDATE;
-- 临键锁：锁 (10, 20] 以及可能包含 (5, 10]，取决于索引情况

SELECT * FROM t WHERE id > 10 AND id < 20 FOR UPDATE;
-- 间隙锁：锁 (10, 20) 之间的间隙，别的事务不能插入 id=15
```

**面试回答：**

> InnoDB 的行锁是加在索引上的。RR 隔离级别下默认用临键锁，即记录锁加间隙锁，锁住记录本身和它前面的间隙，防止其他事务在范围内插入数据，从而解决当前读的幻读。要注意如果更新条件没走索引，InnoDB 会对所有记录加锁，相当于锁全表，这是生产死锁和性能事故的常见来源。

### 4.4 共享锁与排他锁

```sql
SELECT * FROM t WHERE id = 1 LOCK IN SHARE MODE;  -- S 锁（8.0: FOR SHARE）
SELECT * FROM t WHERE id = 1 FOR UPDATE;          -- X 锁
```

| 组合 | 兼容性 |
|------|--------|
| S + S | 兼容 |
| S + X | 冲突 |
| X + X | 冲突 |

### 4.5 死锁

**产生条件：** 互斥、持有并等待、不可剥夺、循环等待。

**经典场景：**

```sql
-- 事务 A                          -- 事务 B
UPDATE t SET x=1 WHERE id=1;      UPDATE t SET x=1 WHERE id=2;
UPDATE t SET x=1 WHERE id=2;      UPDATE t SET x=1 WHERE id=1;
-- A 等 B 释放 id=2，B 等 A 释放 id=1 -> 死锁
```

**InnoDB 死锁处理：**
- 死锁检测（innodb_deadlock_detect=on）：发现循环等待立即回滚代价小的事务
- 锁等待超时（innodb_lock_wait_timeout，默认 50 秒）

**如何避免死锁：**
1. 多行更新按固定顺序访问（如按主键升序）
2. 大事务拆小，缩短锁持有时间
3. 给条件列建索引，避免锁范围扩大
4. 降低隔离级别到 RC（没有间隙锁，锁范围更小）
5. 必要时一次性锁定（FOR UPDATE 代替先读后写）

### 4.6 乐观锁与悲观锁

| 对比项 | 悲观锁 | 乐观锁 |
|--------|--------|--------|
| 思想 | 先加锁再操作 | 不加锁，提交时校验冲突 |
| 实现 | SELECT FOR UPDATE | 版本号 / CAS |
| 性能 | 并发低时安全 | 并发高时重试多 |
| 适用 | 写多冲突多 | 读多冲突少 |

```sql
-- 乐观锁示例
UPDATE goods SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = #{oldVersion};
-- 影响行数为 0 说明并发修改，需要重试
```

## 五、日志体系（重点）

### 5.1 三大日志总览

| 日志 | 层级 | 作用 | 内容 |
|------|------|------|------|
| redo log | InnoDB 引擎层 | 崩溃恢复，保证持久性 | 物理日志：某页某偏移做了什么修改 |
| undo log | InnoDB 引擎层 | 回滚 + MVCC | 逻辑日志：反向操作（INSERT 的 undo 是 DELETE） |
| binlog | Server 层 | 主从复制、数据恢复 | 逻辑日志：SQL 或行变更 |

### 5.2 redo log

**为什么需要 redo log？**

> 如果每次提交都强制把脏页刷盘，随机 IO 性能极差。redo log 把"在哪个页哪个位置改了什么"顺序追加到日志文件，提交时只需保证 redo log 落盘（顺序 IO 快），脏页异步刷。宕机后重放 redo log 恢复数据，这就是 crash-safe。

**刷盘策略（innodb_flush_log_at_trx_commit）：**

| 值 | 行为 | 安全性 | 性能 |
|----|------|--------|------|
| 1 | 每次提交都 fsync 刷盘 | 最高，不丢数据 | 最低 |
| 0 | 每秒由后台线程刷 | 最低，宕机丢 1 秒 | 最高 |
| 2 | 提交时写到 OS 缓存（page cache），每秒 fsync | 宕机不丢，主机断电丢 1 秒 | 较高 |

**redo log 写满了怎么办？**

> redo log 是固定大小的循环写文件（如 4 个 1GB 文件）。写满时会强制推进 checkpoint，把最老的脏页刷盘腾出空间，此时所有更新都会被阻塞。线上如果出现"redolog 写满"告警，说明写入压力远超刷盘能力，需要扩容或调大 redo log。

### 5.3 binlog

**三种格式：**

| 格式 | 内容 | 优缺点 |
|------|------|--------|
| STATEMENT | 记录 SQL 原文 | 日志量小，但 NOW()/UUID() 等函数主从可能不一致 |
| ROW | 记录每行数据的变更前后镜像 | 绝对一致，但日志量大 |
| MIXED | 自动选择 | 折中方案 |

**生产建议：** ROW 格式，虽然日志量大，但主从一致性最好，且数据恢复精确。

**binlog 写入机制：**

```text
事务执行过程中 -> 写入 binlog cache（每个线程独立）
事务提交时    -> 写入 binlog 文件（可能先到 page cache）
sync_binlog = 1  每次提交都 fsync，最安全
sync_binlog = 0  交给 OS，性能最好风险最高
sync_binlog = N  攒 N 个事务 fsync 一次
```

### 5.4 两阶段提交（高频必考）

**为什么需要两阶段提交？**

redo log 和 binlog 是两个独立的日志系统，如果不保证它们的一致性，崩溃恢复后主从数据会不一致。

**流程：**

```text
1. redo log 写入，状态置为 prepare
2. 写 binlog
3. redo log 状态置为 commit

崩溃恢复时的判断：
- redo log 已 commit          -> 直接恢复
- redo log 处于 prepare：
    - binlog 完整（有对应 XID）-> 提交事务
    - binlog 不完整            -> 回滚事务
```

**反证法理解（面试回答模板）：**

> 假设不用两阶段提交。先写 redo log 后写 binlog：redo 写完崩溃，主库恢复后事务生效，但 binlog 没写，从库丢失该事务，主从不一致。先写 binlog 后写 redo log：binlog 写完崩溃，主库恢复后回滚事务，但从库重放了 binlog，从库多出数据。两阶段提交让 redo log 处于 prepare 时必须检查 binlog 是否完整，完整则提交、不完整则回滚，保证两份日志的逻辑一致。

### 5.5 redo log 与 binlog 的区别

| 对比项 | redo log | binlog |
|--------|----------|--------|
| 层级 | InnoDB 引擎层 | Server 层（所有引擎都有） |
| 类型 | 物理日志 | 逻辑日志 |
| 写法 | 循环写，固定大小 | 追加写，写满换新文件 |
| 用途 | 崩溃恢复 | 主从复制、数据恢复 |
| 写入时机 | 事务执行过程中不断写入 | 事务提交时一次性写入 |

### 5.6 undo log

**两大作用：**
1. **回滚**：事务失败或手动 ROLLBACK 时，按 undo log 反向补偿
2. **MVCC**：通过 roll_ptr 构建版本链，支撑快照读

**注意：** undo log 本身也要写 redo log 保护（保证回滚操作本身可恢复）。长事务会持有大量 undo log 无法清理，导致 undo 表空间膨胀，这是长事务的危害之一。

### 5.7 一条 UPDATE 的完整日志流程（综合题）

```text
BEGIN;
UPDATE user SET name = 'wangwu' WHERE id = 1;
COMMIT;

执行过程：
1. 加锁：id=1 加排他记录锁
2. 写 undo log：记录旧值 name='lisi'
3. 修改 Buffer Pool 数据页（脏页）
4. 写 redo log buffer（prepare 状态）
5. COMMIT 触发两阶段提交：
   a. redo log fsync 落盘（prepare）
   b. 写 binlog cache 并 fsync 到 binlog 文件
   c. redo log 置为 commit
6. 后台线程异步刷脏页
7. 事务提交后 undo log 暂时保留（供其他事务 MVCC 读），无事务引用后清理
```

## 六、高频面试题

### 6.1 为什么 MySQL 用 B+ 树？

减少磁盘 IO：16KB 页 + 非叶子节点只存键 -> 树矮（千万数据 3~4 层）；叶子双向链表支持范围查询；所有查询路径长度一致，性能稳定。

### 6.2 什么是回表？怎么避免？

二级索引叶子只存主键，查完整行需要回聚簇索引再查一次。避免方式：覆盖索引（查询列都在索引中）。

### 6.3 为什么推荐自增主键？

聚簇索引按主键组织，自增主键顺序追加写、页分裂少；随机主键（UUID）导致频繁页分裂、碎片、写入性能差。

### 6.4 MVCC 是怎么实现的？

隐藏字段（trx_id、roll_ptr）+ undo log 版本链 + Read View 可见性判断。RC 每条语句生成视图，RR 事务内复用视图。

### 6.5 RR 如何解决幻读？

快照读靠 MVCC（视图复用，新插入不可见）；当前读靠临键锁（记录锁+间隙锁）锁住范围禁止插入。混用快照读和当前读时幻读仍可能发生。

### 6.6 redo log 和 binlog 的区别？

引擎层 vs Server 层；物理 vs 逻辑；循环写 vs 追加写；崩溃恢复 vs 复制恢复。通过两阶段提交保证一致。

### 6.7 一条 UPDATE 的执行过程？

加行锁 -> 写 undo log -> 改 Buffer Pool 脏页 -> 写 redo log(prepare) -> 提交时写 binlog -> redo log commit -> 异步刷脏页。

### 6.8 什么是索引下推？

MySQL 5.6 优化，把联合索引中无法用于定位但可以用于过滤的条件，下推到存储引擎层在索引上先过滤，减少回表次数。

### 6.9 死锁怎么排查和避免？

`SHOW ENGINE INNODB STATUS` 查看最近死锁日志。避免：固定顺序访问、小事务、索引避免锁扩大、必要时降级 RC。

### 6.10 长事务有什么危害？

undo log 无法清理导致膨胀；长期持有 MDL 读锁阻塞 DDL；锁持有时间长引发阻塞和死锁；主从延迟加大。用 `information_schema.innodb_trx` 监控并 kill 超长事务。
