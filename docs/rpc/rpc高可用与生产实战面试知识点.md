# RPC 高可用与生产实战面试知识点

## 一、超时机制

### 1.1 为什么必须设置超时？

RPC 调用没有超时意味着：网络分区、对端宕机、对端慢查询时，调用方线程会**永久阻塞**。在高并发下，阻塞线程快速累积，最终耗尽线程池，导致调用方自身也宕机——这是服务雪崩的典型起点。

> 核心认知：**不设置超时的 RPC 调用 = 把自身的稳定性交给网络和下游**。

### 1.2 超时时间怎么设置才合理？

| 原则 | 说明 |
|------|------|
| 基于 P99 延迟 | 参考下游正常时的 P99 耗时，略加 buffer（如 P99 的 1.5~2 倍） |
| 自上而下递减 | 调用链路上游超时 > 下游超时，避免下游还在干活上游已放弃 |
| 区分核心与非核心 | 核心链路超时短、快速失败；非核心可适当放宽 |
| 不能无限大 | 再慢的接口也要有上限，否则等于没设 |

**超时传递问题（面试高频）：**

```text
网关(超时 3s) -> A 服务(剩 2.5s) -> B 服务(剩 2s) -> C 服务
```

Dubbo 等框架会把**剩余超时时间**放在隐式参数（attachment）里层层传递，下游用剩余时间作为自己的真实超时，避免"上游已超时、下游还在执行"的无效计算。

### 1.3 超时发生在哪一端？

- **消费端超时**：消费方在 Future 上等待超过设定时间，抛出 `TimeoutException`，但请求可能已经到达服务端并被执行。
- **服务端超时**：Dubbo 2.7+ 支持服务端超时检测，业务线程执行超时后返回异常，但默认不中断业务线程。

**关键认知：消费端超时 ≠ 服务端没执行。** 这直接导致幂等问题（见第二章）。

## 二、重试机制与幂等

### 2.1 常见集群容错策略

| 策略 | 行为 | 适用场景 |
|------|------|----------|
| Failover（失败重试） | 失败后换一台重试，Dubbo 默认重试 2 次 | 读操作、幂等写操作 |
| Failfast（快速失败） | 失败立即报错，不重试 | 非幂等写操作（如扣款） |
| Failsafe（失败安全） | 失败直接忽略 | 日志、埋点等可丢失场景 |
| Failback（失败自动恢复） | 失败后定时重发 | 消息通知类最终一致场景 |
| Forking（并行调用） | 同时调多台，取最先成功的 | 读多、对实时性要求极高，浪费资源 |
| Broadcast（广播） | 逐个调用所有提供者，一台失败即失败 | 本地缓存刷新、配置同步 |

### 2.2 重试会带来什么问题？

```text
Consumer -> ProviderA（执行成功，但响应丢失/超时）
Consumer 超时 -> 重试 ProviderB -> 同一笔扣款执行了两次
```

**重试的三大风险：**

1. **重复执行**：非幂等接口被重试导致数据错误（重复扣款、重复下单）。
2. **流量放大**：下游已经过载时，重试让流量翻倍，加剧雪崩（重试风暴）。
3. **长尾延迟**：P99 延迟因重试显著升高。

### 2.3 幂等性怎么保证？

**面试必考。** 幂等是指同一请求执行一次和执行 N 次效果相同。

| 方案 | 原理 | 典型场景 |
|------|------|----------|
| 唯一请求号 + 去重表 | 请求带唯一 ID，服务端插入去重表，冲突则拒绝 | 支付、下单 |
| 数据库唯一索引 | 业务唯一键（订单号）加唯一索引，重复插入报错 | 创建类操作 |
| 状态机校验 | 只有特定状态才能流转（如 待支付->已支付） | 订单状态变更 |
| 乐观锁/version | 更新时带版本号，`where version = ?` | 账户余额、库存 |
| 天然幂等设计 | 用 set 语义代替 increment 语义（"设置为 100"而非"加 1"） | 配置更新 |

**面试回答模板：**

> RPC 重试的前提是接口幂等。读接口天然幂等可以配 Failover；写接口要么框架层用 Failfast 不重试，要么业务层做幂等：调用方生成全局唯一请求号，服务端通过去重表或唯一索引保证同一请求只生效一次；状态流转类接口用状态机前置校验；余额库存类用乐观锁。另外重试次数要控制（一般不超过 2~3 次），避免下游过载时的重试风暴。

## 三、熔断、限流、降级

### 3.1 三者的区别（面试高频）

| 机制 | 保护对象 | 触发条件 | 类比 |
|------|----------|----------|------|
| 限流 | 服务端（保护自己） | QPS/并发数超过阈值 | 景区限流，超过承载量就拒客 |
| 熔断 | 调用方（保护自己不被下游拖死） | 下游错误率/慢调用比例超阈值 | 保险丝，电流过大自动断开 |
| 降级 | 整体系统（保核心舍次要） | 系统压力大时主动/自动关闭非核心功能 | 大促时关闭退款、评价保下单 |

### 3.2 熔断器工作原理（状态机）

```text
        失败率超阈值                熔断时长到达，试探放行
 ┌─────────┐ ───────────▶ ┌─────────┐ ───────────────────▶ ┌──────────────┐
 │ Closed   │              │  Open    │                      │ Half-Open     │
 │ 正常调用  │ ◀─────────── │ 直接失败  │ ◀─────────────────── │ 放少量请求试探 │
 └─────────┘  试探成功恢复   └─────────┘   试探失败重新熔断     └──────────────┘
```

- **Closed**：正常调用，统计错误率/慢调用比例。
- **Open**：达到阈值后熔断，请求直接失败（快速失败），不再打到下游，给下游恢复时间。
- **Half-Open**：熔断时间窗口过后放少量请求试探，成功则关闭，失败则继续熔断。

### 3.3 常见限流算法

| 算法 | 原理 | 特点 |
|------|------|------|
| 固定窗口 | 单位时间窗口内计数，超限拒绝 | 实现简单，窗口边界有临界突刺 |
| 滑动窗口 | 窗口细分成小格滑动统计 | 更平滑，临界问题缓解 |
| 漏桶 | 请求进桶，按固定速率流出 | 输出绝对平滑，无法应对突发 |
| 令牌桶 | 按固定速率发令牌，拿令牌才能通过 | 允许一定突发，最常用 |

### 3.4 Sentinel vs Hystrix

| 对比项 | Sentinel | Hystrix |
|--------|----------|---------|
| 出品方 | 阿里开源 | Netflix（已停更） |
| 隔离方式 | 信号量/并发数隔离 | 线程池隔离 + 信号量 |
| 限流能力 | 强（QPS、热点参数、集群流控） | 弱 |
| 熔断策略 | 慢调用比例、异常比例、异常数 | 错误率 |
| 控制台 | 有完善 dashboard | 需配合 Turbine |
| 现状 | 社区活跃，主流选择 | 停止维护，存量系统在用 |

**面试回答模板：**

> 我们的 RPC 防护体系是分层组合的：入口层网关限流防外部流量洪峰；服务间调用用 Sentinel 做熔断降级，下游慢调用比例超阈值就熔断一段时间，降级返回兜底数据；线程模型上通过并发数隔离防止单个下游拖垮整个应用；大促期间再配合预案手动降级非核心链路。核心思想是：任何下游都不可信，每个依赖都要有超时、有熔断、有兜底。

## 四、优雅停机与启动预热

### 4.1 为什么需要优雅停机？

直接 `kill -9` 服务提供者会出现两类问题：

1. **正在处理的请求被中断**：业务执行一半，数据不一致。
2. **消费方请求打到已死的实例**：注册中心列表还没来得及剔除（ZK 会话超时可能要几秒到几十秒），消费方在这段时间内持续报错。

### 4.2 优雅停机流程

```text
① 收到停机信号（kill -15 / actuator shutdown）
② 从注册中心注销自己（主动，秒级生效）
③ 停止接收新请求（消费方列表更新后不再路由过来）
④ 等待在途请求处理完成（有上限，如 30s）
⑤ 关闭线程池、连接、释放资源，进程退出
```

**兜底手段**：消费方开启重试 + 熔断，即使列表有脏数据，换一台重试即可成功，对业务无感。

### 4.3 启动预热

**问题**：服务刚启动时 JIT 未编译热点代码、本地缓存为空、连接池未建立，直接承接全量流量会导致响应毛刺甚至超时。

**解决方案：**

| 方案 | 说明 |
|------|------|
| 小流量预热 | 注册时把权重调小（如 10%），逐步调大，Dubbo 原生支持 warm-up |
| 延迟发布 | 注册后先不对外提供，预热完成再暴露 |
| 主动预热 | 启动后自动调用自身热点接口、预加载缓存、预建连接 |

## 五、注册中心高可用

### 5.1 CP 与 AP 之争

| 注册中心 | 模型 | 取舍说明 |
|----------|------|----------|
| ZooKeeper | CP | 网络分区时，少数派节点不可用，保证数据一致 |
| Eureka | AP | 每个节点都能提供服务，数据可能短暂不一致 |
| Nacos | 支持 CP/AP 切换 | 临时实例默认 AP，持久实例/配置走 CP |
| Etcd | CP | 基于 Raft 强一致 |

**面试高频：注册中心选 CP 还是 AP？**

> 服务发现场景宁可拿到短暂不一致的列表，也不能整个系统不可寻址。列表里多一个死实例，靠重试和熔断可以容忍；但注册中心不可用导致新 Consumer 起不来、扩缩容失效，影响更大。所以服务注册发现一般倾向 AP（Eureka、Nacos AP 模式）；而分布式锁、选主这类强协调场景必须 CP（ZK、Etcd）。

### 5.2 注册中心自我保护

Eureka 经典问题：大量实例心跳同时丢失（往往是网络抖动而非真宕机），如果直接全部剔除，会造成服务列表瞬间清空。

**自我保护机制**：15 分钟内心跳续约比例低于阈值（默认 85%）时，Eureka 进入自我保护，**不再剔除任何实例**，宁可保留可能的死实例，等待网络恢复。

**启示**：健康检测只能检测到"网络不可达"，无法区分"实例真死"和"网络分区"，设计时必须考虑误判场景。

### 5.3 多级容灾实践

1. **Consumer 本地缓存列表**：注册中心挂了也能调用（前提：提供者没变）。
2. **本地文件快照**：Consumer 把列表持久化到本地文件，重启后注册中心不可用也能用快照兜底。
3. **注册中心集群部署**：跨机房多节点，避免单点。
4. **直连兜底**：核心服务可配置 `url` 直连地址作为最后手段。

## 六、分布式链路追踪

### 6.1 为什么需要链路追踪？

微服务下，一次用户请求可能经过十几个 RPC 调用。没有链路追踪时：

- 请求慢，不知道慢在哪个环节。
- 请求报错，不知道错误发生在哪一跳。
- 服务依赖关系靠人脑记忆，无法评估变更影响。

### 6.2 核心概念

```text
TraceId：贯穿一次完整请求的唯一 ID（全局）
SpanId：一次调用（一跳）的 ID
ParentSpanId：父调用 SpanId，用于构建调用树

一次下单请求：
网关(Span1) ──▶ 订单服务(Span2) ──▶ 库存服务(Span3)
                        └──▶ 支付服务(Span4)
所有 Span 共享同一个 TraceId，按 ParentSpanId 组织成树
```

### 6.3 TraceId 如何在 RPC 间传递？

通过 RPC 协议的**隐式参数（attachment）**：

```java
// 消费方：过滤器中把上下文写入 attachment
RpcContext.getContext().setAttachment("traceId", TraceContext.currentTraceId());

// 提供方：过滤器中取出并放入本地 MDC
String traceId = invocation.getAttachment("traceId");
MDC.put("traceId", traceId);
```

> 同理，用户身份、灰度标签、剩余超时时间也都是通过 attachment 透传的，这是 RPC 上下文传递的统一机制。

### 6.4 常见实现

| 组件 | 特点 |
|------|------|
| SkyWalking | 国产，字节码增强无侵入，带服务拓扑和性能分析 |
| Zipkin | 老牌，Spring Cloud Sleuth 配套 |
| Jaeger | Uber 开源，CNCF 项目，云原生友好 |
| OpenTelemetry | 厂商中立的采集标准，当前趋势 |

## 七、性能优化实战

### 7.1 RPC 性能优化清单

| 层面 | 优化手段 |
|------|----------|
| 序列化 | 换高性能序列化（Kryo/Protobuf）；瘦身请求响应对象，去掉无用字段 |
| 网络 | 长连接复用；合理配置 IO/业务线程数；开启 TCP_NODELAY 减少小包延迟 |
| 调用方式 | 无依赖的多次调用改异步并行；批量接口代替循环单条调用 |
| 协议 | 减小报文体积；避免大对象传输（单次过大考虑拆分或走文件/OSS） |
| 服务端 | 业务线程池隔离快慢接口；避免在 RPC 线程里做重活；JIT 预热 |
| 客户端 | 减少不必要的重试；合理超时避免线程堆积 |

### 7.2 高频生产问题排查模板

**问题：RPC 调用超时突然增多，怎么排查？**

```text
① 看监控定位：是某一个 Provider 慢，还是全部慢？
   ├─ 个别实例慢 -> 单机问题：GC、CPU 飙高、磁盘 IO、网络
   └─ 全部慢 -> 下游依赖问题：DB 慢查询、缓存命中率下降、下游的下游故障
② 单机问题深入：jstat 看 GC、top + jstack 看线程、arthas trace 看方法耗时
③ 依赖问题深入：DB 慢查询日志、Redis bigkey/热key、下游服务自身监控
④ 流量层面：是否突发流量？QPS 是否超过容量？线程池是否打满排队？
```

**问题：线上出现大量 "no provider available"，可能原因？**

1. Provider 全部宕机或假死（Full GC、线程池打满导致心跳失败）。
2. 网络分区导致 Provider 与注册中心断连，临时节点被删。
3. Consumer 与 Provider 版本/分组不匹配。
4. Provider 启动时注册失败（注册中心故障、配置错误）。
5. 刚发布时 Consumer 列表尚未更新（短暂，正常）。

**问题：RPC 线程池打满怎么处理和预防？**

- 临时处理：扩容实例、重启释放（不推荐，掩盖问题）、限流保护。
- 根因排查：一定有慢请求堆积——用 jstack 看线程都卡在什么方法（通常卡在下游 DB/Redis/另一个 RPC）。
- 预防：快慢接口线程池隔离、依赖全部加超时、入口限流、容量评估。

## 八、服务治理进阶话题

### 8.1 灰度发布与路由

**目标**：新版本先让小部分流量验证，没问题再全量。

**实现方式：**

| 方式 | 说明 |
|------|------|
| 版本号路由 | Provider 以不同 version 注册，Consumer 指定 version 调用 |
| 标签路由 | 实例打标（gray/online），按请求特征（用户 ID、Header）路由到带标实例 |
| 权重路由 | 新版本实例权重调小，承接少量流量后逐步放大 |

请求级标签通过 attachment 透传，保证全链路都走灰度节点（配合全链路灰度方案）。

### 8.2 接口版本管理与兼容性

| 原则 | 说明 |
|------|------|
| 只加不改 | 接口只新增字段/方法，不删除、不改语义 |
| 不兼容升级用 version | 必须breaking change 时，新版本接口与旧版本并行一段时间 |
| DTO 字段可缺省 | 新增字段用包装类型/带默认值，老 Consumer 不受影响 |
| 有序下线 | 先下线 Consumer 依赖，再下线 Provider |

### 8.3 泛化调用

**场景**：网关、测试平台需要调用任意 Dubbo 服务，但不可能依赖所有服务的接口包。

**方案**：泛化调用不依赖接口类，直接用"接口全名 + 方法名 + 参数类型 + 参数 Map/JSON"发起调用：

```java
GenericService genericService = reference.get();
Object result = genericService.$invoke(
        "getUserById",                       // 方法名
        new String[]{"java.lang.Long"},      // 参数类型
        new Object[]{1001L});                // 参数值
```

这是 API 网关对接 RPC 服务的标准姿势：网关收到 HTTP 请求，按配置映射成泛化调用，实现协议转换。

### 8.4 服务自检与依赖梳理

生产实践经验：

- 每个 RPC 依赖登记造册：负责人、SLA 等级、超时配置、降级预案。
- 定期演练：手动熔断某依赖，验证兜底逻辑真实有效（降级逻辑不演练等于没有）。
- 强弱依赖标注：强依赖挂了就返回失败，弱依赖挂了走兜底数据，决不能一视同仁。

## 九、高频面试速记

1. **超时**：必须设；按下游 P99 设；链路上游大于下游；剩余超时可透传。
2. **重试**：只对幂等接口重试；非幂等用 Failfast；警惕重试风暴放大流量。
3. **幂等方案**：唯一请求号去重表、唯一索引、状态机、乐观锁、天然幂等设计。
4. **熔断三态**：Closed/Open/Half-Open，给下游恢复时间，调用方快速失败。
5. **限流算法**：令牌桶最常用（允许突发），漏桶绝对平滑。
6. **降级**：保核心舍次要；兜底逻辑要演练。
7. **优雅停机**：先注销注册中心 -> 停收新请求 -> 等在途完成 -> 退出；配合消费方重试对业务无感。
8. **启动预热**：小流量起步 + JIT/缓存/连接预热，避免冷启动毛刺。
9. **注册中心 CP/AP**：服务发现倾向 AP，协调选主必须 CP；注册中心挂了存量调用不受影响。
10. **链路追踪**：TraceId + Span 树，通过 RPC attachment 透传。
11. **超时排查**：先分个别慢还是全部慢，再看 GC/线程池/下游依赖/流量突增。
12. **泛化调用**：网关调 RPC 的标准方式，接口名 + 方法名 + 参数类型 + Map 参数。
