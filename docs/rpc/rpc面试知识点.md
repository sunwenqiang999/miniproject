## 一、RPC 基础概念

### 1.1 什么是 RPC？

RPC（Remote Procedure Call，远程过程调用）是一种让程序**像调用本地方法一样调用远程服务**的通信方式。调用方不需要关心网络传输、序列化、寻址等细节，由 RPC 框架屏蔽。

**核心目标：**
- 屏蔽网络通信细节，让远程调用和本地调用的编码体验一致
- 提供比裸 HTTP 更高的性能和更强的服务治理能力

**核心特点：**
- 透明性：调用方感知不到远程过程的存在
- 高性能：一般采用 TCP 长连接 + 二进制序列化
- 服务治理：注册发现、负载均衡、熔断、限流、监控等能力
- 强契约：通常基于接口定义（IDL 或 Java 接口），类型安全

### 1.2 为什么需要 RPC？

单体架构拆分为微服务后，服务之间需要跨进程、跨机器通信。如果每个服务都手写 HTTP 客户端，会面临：

1. **重复建设**：每个调用方都要处理连接管理、序列化、异常、超时重试。
2. **服务寻址困难**：服务实例动态上下线，IP 列表写死无法维护。
3. **治理能力缺失**：负载均衡、熔断、限流、监控需要统一框架支持。
4. **性能不足**：HTTP/1.1 短连接 + 文本序列化在高频内部调用场景开销大。

RPC 框架把这些通用能力沉淀下来，业务只写接口和实现。

### 1.3 一次 RPC 调用发生了什么？

```text
客户端调用方                                        服务端提供方
    │                                                  │
    │  1. 调用接口代理对象的方法                          │
    ▼                                                  │
 动态代理（Proxy）                                       │
    │  2. 封装调用信息（接口、方法、参数）                  │
    ▼                                                  │
 序列化（Protobuf/Kryo/Hessian）                        │
    │  3. 编码为 RPC 协议报文                            │
    ▼                                                  │
 网络传输（Netty/TCP 长连接）  ────── 4. 发送请求 ───────▶  网络接收（Netty）
                                                           │
                                                           ▼  5. 解码 + 反序列化
                                                       路由到具体实现类
                                                           │
                                                           ▼  6. 反射调用业务方法
                                                       执行结果原路返回
```

**面试回答：**

> 一次 RPC 调用大致分为：客户端通过动态代理拦截接口调用，把接口名、方法名、参数封装成请求对象，经过序列化和协议编码后通过 TCP 长连接发送给服务端；服务端解码反序列化后，根据服务名找到具体实现，通过反射执行方法，再把结果序列化后原路返回。中间还会涉及服务发现（从注册中心拿到提供者列表）、负载均衡（选出一个实例）、过滤器链（熔断限流、链路追踪埋点）等环节。

### 1.4 RPC 与本地调用对比

| 对比项 | 本地调用 | RPC 调用 |
|--------|----------|----------|
| 执行位置 | 同一进程内 | 跨进程、跨机器 |
| 失败可能 | 基本只有代码异常 | 网络超时、丢包、对端宕机、序列化失败 |
| 延迟 | 纳秒~微秒级 | 毫秒级，受网络影响 |
| 参数传递 | 内存引用，零拷贝 | 必须序列化后网络传输 |
| 结果确定性 | 调用结果确定 | 超时后无法确定对端是否执行成功 |
| 事务 | 本地事务 | 需要分布式事务/最终一致性 |

> 面试高频追问：**RPC 超时后怎么知道对端执行没执行？** 答案是不知道，这就是为什么需要幂等设计和重试控制，详见实战文档。

### 1.5 RPC 与 HTTP/REST 对比

| 对比项 | RPC（Dubbo/gRPC） | HTTP/REST |
|--------|-------------------|-----------|
| 传输协议 | TCP 长连接为主（gRPC 用 HTTP/2） | HTTP/1.1 为主 |
| 序列化 | 二进制（Protobuf/Kryo），体积小 | JSON 文本为主，体积大 |
| 性能 | 高，连接复用 + 二进制 | 相对较低 |
| 服务治理 | 框架内置注册发现、负载均衡 | 通常依赖网关或额外组件 |
| 接口契约 | 强类型 IDL/接口 | 松散，靠文档约束 |
| 可读性/调试 | 二进制不易抓包阅读 | 文本可读，curl 即可调试 |
| 跨语言 | gRPC/Thrift 好，Dubbo 偏弱 | 天然跨语言 |
| 典型场景 | 内部服务间高频调用 | 对外 API、浏览器交互 |

**面试回答：**

> RPC 和 HTTP 不是对立关系，RPC 是一种调用范式，HTTP 也可以作为 RPC 的传输协议（比如 gRPC 基于 HTTP/2）。选型上：公司内部微服务之间高频调用、对性能和服务治理要求高，用 Dubbo/gRPC 这类 RPC 框架；对外开放的 API、需要浏览器直接访问、跨组织协作，用 RESTful HTTP 更合适。

### 1.6 RPC 常见使用场景

| 场景 | 说明 | 典型框架 |
|------|------|----------|
| 微服务间调用 | 订单服务调用库存、用户服务 | Dubbo、Spring Cloud |
| 跨语言调用 | Java 调 Go、C++ 服务 | gRPC、Thrift |
| 高性能内部调用 | 广告、推荐、交易核心链路 | Dubbo、brpc、gRPC |
| 移动端/前端直连后端 | 需要强契约和多路复用 | gRPC、gRPC-Web |
| 大数据/基础设施 | HDFS、HBase 内部通信 | Hadoop RPC、Protobuf |

## 二、RPC 核心组件

### 2.1 RPC 框架的核心模块

一个完整的 RPC 框架通常包含以下模块：

| 模块 | 职责 | 常见实现 |
|------|------|----------|
| 动态代理 | 生成接口代理，拦截本地调用 | JDK Proxy、Javassist、ByteBuddy |
| 序列化 | 对象与字节流互转 | Protobuf、Kryo、Hessian、JSON |
| 网络通信 | TCP 连接管理、数据收发 | Netty、Mina |
| 协议编解码 | 自定义协议、处理粘包拆包 | 协议头 + 长度字段 |
| 注册中心 | 服务注册与发现 | ZooKeeper、Nacos、Etcd |
| 负载均衡 | 从多个提供者中选一个 | 随机、轮询、最少活跃、一致性 Hash |
| 集群容错 | 失败重试、快速失败、熔断 | Failover、Failfast、Failsafe |
| 过滤器链 | 埋点、鉴权、限流、上下文传递 | Filter/Interceptor |

**面试常问：如果让你设计一个 RPC 框架，需要考虑哪些方面？**

> 可以按上面模块逐一展开：先用动态代理屏蔽调用细节，用 Netty 做 NIO 网络通信并维持长连接，用 Protobuf/Kryo 做序列化，自定义带魔数和长度字段的协议解决粘包拆包，用 ZooKeeper/Nacos 做注册发现，加负载均衡和失败重试等集群容错策略，最后用过滤器链做限流、熔断、链路追踪等扩展。

### 2.2 一次完整调用中的关键路径

```text
Consumer 端：
接口代理 -> 集群容错(Cluster) -> 路由(Router) -> 负载均衡(LoadBalance)
        -> 过滤器链 -> 序列化 -> 编码 -> Netty 发送

Provider 端：
Netty 接收 -> 解码 -> 反序列化 -> 线程池分发 -> 过滤器链
        -> 反射调用实现 -> 结果序列化回传
```

关键理解：
- **集群容错在客户端**：重试、快速失败等策略由调用方执行。
- **负载均衡在客户端**：注册中心只给列表，选哪台由客户端决定（区别于 Nginx 服务端负载均衡）。
- **业务线程池在服务端**：IO 线程只负责读写，业务逻辑交给独立线程池，避免阻塞网络收发。

## 三、主流 RPC 框架对比

### 3.1 Dubbo vs gRPC vs Spring Cloud OpenFeign

| 对比项 | Dubbo | gRPC | OpenFeign |
|--------|-------|------|-----------|
| 出品方 | Apache（阿里开源） | Google | Spring Cloud |
| 传输协议 | 自有协议(TCP)、Triple(HTTP/2) | HTTP/2 | HTTP/1.1 |
| 序列化 | Hessian2、Kryo、Protobuf 等可选 | Protobuf | JSON |
| 接口定义 | Java 接口 | .proto IDL 文件 | Java 接口 + 注解 |
| 跨语言 | 较弱（Triple 改善） | 强，官方多语言 | 弱，主要 Java |
| 服务治理 | 非常丰富（路由、限流、灰度） | 较弱，需配合 Service Mesh | 依赖 Spring Cloud 组件 |
| 注册中心 | ZK、Nacos、Etcd 等 | 需自行集成 | Eureka、Nacos |
| 典型场景 | 国内 Java 微服务 | 跨语言、云原生 | Spring 技术栈快速开发 |

### 3.2 其他常见框架

| 框架 | 特点 | 使用方 |
|------|------|--------|
| Thrift | Facebook 开源，IDL + 代码生成，跨语言 | 早期大型互联网公司 |
| brpc | 百度开源 C++ RPC，性能极高 | 百度系、对性能敏感场景 |
| Tars | 腾讯开源，含运维管理平台 | 腾讯系 |
| Motan | 微博开源 Java RPC | 微博 |
| sofa-rpc | 蚂蚁开源，金融级 | 蚂蚁系 |

### 3.3 框架选型面试回答模板

> 如果是 Java 技术栈、对服务治理要求高，选 Dubbo；如果有多语言诉求或者是云原生架构，选 gRPC 配合 Kubernetes/Service Mesh；如果团队全是 Spring 且追求开发效率，可以用 OpenFeign + Nacos。核心考量点是：性能要求、跨语言需求、服务治理能力、团队技术栈和生态成熟度。

## 四、高频面试速记

1. **什么是 RPC？** 像调本地方法一样调远程服务，框架屏蔽网络、序列化、寻址细节。
2. **RPC 和 HTTP 的区别？** RPC 是范式，多用 TCP 长连接 + 二进制序列化，性能高、治理强；HTTP 文本协议可读性好、跨语言天然支持，适合对外。
3. **一次 RPC 调用流程？** 代理拦截 -> 封装请求 -> 序列化 -> 网络发送 -> 服务端反序列化 -> 反射执行 -> 结果回传。
4. **负载均衡在哪一端？** RPC 一般是客户端负载均衡，从注册中心拿到列表后本地选择。
5. **常见框架？** Dubbo（Java、治理强）、gRPC（跨语言、HTTP/2）、Feign（Spring 生态、HTTP）。
6. **为什么 RPC 比 HTTP 快？** 长连接复用减少握手、二进制序列化体积小、协议头开销小。
7. **RPC 的代价？** 超时语义不确定、调试困难、强耦合接口版本管理复杂。
