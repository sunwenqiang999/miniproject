# 内存飙升场景题排查思路（通用 + Java + Go）

## 阅读建议

内存飙升与 CPU 飙高并列为生产环境两大高频场景题。考察链路同样是"**原因分类 → 排查步骤 → 工具使用 → 定位到代码 → 解决方案**"，但内存问题多了一个终极形态：**OOM（Out Of Memory）**。

| 视角 | 内容重点 |
|------|----------|
| 通用（Linux/系统） | RSS/VSS 区分、内存泄漏、缓存滥用、swap、OOM Killer、容器 memory limit |
| Java | 堆内存泄漏、堆外内存泄漏、元空间溢出、GC 调优、jmap/MAT/Arthas |
| Go | slice/闭包引用泄漏、goroutine 泄漏连带内存、逃逸分析、pprof heap |

## 一、通用视角：内存飙升的可能原因

### 1.1 先搞懂几个内存指标

| 指标 | 含义 | 说明 |
|------|------|------|
| VSS（Virtual Set Size） | 虚拟内存大小 | 进程申请的地址空间，不代表实际占用，**看内存问题不要看它** |
| RSS（Resident Set Size） | 常驻内存大小 | 实际占用物理内存的大小，**排查内存飙升主要看它** |
| PSS（Proportional Set Size） | 按比例分摊的物理内存 | 共享库按进程数分摊，容器/系统级统计更准确 |

```bash
# 查看进程 RSS
ps -o pid,rss,vsz,cmd -p <pid>
# RSS 单位是 KB

# 更详细的内存映射分布
cat /proc/<pid>/smaps_rollup
# Rss / Pss / Swap 各项一目了然

# 系统级内存
free -h
# available 才是真正可用内存，free 会包含可回收的 cache
```

**命令参数说明：**

| 命令 | 参数 | 含义 |
|------|------|------|
| `ps -o pid,rss,vsz,cmd` | `-o` | 自定义输出列（output）：pid 进程号、rss 常驻内存（KB）、vsz 虚拟内存、cmd 启动命令 |
| | `-p <pid>` | 只显示指定 PID 的进程 |
| `cat /proc/<pid>/smaps_rollup` | 无参 | smaps 的汇总版本，直接给出整个进程的 Rss/Pss/Swap 合计值，比逐段看 smaps 高效 |
| `free -h` | `-h` | 人类可读单位（human-readable，自动换算 GB/MB）；也可用 `-m`（固定 MB）、`-g`（固定 GB） |

### 1.2 原因总览

| 类别 | 具体原因 | 典型特征 |
|------|----------|----------|
| 业务负载 | 流量突增导致缓存/对象数量上涨 | 内存与 QPS 同步，流量回落后回落 |
| 内存泄漏 | malloc 未 free、缓存只增不减 | 内存阶梯式上涨，永不回落，最终 OOM |
| 缓存滥用 | 本地缓存无淘汰策略、缓存 Key 无限增长 | 老年代/堆持续增长 |
| 大对象 | 一次性加载大文件、大查询结果集（未分页） | 内存瞬间尖刺 |
| 系统层面 | page cache 占用、tmpfs、内存碎片 | 进程内存不高但系统内存高 |
| 外部因素 | 病毒、共享库内存泄漏 | 非业务进程占用 |
| 容器环境 | 超过 memory limit 被 OOM Kill | 容器重启，exit code 137 |

### 1.3 通用排查步骤

```bash
# 第一步：确认哪个进程吃内存
top -c   # 按 M（按内存排序）

# 第二步：看进程内存分布
cat /proc/<pid>/smaps_rollup   # RSS/PSS/Swap 分布
pmap -x <pid> | sort -k3 -n -r | head   # 按内存排序的映射区

# 第三步：判断是"泄漏"还是"高水位"
# 观察内存曲线：阶梯式上涨不回落 → 泄漏
#              随流量波动 → 容量问题

# 第四步：系统级检查
vmstat 1        # si/so 列非零说明在用 swap（性能劣化前兆）
dmesg -T | grep -i "killed process"   # 是否发生过 OOM Kill
```

**命令参数说明：**

| 命令 | 参数 | 含义 |
|------|------|------|
| `top -c` | `-c` | 显示完整命令行；进入交互界面后按 `M` 按内存排序、按 `P` 按 CPU 排序 |
| `pmap -x <pid>` | `-x` | 扩展格式（extended），显示每个内存映射区的 RSS/Dirty 明细 |
| `sort -k3 -n -r` | `-k3` | 按第 3 列（RSS）排序；`-n` 按数值比较；`-r` 倒序，最大的排在前面 |
| `vmstat 1` | `1` | 每 1 秒采样一次；重点看 `si`/`so`（swap in/out），长期非零说明物理内存不足 |
| `dmesg -T` | `-T` | 把内核日志时间戳转为可读日期（默认是开机以来的秒数）；`\| grep -i` 忽略大小写过滤 OOM 记录 |

### 1.4 Linux OOM Killer 机制

- 物理内存 + swap 耗尽时，内核按 `oom_score`（与 RSS 正相关）选择牺牲进程。
- 容器内超过 memory limit 触发 **cgroup OOM**，进程被 SIGKILL（exit code 137）。
- **重要区别**：cgroup OOM 是"硬顶"，没有 swap 可用，超了直接杀；宿主机 OOM 才有 swap 缓冲。

```bash
# 查看容器是否被 OOM Kill 过
kubectl describe pod <pod> | grep -A 3 "Last State"
# Reason: OOMKilled, Exit Code: 137
```

**命令参数说明：**

| 命令 | 参数 | 含义 |
|------|------|------|
| `kubectl describe pod <pod>` | 无参 | 输出 Pod 详情与事件；`Last State: Terminated → Reason: OOMKilled → Exit Code: 137` 即因超 memory limit 被杀 |
| `grep -A 3 "Last State"` | `-A 3` | 显示匹配行及其后 3 行（After），正好覆盖 Reason 和 Exit Code |
| | 补充 | Exit Code 137 = 128 + 9（SIGKILL）；143 = 128 + 15（SIGTERM，正常滚动更新） |

### 1.5 容器环境特有问题

- **JVM/Go 不感知 memory limit**：JVM 老版本按宿主机内存算堆大小，容器 limit 4G 但 JVM 默认堆 = 宿主机内存 1/4（如 16G），直接被 cgroup OOM Kill。
  - JDK 8u191+ / JDK 10+：使用 `-XX:+UseContainerSupport`（默认开启）
  - 或显式指定：`-Xmx`、`-XX:MaxMetaspaceSize`、`-Xss`
- **page cache 计入 cgroup**：文件读写产生的 page cache 算在容器 cgroup 内，可能"看起来"内存高但可回收。

## 二、Java 视角：内存飙升的可能原因

### 2.1 Java 内存区域回顾（定位问题的地图）

| 区域 | 存放内容 | 溢出报错 |
|------|----------|----------|
| 堆（Heap） | 对象实例、数组 | `java.lang.OutOfMemoryError: Java heap space` |
| 元空间（Metaspace） | 类元数据 | `OutOfMemoryError: Metaspace` |
| 线程栈 | 线程栈帧 | `OutOfMemoryError: unable to create new native thread` |
| 直接内存 | NIO DirectBuffer | `OutOfMemoryError: Direct buffer memory` |
| 代码缓存 | JIT 编译代码 | `OutOfMemoryError: CodeCache` |

### 2.2 原因分类（按概率排序）

| 排名 | 原因 | 典型场景 |
|------|------|----------|
| 1 | **堆内存泄漏** | 静态集合持有对象、ThreadLocal 未 remove、缓存无界 |
| 2 | **缓存无淘汰** | 手写 Map 缓存无过期/上限，或 Guava Cache 参数不当 |
| 3 | **大对象/大结果集** | 一次 SQL 查询百万行、大文件一次性读入 |
| 4 | **ThreadLocal 泄漏** | 线程池场景下 ThreadLocal 未清理（Entry 的 key 是弱引用，value 是强引用） |
| 5 | **类加载器泄漏** | 热部署/动态代理（CGLIB）生成类未卸载，Metaspace 涨 |
| 6 | **堆外内存泄漏** | Netty DirectBuffer 未释放、NIO 泄漏 |
| 7 | **线程数过多** | 每线程 1MB 栈 × 数千线程，native 内存暴涨 |

### 2.3 经典内存泄漏场景（面试必背）

```java
// 1. 静态集合持有对象（生命周期 = JVM 生命周期）
static Map<String, Object> cache = new HashMap<>();
public void handle(String key) {
    cache.put(key, new BigObject()); // 只进不出，永不回收
}

// 2. ThreadLocal 在线程池中未 remove
private static ThreadLocal<BigContext> ctx = new ThreadLocal<>();
public void handle() {
    ctx.set(new BigContext());
    // 忘记 ctx.remove()
    // 线程池线程不死，Entry.value 强引用一直存在
}

// 3. 监听器/回调未注销
listenerRegistry.register(this);
// 对象用完后没有 unregister，注册表一直持有引用

// 4. 连接/流未关闭
InputStream in = url.openStream();
// 没有 try-with-resources，异常路径泄漏

// 5. equals/hashCode 不当导致 HashMap "丢" key
// key 的 hashCode 可变，put 后再也无法 get/remove，条目永久滞留
```

### 2.4 Java 排查工具链

#### 方式一：原生工具（面试必背）

> **前置疑问：为什么这里没有"定位线程"这一步？**
>
> - **PID 从哪来**：1.3 节通用排查第一步（`top -c` 按 `M` 内存排序）或监控告警直接给出进程，Java 工具链默认已拿到 PID。
> - **为什么不需要定位线程**：堆内存是**进程内所有线程共享**的，一个对象可能被几十个线程引用，"哪个线程占的内存"这个问题本身不成立。CPU 是按线程消耗的（所以要 `top -Hp`），内存是按对象+引用链存在的（所以走 jmap → MAT 引用链）。
> - **对比记忆**：CPU 排查 = 进程 → 线程 → 堆栈（三级下钻）；内存排查 = 进程 → 内存区域（堆/元空间/堆外）→ 对象/引用链（两级下钻）。
> - **两个例外会"回到线程视角"**（但都是分析产出，不是排查起点）：① ThreadLocal 泄漏时 MAT 引用链会显示对象挂在哪个线程上；② 线程数过多导致 native 内存涨时，看的是 jstack 里的**线程总数**（每线程约 1MB 栈），而非单个线程。

```bash
# 0. 前置：确认目标进程（来自 1.3 节通用排查或监控告警）
top -c    # 按 M 内存排序，拿到高内存 Java 进程的 PID
# 例：PID = 12345 的 java 进程 RSS 7.8G，其余进程正常

# 1. 看 GC 情况：老年代是否持续打满、Full GC 后是否回收
jstat -gcutil <pid> 1000
# O 列（老年代使用率）Full GC 后仍接近 100% → 内存泄漏
# FGC 持续增长 + FGCT 时间累加 → 频繁 Full GC

# 2. 查看堆内对象统计
jmap -histo <pid> | head -20
# 按实例数/字节数排序，看哪个类异常多

# 3. dump 堆快照（注意：会 STW，大堆耗时久，生产慎用）
jmap -dump:live,format=b,file=heap.hprof <pid>
# live 参数：先触发一次 Full GC 只保留存活对象

# 4. MAT 分析 heap.hprof
# 打开 Leak Suspects 报告 → 看 Dominator Tree → 找 GC Roots 引用链
# "Path to GC Roots (exclude weak/soft references)" 是定位泄漏的关键
```

**命令参数说明：**

| 命令 | 参数 | 含义 |
|------|------|------|
| `jstat -gcutil <pid> 1000` | `-gcutil` | 各代使用率百分比汇总：S0/S1（幸存区）、E（Eden）、O（老年代）、M（元空间）、YGC/FGC（GC 次数）、GCT（总耗时）；`1000` 为采样间隔（毫秒） |
| `jmap -histo <pid>` | `-histo` | 输出堆对象直方图：类名、实例数、占用字节数，按大小降序；`\| head -20` 只看前 20 个大户 |
| `jmap -dump:live,format=b,file=...` | `live` | dump 前先触发 Full GC，只保留存活对象（减小体积、排除垃圾干扰） |
| | `format=b` | 二进制格式（binary），MAT/JProfiler 可直接打开 |
| | `file=heap.hprof` | 输出文件路径；注意文件会很大（≈堆大小），确保磁盘空间足够 |

#### 方式二：Arthas（生产推荐，不 dump 大堆）

```bash
# 查看堆概况（相当于图形化 dashboard）
dashboard

# 实时观察已加载类和对象数量
vmtool --action getInstances --className com.xxx.BigObject --limit 10

# 观察指定方法的调用与对象创建
watch com.xxx.Service handle '{params, returnObj}' -x 2

# 触发 heap dump（同 jmap）
heapdump /tmp/heap.hprof
```

**命令参数说明：**

| 命令 | 参数 | 含义 |
|------|------|------|
| `dashboard` | 无参 | Arthas 实时面板：线程状态、各代内存使用率、GC 次数，每秒自动刷新 |
| `vmtool --action getInstances` | `--action` | 指定动作，`getInstances` 表示"获取堆中指定类的所有存活实例" |
| | `--className` | 目标类的全限定名 |
| | `--limit 10` | 最多返回 10 个实例，防止大堆下输出爆炸 |
| `watch <类> <方法> '{...}'` | `'{params, returnObj}'` | OGNL 表达式：观察方法的入参和返回值（`throwExp` 可观察异常） |
| | `-x 2` | 对象展开深度（expand）为 2 层；默认 1 层太浅看不到字段内容，最大 4 |
| `heapdump <路径>` | 无参 | 等同 `jmap -dump:live`，只 dump 存活对象生成 hprof 文件 |

#### 方式三：堆外内存排查

```bash
# NMT（Native Memory Tracking，需启动参数 -XX:NativeMemoryTracking=summary）
jcmd <pid> VM.native_memory summary
# 对比 Commit 内存与 RSS 差值，定位堆外增长点

# Netty 场景：开启泄漏检测
-Dio.netty.leakDetection.level=PARANOID
# 日志中出现 "LEAK: ByteBuf.release() was not called" 即泄漏点

# pmap + gdb 定位 native 泄漏（终极手段）
pmap -x <pid> | sort -k3 -n -r | head
```

**命令参数说明：**

| 命令 | 参数 | 含义 |
|------|------|------|
| `jcmd <pid> VM.native_memory summary` | `summary` | 输出 native 内存分类汇总（Java Heap/Class/Thread/Code/GC/Internal 等），需启动参数 `-XX:NativeMemoryTracking=summary` 开启 |
| | 配套命令 | `VM.native_memory baseline` 打基线 → 一段时间后 `VM.native_memory summary.diff` 对比增量，是定位堆外泄漏增长点的标准流程 |
| `-Dio.netty.leakDetection.level` | 四个级别 | DISABLED（关闭）→ SIMPLE（约 1% 采样，默认）→ ADVANCED（采样+记录详细创建位置）→ PARANOID（全量检测，开销大仅压测用） |
| `pmap -x <pid>` | `-x` | 扩展格式显示每个映射区的 RSS/Dirty；进程 RSS 减去 NMT 堆内 Commit 即为堆外占用量 |

### 2.5 Java 场景题标准回答模板

> **第一步**：确认是堆内还是堆外：`jstat -gcutil` 看老年代，若堆使用率正常但 RSS 持续涨 → 堆外/元空间/线程栈问题。
> **第二步**：堆内问题 → `jmap -histo` 看对象排行，`jmap -dump` + MAT 看 GC Roots 引用链，定位泄漏源。
> **第三步**：堆外问题 → NMT + pmap 定位；Netty 用泄漏检测参数。
> **第四步**：区分"泄漏"与"容量不足"：Full GC 后能回收 → 容量不足（调大堆/优化缓存）；回收不掉 → 泄漏（改代码）。
> **第五步**：修复后观察内存曲线是否平稳、Full GC 频率是否下降。

### 2.6 Java 实战排查案例（完整走一遍）

**背景**：用户中心服务（4C8G 容器，JDK8，堆 4G）老年代使用率每天涨 10%，一周后持续 Full GC，接口大面积超时，监控显示堆内存"锯齿越来越浅"（每次 Full GC 后的高位不断抬升）。

**第一步：jstat 确认是堆内问题**

```bash
jstat -gcutil 12345 1000
#  S0     S1     E      O      M     YGC    YGCT    FGC    FGCT     GCT
#  0.00 100.00  85.32  99.87  96.20   4521   88.12   892   512.33   600.45
#  0.00 100.00  90.11  99.91  96.20   4522   88.25   893   512.98   601.23
# O 列 99.9%，FGC 每秒 +1 → 老年代打满且 Full GC 回收不掉
# 手动触发一次 Full GC（jcmd 12345 GC.run）后再看：O 仍 99.2% → 泄漏实锤
```

**第二步：jmap -histo 看对象排行**

```bash
jmap -histo 12345 | head -10
#  num     #instances         #bytes  class name
#     1:      28451203      1589287368  [Lcom.user.session.SessionAttr;
#     2:      28451203      682824872  com.user.session.SessionAttr
#     3:        945123       45283456  java.util.concurrent.ConcurrentHashMap$Node
# SessionAttr 实例 2845 万个，占 2.2GB → 会话属性对象泄漏
```

**第三步：dump + MAT 找引用链**

```bash
jmap -dump:live,format=b,file=/tmp/heap.hprof 12345
# MAT 打开 → Leak Suspects：
# "ThreadLocal" 占 2.3GB (58.2%)
# → Path to GC Roots（排除弱引用）：
#   SessionAttr
#     └─ value of ThreadLocal$ThreadLocalMap$Entry
#       └─ ThreadLocalMap (线程 172 的属性)
#         └─ http-nio-8080-exec-172 (Tomcat 工作线程)
# → ThreadLocal 值被 Tomcat 线程池线程持有，线程不死，value 永不回收
```

**第四步：定位问题代码**

```java
// 问题代码：网关鉴权过滤器把用户会话塞进 ThreadLocal，但只在"正常路径"清理
public class AuthFilter implements Filter {
    private static final ThreadLocal<SessionAttr> CURRENT_SESSION = new ThreadLocal<>();

    public void doFilter(...) {
        SessionAttr session = parseToken(token);
        CURRENT_SESSION.set(session);
        try {
            chain.doFilter(req, resp);
        } finally {
            // 修复前：没有 finally，异常路径（如下游超时抛异常）跳过了 remove
            CURRENT_SESSION.remove();
        }
    }
}
```

**第五步：修复与验证**

```bash
# 修复：把 remove() 放进 finally（如上），保证任何路径都清理
# 上线后观察一周：
jstat -gcutil 12345 5000
#  S0     S1     E      O      M     YGC    YGCT   FGC    FGCT     GCT
#  0.00  62.31  70.22  58.45  96.20   5102  102.11   893   512.33   614.44
# O 列稳定在 58%，FGC 不再增长 → 修复成功
```

**案例复盘**：Full GC 回收不掉 → jmap -histo 发现 2845 万 SessionAttr → MAT 引用链指向 ThreadLocal → 异常路径漏了 remove()。**ThreadLocal 泄漏三要素**：线程池（线程不死）+ ThreadLocal.set（Entry.value 强引用）+ 忘记 remove。这是 Java 内存泄漏面试题的第一名场景。

## 三、Go 视角：内存飙升的可能原因

### 3.1 原因分类

| 排名 | 原因 | 说明 |
|------|------|------|
| 1 | **slice 底层数组被引用** | 大 slice 切一小片长期持有，整个底层数组无法回收 |
| 2 | **goroutine 泄漏** | 每个 goroutine 至少 2KB 栈 + 持有的变量，泄漏累积 |
| 3 | **map 只增不减** | map 删除 key 不会缩容，bucket 内存不释放 |
| 4 | **闭包捕获引用** | 闭包长期存活导致捕获的大对象无法回收 |
| 5 | **全局变量/缓存无淘汰** | 全局 map 做缓存无过期机制 |
| 6 | **逃逸过多** | 大量对象逃逸到堆上，GC 压力大 |
| 7 | **CGO 内存** | C 侧 malloc 的内存 Go GC 无法感知，需手动 free |

### 3.2 Go 特有的经典泄漏场景（面试必背）

```go
// 1. slice 切片引用大数组
func leak() {
    big := make([]byte, 100<<20) // 100MB
    small := big[:10]            // 只用前 10 字节
    globalRef = small            // 但整个 100MB 底层数组无法回收！
}
// 修复：small := append([]byte{}, big[:10]...) 拷贝出来

// 2. goroutine 阻塞泄漏（连带内存泄漏）
func leak2() {
    ch := make(chan struct{})
    go func() {
        <-ch // 没人发送，goroutine 永久阻塞，栈内存+捕获变量全泄漏
    }()
}

// 3. map 不缩容
m := make(map[int][1024]byte)
for i := 0; i < 1<<20; i++ { m[i] = [1024]byte{} }
for k := range m { delete(m, k) } // 删光，内存也不还给 runtime
// 修复：定期重建 map（换新 map，旧的整体回收）

// 4. time.Ticker 未 Stop
t := time.NewTicker(time.Second)
defer t.Stop() // 忘记写，ticker 内部 timer 永久持有引用

// 5. http resp.Body 未关闭
resp, _ := http.Get(url)
defer resp.Body.Close() // 忘记写，连接和 buffer 泄漏
```

### 3.3 Go 内存指标：RSS 高 ≠ 泄漏（重要认知）

- Go runtime **不会立即把内存还给 OS**：`GOGC` 触发 GC 后，内存先归还到 runtime 的空闲列表（`HeapIdle`），通过 `MADV_FREE` 惰性归还 OS。
- 因此 Go 服务 RSS 常见"锯齿缓慢上涨后平稳"，这是**正常行为**，不是泄漏。
- 判断泄漏的正确指标：`HeapInuse`（活跃堆）是否持续上涨不回落。

```bash
# 查看 runtime 内存指标
curl http://localhost:6060/debug/pprof/heap?debug=1 | head -30
# HeapInuse 持续上涨 → 真泄漏
# HeapIdle 涨但 HeapInuse 平稳 → 正常，runtime 缓存

# 强制归还 OS（应急手段，会 STW）
debug.FreeOSMemory()
```

**命令参数说明：**

| 命令 | 参数 | 含义 |
|------|------|------|
| `curl .../heap?debug=1` | `?debug=1` | 文本格式输出 runtime.MemStats 摘要：HeapAlloc（当前分配）、HeapSys（向 OS 申请）、HeapIdle（空闲）、HeapInuse（使用中）、HeapReleased（已还 OS） |
| `debug.FreeOSMemory()` | 无参 | 强制 GC 并把空闲内存立即归还 OS；会触发 STW，仅应急/验证用，禁止在业务代码中常规调用 |

### 3.4 Go 排查工具链

#### 方式一：heap profile（核心手段）

```bash
# 1. 抓当前堆 profile
go tool pprof http://localhost:6060/debug/pprof/heap

# 2. 关键：对比两个时间点，找"增长"而不是"总量"
go tool pprof -base heap_t1.pb.gz heap_t2.pb.gz
# 差值分析：两个时间点之间哪些对象在增长 → 泄漏源

# 3. 常用视图
(pprof) top 10            # 按内存排序的函数
(pprof) list funcName     # 定位到具体分配行
(pprof) sample_index=alloc_space   # 看累计分配（找分配大户）
(pprof) sample_index=inuse_space   # 看当前存活（找泄漏）
```

**命令参数说明：**

| 命令 | 参数 | 含义 |
|------|------|------|
| `go tool pprof -base a.pb.gz b.pb.gz` | `-base` | 以第一个 profile 为基线，展示两个时间点的**差值**；泄漏排查只看增量、不看总量（新版可用 `-diff_base`） |
| `sample_index=alloc_space` | alloc_space | 按"累计分配总量"排序：找分配大户（GC 压力的来源） |
| `sample_index=inuse_space` | inuse_space | 按"当前存活量"排序：找泄漏对象（heap 的默认视图） |
| | 其他维度 | `alloc_objects`（累计分配次数）、`inuse_objects`（当前存活对象数） |

#### 方式二：goroutine 泄漏检查

```bash
# goroutine 数量是内存泄漏的前置指标
curl http://localhost:6060/debug/pprof/goroutine?debug=1 | head -5

# 数量持续增长 → dump 栈，统计阻塞位置
curl http://localhost:6060/debug/pprof/goroutine?debug=2 > goroutine.txt
# 找大量阻塞在 chan send/receive、lock 的 goroutine
```

**命令参数说明：**

| 参数 | 含义 |
|------|------|
| `?debug=1` | 文本汇总：goroutine 总数 + 按"创建来源函数"分组统计（泄漏排查最常用） |
| `?debug=2` | 输出每个 goroutine 的完整堆栈（类似 jstack），定位具体阻塞点 |
| `> goroutine.txt` | 重定向落盘，便于用 grep/awk 统计相同堆栈的 goroutine 数量 |

#### 方式三：逃逸分析（开发期预防）

```bash
# 编译期查看哪些变量逃逸到堆
go build -gcflags="-m" ./...
# "escapes to heap" 的行就是堆分配点

# 对比基准测试内存分配
go test -bench . -benchmem
# allocs/op 高的函数优先优化
```

**命令参数说明：**

| 命令 | 参数 | 含义 |
|------|------|------|
| `go build -gcflags="-m"` | `-gcflags` | 传递编译器 flags；`-m` 输出逃逸分析结果，可用 `-m -m` 查看更详细的逃逸决策原因 |
| `go test -bench . -benchmem` | `-bench .` | 运行所有 Benchmark 函数（`.` 是正则，匹配全部） |
| | `-benchmem` | 额外输出内存指标：`B/op`（每次操作分配字节数）、`allocs/op`（每次操作分配次数） |

### 3.5 Go 场景题标准回答模板

> **第一步**：先看 goroutine 数量是否暴涨（内存泄漏常伴随 goroutine 泄漏）。
> **第二步**：抓 heap profile，用 `-base` 对比两个时间点差值，定位增长对象。
> **第三步**：区分"真泄漏"与"runtime 缓存"：看 `HeapInuse` 而不是 RSS。
> **第四步**：常见嫌疑清单：slice 引用大数组、map 不缩容、闭包捕获、Ticker/Body 未关闭。
> **第五步**：修复后观察 `HeapInuse` 曲线与 goroutine 数量是否平稳。

### 3.6 Go 实战排查案例（完整走一遍）

**背景**：推荐服务（Go 1.21，容器 limit 4G）RSS 从 800MB 一周内爬升到 3.8G，逼近 limit，随时可能 OOMKilled。GC 频率也从 5 分钟一次升到 10 秒一次。

**第一步：先看 goroutine 数量（排除连带泄漏）**

```bash
curl http://localhost:6060/debug/pprof/goroutine?debug=1 | head -1
# goroutine profile: total 2841
# 2841 个，数量正常 → 排除 goroutine 泄漏，是纯内存泄漏
```

**第二步：确认是真泄漏还是 runtime 缓存**

```bash
curl http://localhost:6060/debug/pprof/heap?debug=1 | head -12
# HeapInuse: 3.1GB     ← 活跃堆持续上涨，不是 runtime 缓存，真泄漏！
# HeapIdle: 0.4GB
# HeapReleased: 0.1GB
# RSS 3.8G ≈ HeapInuse 3.1G + runtime 开销 → 内存确实被业务对象占着
```

**第三步：抓两个时间点的 heap profile 做差值**

```bash
# 间隔 2 小时抓两次
curl -o heap_t1.pb.gz http://localhost:6060/debug/pprof/heap
sleep 7200
curl -o heap_t2.pb.gz http://localhost:6060/debug/pprof/heap

# 差值分析：只看"增长"，不看"总量"
go tool pprof -base heap_t1.pb.gz heap_t2.pb.gz
(pprof) top 5
# Showing nodes accounting for 1.2GB, 92.3% of 1.3GB total
# flat  flat%   sum%      cum   cum%
# 1.1GB 84.6%  84.6%    1.1GB 84.6%  recsys/feed.(*UserCache).Get
# 0.1GB  7.7%  92.3%   0.1GB  7.7%  runtime.mallocgc
# 2 小时内 UserCache.Get 增长了 1.1GB → 泄漏源锁定
```

**第四步：list 定位到具体分配行**

```bash
(pprof) list UserCache.Get
# ROUTINE ======================== recsys/feed.(*UserCache).Get
# 1.1GB     1.1GB (flat, cum) 84.6% of Total
#          .          .   45: func (c *UserCache) Get(userID int64) *UserProfile {
#          .          .   46:     if p, ok := c.cache[userID]; ok {
#          .          .   47:         return p
#          .          .   48:     }
#    1.1GB     1.1GB   49:     p := loadProfileFromDB(userID)   ← 第 49 行，每次未命中都从 DB 加载
#          .          .   50:     c.cache[userID] = p            ← 第 50 行，只写不删！
#          .          .   51:     return p
#          .          .   52: }
```

**第五步：定位问题代码并修复**

```go
// 问题代码：全局 map 缓存用户画像，只写不删，用户量 5000 万 → 无限膨胀
type UserCache struct {
    mu    sync.RWMutex
    cache map[int64]*UserProfile   // 无上限、无过期
}

// 修复方案一：换成带 TTL 的缓存库（推荐）
import "github.com/patrickmn/go-cache"

c := cache.New(10*time.Minute, 30*time.Minute) // 默认 TTL 10 分钟，30 分钟清理一次过期项

// 修复方案二：定期重建 map（利用"旧 map 整体可回收"的特性）
func (c *UserCache) rebuild() {
    c.mu.Lock()
    defer c.mu.Unlock()
    fresh := make(map[int64]*UserProfile, 100_000) // 新 map
    for id, p := range c.cache {
        if time.Since(p.loadedAt) < 10*time.Minute {
            fresh[id] = p // 只保留热数据
        }
    }
    c.cache = fresh // 旧 map 失去引用，整体被 GC 回收
}
```

**第六步：验证**

```bash
# 上线后观察 3 天：
curl http://localhost:6060/debug/pprof/heap?debug=1 | head -3
# HeapInuse: 620MB    ← 从 3.1GB 回落到 620MB，稳定不再上涨
# RSS 稳定在 900MB，GC 恢复到 5 分钟一次
```

**案例复盘**：RSS 爬升 + HeapInuse 同步涨 → 真泄漏（非 runtime 缓存）→ 两次 heap profile 差值分析锁定 `UserCache.Get` → `list` 定位到"map 只写不删"的代码行 → 换 TTL 缓存或定期重建。**Go 内存排查的灵魂是 `-base` 差值分析**：总量里全是正常业务对象，只有"增量"才指向泄漏点。

## 四、三视角对比总结

| 维度 | 通用 | Java | Go |
|------|------|------|-----|
| 最高频原因 | 缓存无界、泄漏 | 堆泄漏（静态集合/ThreadLocal/缓存） | slice 引用、goroutine 泄漏、map 不缩容 |
| 核心指标 | RSS/PSS | 老年代使用率、Full GC 后回收效果 | HeapInuse、goroutine 数量 |
| 核心工具 | smaps/pmap/free | jstat/jmap/MAT/Arthas/NMT | pprof heap(-base)/goroutine |
| 快照分析 | core dump | heap.hprof + MAT 引用链 | profile 差值对比 |
| 容器陷阱 | cgroup OOM（137） | JVM 不感知 limit 被 OOM Kill | runtime 不还内存被误判泄漏 |
| 特有陷阱 | page cache 计入 cgroup | Metaspace、堆外 DirectBuffer | MADV_FREE 惰性归还、CGO 内存 |

## 五、面试回答要点（30 秒版本）

1. **先分清"泄漏"还是"容量"**：内存曲线阶梯上涨不回落 = 泄漏；随流量波动 = 容量问题。
2. **Java 先看 GC**：Full GC 后老年代能降 → 容量问题；降不下去 → 泄漏，dump + MAT 找 GC Roots 引用链。
3. **Go 先看 goroutine 和 HeapInuse**：RSS 高不一定是泄漏，runtime 会缓存内存。
4. **堆外别忽略**：Java 的 DirectBuffer/Metaspace、Go 的 CGO 内存，都是"堆正常但内存涨"的元凶。
5. **容器环境**：OOMKilled（exit 137）先查 limit 与 JVM/GOMAXPROCS 配置是否匹配。
