    # Redis 原理机制面试知识点

## 一、Redis 单线程模型与 IO 多路复用

### 1.1 Redis 真的是单线程吗？

Redis 不能简单理解为“完全单线程”，更准确的说法是：**Redis 的核心命令执行线程主要是单线程**。

不同模块的线程模型如下：

| 模块 | 是否单线程 | 说明 |
|------|------------|------|
| 命令执行 | 主要单线程 | 保证命令原子性，避免锁竞争 |
| 网络 IO | Redis 6.0 前主要单线程，6.0 后可多线程 | 多线程主要处理读写和协议解析 |
| RDB 持久化 | 子进程 | `BGSAVE` 会 fork 子进程生成快照 |
| AOF 刷盘 | 后台线程/操作系统 | 根据 fsync 策略刷盘 |
| 惰性释放 | 后台线程 | `UNLINK`、异步删除大 Key |

**面试回答：**

> Redis 的命令执行核心是单线程，所以单条命令天然具备原子性，也避免了锁竞争和线程切换成本。但 Redis 并不是所有事情都单线程，持久化、异步删除、网络 IO 等部分可能使用子进程或后台线程。Redis 6.0 以后还引入了多线程 IO，但命令执行仍主要由主线程完成。

### 1.2 为什么单线程还能支持高并发？

Redis 单线程仍然快，主要原因如下：

1. **基于内存操作**：大部分读写在内存中完成。
2. **命令执行很快**：大多数命令时间复杂度是 O(1) 或 O(logN)。
3. **IO 多路复用**：一个线程可以同时监听大量客户端连接。
4. **避免锁竞争**：没有复杂的多线程锁竞争。
5. **避免频繁上下文切换**：线程模型简单。
6. **高效数据结构**：SDS、Dict、SkipList、QuickList 等。

### 1.3 IO 多路复用模型

Redis 使用 IO 多路复用同时监听多个 Socket 事件。

```text
客户端连接 1 ─┐
客户端连接 2 ─┤
客户端连接 3 ─┤      epoll/kqueue/select
客户端连接 N ─┘              │
                              ▼
                        Redis 事件循环
                              │
                              ▼
                        读取请求 -> 执行命令 -> 返回响应
```

**核心理解：**
- 一个线程不代表只能服务一个客户端。
- IO 多路复用可以让一个线程管理大量连接。
- 有连接就绪时，Redis 再处理对应事件。

### 1.4 Redis 6.0 多线程 IO

Redis 6.0 引入多线程 IO，主要为了解决网络 IO 和协议解析在高并发下成为瓶颈的问题。

**注意点：**
- 多线程 IO 不等于多线程执行命令。
- 命令执行仍由主线程完成。
- 多线程主要负责网络数据读写和协议解析。

**为什么命令执行不改成多线程？**
- 多线程执行需要大量锁控制。
- 会破坏单线程模型下的原子性和简单性。
- Redis 的瓶颈通常不是命令执行 CPU，而是网络和内存。

## 二、Redis 持久化机制

### 2.1 为什么 Redis 需要持久化？

Redis 是内存数据库，如果进程退出或机器宕机，内存数据会丢失。持久化的作用是把内存数据保存到磁盘，用于故障恢复、备份、迁移。

Redis 主要有三种持久化方式：

| 方式 | 说明 |
|------|------|
| RDB | 某一时刻的数据快照 |
| AOF | 记录每次写命令日志 |
| 混合持久化 | RDB 快照 + AOF 增量日志 |

### 2.2 RDB 文件和 AOF 文件都在磁盘吗？

是的，RDB 和 AOF 最终都是磁盘文件。

| 文件 | 常见文件名 | 本质 | 写入特点 |
|------|------------|------|----------|
| RDB | `dump.rdb` | 内存快照 | 定期或手动生成一次完整快照 |
| AOF | `appendonly.aof` | 写命令日志 | 持续追加写命令，根据 `appendfsync` 策略刷盘 |

需要注意：AOF 文件在磁盘上，但写命令不一定每次都立即同步落盘，取决于 `appendfsync` 配置：

```bash
appendfsync always    # 每条命令都刷盘，最安全但最慢
appendfsync everysec  # 每秒刷盘一次，生产常用，最多丢 1 秒数据
appendfsync no        # 交给操作系统决定，性能最好但风险较高
```

面试可以这样回答：

> RDB 和 AOF 都是 Redis 的磁盘持久化文件。RDB 是某一时刻的内存快照，常见文件是 `dump.rdb`；AOF 是写命令追加日志，常见文件是 `appendonly.aof`。RDB 是定期生成快照，恢复快但可能丢失最近数据；AOF 是持续追加写命令，数据更安全，但刷盘时机取决于 `appendfsync` 策略。

### 2.3 RDB 持久化

RDB 是 Redis 在某一时刻生成的内存数据快照。

**触发方式：**

```bash
SAVE
BGSAVE
```

| 命令 | 说明 | 是否阻塞 |
|------|------|----------|
| SAVE | 主线程同步保存快照 | 阻塞 |
| BGSAVE | fork 子进程保存快照 | 主线程短暂阻塞 fork |

**自动触发配置：**

```bash
save 900 1
save 300 10
save 60 10000
```

含义：
- 900 秒内至少 1 个 Key 被修改则触发。
- 300 秒内至少 10 个 Key 被修改则触发。
- 60 秒内至少 10000 个 Key 被修改则触发。

### 2.4 RDB 执行流程

```text
客户端写入数据
      │
      ▼
Redis 内存数据变化
      │
      ▼
触发 BGSAVE
      │
      ▼
主进程 fork 子进程
      │
      ▼
子进程生成临时 RDB 文件
      │
      ▼
替换旧 RDB 文件
```

**fork 的影响：**
- fork 期间主线程会短暂阻塞。
- 数据量越大，页表越大，fork 成本越高。
- 如果开启了写时复制，写入频繁时可能额外消耗内存。

### 2.5 RDB 优缺点

**优点：**
- 文件紧凑，适合备份。
- 恢复速度快。
- 对主线程影响较小，主要由子进程完成。

**缺点：**
- 可能丢失最近一次快照之后的数据。
- fork 子进程可能带来 CPU 和内存压力。
- 快照频率太高会影响性能，太低会增加数据丢失风险。

### 2.6 AOF 持久化

AOF 通过追加写命令日志记录数据变更。

**配置示例：**

```bash
appendonly yes
appendfsync always
appendfsync everysec
appendfsync no
```

| 策略 | 说明 | 数据安全性 | 性能 |
|------|------|------------|------|
| always | 每条写命令都 fsync | 最高 | 最低 |
| everysec | 每秒 fsync 一次 | 较高，最多丢 1 秒 | 较好 |
| no | 交给操作系统决定 | 较低 | 最高 |

**生产常用：** `appendfsync everysec`。

### 2.7 AOF 写入流程

```text
客户端执行写命令
      │
      ▼
命令追加到 AOF 缓冲区
      │
      ▼
根据 appendfsync 策略刷盘
      │
      ▼
写入 AOF 文件
```

### 2.8 AOF 重写

AOF 文件会随着写命令增加而越来越大，因此需要 AOF Rewrite。

**你说的“连续对同一个 Key 加 10 次，最后合并成一次”，对应的就是 AOF 重写机制。**

但要注意区分两个阶段：

| 阶段 | 是否合并命令 | 说明 |
|------|--------------|------|
| AOF 正常追加写入 | 不会合并 | 每条写命令都会按顺序追加到 AOF 缓冲区/文件 |
| AOF Rewrite 重写 | 会合并 | 根据当前内存状态重新生成一份更小的 AOF 文件 |

#### 2.8.1 普通 AOF 追加不会实时合并

例如客户端连续执行：

```bash
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
```

普通 AOF 文件中可能就会追加 10 条 `INCR counter`。

也就是说，AOF 正常写入时关注的是：

```text
把每条写命令安全、顺序地记录下来
```

它不会每来一条命令就判断能不能和前面的命令合并，因为这样会增加主线程处理成本，也会让 AOF 写入逻辑变复杂。

#### 2.8.2 AOF Rewrite 会根据当前数据状态合并命令

当 AOF 文件越来越大时，Redis 会触发 AOF Rewrite。

**重写不是直接压缩旧 AOF 文件，而是读取当前 Redis 内存数据，重新生成一份能恢复当前状态的最小命令集合。**

例如连续执行 10 次：

```bash
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
INCR counter
```

如果 `counter` 最终值是 `10`，重写后可以变成：

```bash
SET counter 10
```

这样恢复数据时，只需要执行一条命令，而不需要重新执行 10 条历史命令。

#### 2.8.3 更多重写示例

**示例一：同一个 String 多次修改**

原 AOF：

```bash
SET name zhangsan
SET name lisi
SET name wangwu
```

重写后：

```bash
SET name wangwu
```

因为 Redis 恢复时只需要恢复最终值 `wangwu`。

**示例二：List 多次插入**

原 AOF：

```bash
RPUSH list a
RPUSH list b
RPUSH list c
```

重写后可能变成：

```bash
RPUSH list a b c
```

**示例三：Hash 多次写字段**

原 AOF：

```bash
HSET user:1 name zhangsan
HSET user:1 age 18
HSET user:1 city shanghai
```

重写后可能变成：

```bash
HMSET user:1 name zhangsan age 18 city shanghai
```

或者新版本中用多字段 `HSET` 表达：

```bash
HSET user:1 name zhangsan age 18 city shanghai
```

**示例四：Set 多次添加元素**

原 AOF：

```bash
SADD tags java
SADD tags redis
SADD tags mysql
```

重写后可能变成：

```bash
SADD tags java redis mysql
```

#### 2.7.4 AOF Rewrite 的执行流程

```text
1. Redis 判断 AOF 文件达到重写条件
2. 主进程 fork 子进程
3. 子进程根据当前内存数据生成新的 AOF 文件
4. 主进程继续处理客户端请求
5. 重写期间新的写命令会记录到 AOF 重写缓冲区
6. 子进程生成新 AOF 后，主进程把重写缓冲区内容追加进去
7. 使用新 AOF 文件原子替换旧 AOF 文件
```

#### 2.7.5 为什么 AOF Rewrite 要用子进程？

因为重写可能需要遍历当前 Redis 中大量数据，如果放在主线程执行，会阻塞客户端请求。

使用子进程可以让主进程继续处理请求，只在 `fork` 和最终替换阶段有短暂影响。

#### 2.7.6 AOF Rewrite 的好处

- 减小 AOF 文件大小。
- 提升 Redis 重启恢复速度。
- 删除无效历史命令。
- 合并多条重复命令。
- 降低磁盘空间占用。

#### 2.7.7 面试回答模板

可以这样回答：

> AOF 正常写入时不会实时合并命令，而是把每条写命令追加到 AOF 文件中。随着 AOF 文件变大，Redis 会触发 AOF Rewrite。AOF Rewrite 不是压缩旧文件，而是根据当前内存数据重新生成一份最小命令集。比如同一个 Key 连续 `INCR` 10 次，最终值为 10，重写后可以变成一条 `SET key 10`。这样可以减少 AOF 文件大小并加快恢复速度。重写一般由子进程完成，重写期间新的写命令会进入重写缓冲区，最后追加到新 AOF 文件中，再原子替换旧文件。

#### 2.8.8 AOF 重写是发生在磁盘的吗？

这是一个非常容易踩坑的问题。准确的回答是：

> **AOF 重写的"计算过程"发生在内存中，最终的"写入落盘"才发生在磁盘上。** 它不是通过读取旧 AOF 文件在磁盘上进行合并/去重的。

##### 常见误解

很多人以为 AOF 重写的流程是：

```text
读取旧 AOF 文件 -> 在磁盘上合并/压缩命令 -> 写出新 AOF 文件
```

**这是错的。** Redis 的 AOF 重写完全不依赖旧的 AOF 文件，旧文件只是在最后被替换时才用到（被覆盖）。

##### 实际流程：基于内存快照，而非磁盘旧文件

1. 主进程 `fork` 出一个子进程（`bgrewriteaof`）。
2. 子进程基于 **fork 瞬间的内存数据快照**（利用操作系统的 Copy-On-Write 机制），遍历当前内存中所有 Key。
3. 对每个 Key，根据它的**当前值和类型**，生成一条**能直接还原该 Key 现状的最简命令**，写入一个临时 AOF 文件。
4. 主进程继续对外服务，期间产生的新写命令会同时写入 **AOF 重写缓冲区（`aof_rewrite_buf_blocks`）**。
5. 子进程写完临时文件后，通过管道通知主进程，主进程把重写缓冲区中的增量命令追加到临时文件末尾。
6. 用临时文件 **原子性 rename** 替换掉旧的 AOF 文件。

##### 各环节位置拆解

| 环节 | 位置 | 说明 |
|------|------|------|
| 数据来源 | **内存** | 遍历子进程 fork 后的内存 dataset |
| 命令生成/去重 | **内存（CPU）** | 由子进程在内存中计算出等价命令 |
| 重写缓冲区 | **内存** | 主进程新命令暂存在 `aof_rewrite_buf` 中 |
| 临时文件写入 | **磁盘** | 子进程通过 `write` / `fsync` 落盘 |
| 文件替换 | **磁盘** | `rename` 系统调用替换旧 AOF |

所以更严谨的说法是：**AOF 重写是一个"以内存为数据源、以磁盘为输出目标"的过程，计算在内存，IO 在磁盘。**

##### 举例直观理解

假设客户端依次执行：

```bash
LPUSH mylist a
LPUSH mylist b
LPUSH mylist c
LPOP  mylist
```

- **旧 AOF 文件**里会老老实实记录这 4 条命令。
- **AOF 重写**时，子进程直接看内存里 `mylist = [c, b]`，只生成一条：

  ```bash
  RPUSH mylist "b" "c"
  ```

  就能等价还原这个 Key。

这就是为什么 AOF 重写能显著压缩文件体积——它是 **"看结果反推命令"**，而不是 **"翻历史日志做去重"**。

##### 和 RDB 的关系

AOF 重写的机制其实和 RDB 生成非常相似：

- 都是 `fork` 子进程 + COW 遍历内存
- 都会占用额外内存（写多的场景下 COW 会导致内存翻倍风险）
- 区别只是**输出格式**：RDB 输出二进制快照，AOF 重写输出的是**文本化的 Redis 命令**

在 Redis 4.0+ 里还有 **混合持久化（`aof-use-rdb-preamble yes`）**：AOF 重写时，前半段直接写 RDB 二进制，后半段追加增量命令，兼顾了加载速度和持久化实时性。

##### 面试三句话总结

1. **AOF 重写不读旧 AOF 文件**，数据源是 fork 后的内存快照。
2. **主进程不阻塞**，新写命令通过 AOF 重写缓冲区在最后 append。
3. **磁盘只承担"写临时文件 + rename 替换"**，压缩逻辑本身是内存中的 CPU 工作。

### 2.9 混合持久化

Redis 4.0 引入混合持久化：AOF 文件前半部分使用 RDB 格式，后半部分追加 AOF 增量命令。

**优点：**
- RDB 部分恢复快。
- AOF 增量部分减少数据丢失。
- 兼顾恢复速度和数据安全。

### 2.10 RDB、AOF 对比

| 对比项 | RDB | AOF |
|--------|-----|-----|
| 本质 | 数据快照 | 写命令日志 |
| 文件大小 | 较小 | 较大 |
| 恢复速度 | 快 | 相对慢 |
| 数据安全 | 可能丢失较多数据 | 通常最多丢 1 秒 |
| 性能影响 | fork 有影响 | 持续追加和 fsync 有影响 |
| 适合场景 | 备份、灾备、快速恢复 | 数据安全要求较高 |

**面试建议：**

> 如果只做缓存，数据可从数据库恢复，RDB 就够用；如果 Redis 中有相对重要的数据，建议开启 AOF everysec；生产中也常用混合持久化，兼顾恢复速度和数据安全。

## 三、过期删除与内存淘汰

### 3.1 Redis 如何实现 Key 过期？

Redis 内部维护两个字典：

| 字典 | 作用 |
|------|------|
| 主字典 | 存储 Key 和 Value |
| 过期字典 | 存储 Key 和过期时间戳 |

当设置过期时间时，Redis 会把 Key 的过期时间记录在过期字典中。

### 3.2 过期删除策略

Redis 主要使用 **惰性删除 + 定期删除**。

#### 惰性删除

访问某个 Key 时，Redis 检查它是否过期。如果过期，就删除并返回不存在。

**优点：** 节省 CPU。

**缺点：** 如果 Key 一直不被访问，即使过期了也可能占用内存。

#### 定期删除

Redis 会周期性随机抽取一批设置了过期时间的 Key，检查并删除过期 Key。

**优点：** 主动清理过期 Key。

**缺点：** 不能保证所有过期 Key 立即删除。

### 3.3 为什么不用定时删除？

定时删除是指给每个 Key 都设置一个定时器，到期立即删除。

Redis 不主要使用定时删除，因为：
- 定时器数量巨大时内存成本高。
- 维护大量定时器会消耗 CPU。
- 过期删除太及时反而会影响 Redis 正常请求处理。

### 3.4 内存淘汰策略

当 Redis 内存达到 `maxmemory` 时，会根据配置的淘汰策略删除部分 Key。

| 策略 | 说明 |
|------|------|
| noeviction | 不淘汰，写入报错 |
| allkeys-lru | 从所有 Key 中淘汰最近最少使用 |
| volatile-lru | 从设置过期时间的 Key 中淘汰最近最少使用 |
| allkeys-random | 从所有 Key 中随机淘汰 |
| volatile-random | 从设置过期时间的 Key 中随机淘汰 |
| volatile-ttl | 优先淘汰 TTL 更短的 Key |
| allkeys-lfu | 从所有 Key 中淘汰最不常使用 |
| volatile-lfu | 从设置过期时间的 Key 中淘汰最不常使用 |

### 3.5 如何选择淘汰策略？

| 场景 | 推荐策略 |
|------|----------|
| Redis 纯缓存 | `allkeys-lru` 或 `allkeys-lfu` |
| 只有部分 Key 允许淘汰 | `volatile-lru` 或 `volatile-lfu` |
| 数据不能丢 | `noeviction` |
| 热点稳定 | `allkeys-lfu` |
| 热点变化快 | `allkeys-lru` |

### 3.6 LRU 与 LFU 区别

| 对比项 | LRU | LFU |
|--------|-----|-----|
| 判断依据 | 最近是否访问 | 访问频率 |
| 适合场景 | 热点变化快 | 热点较稳定 |
| 典型问题 | 偶发访问会污染缓存 | 新热点建立较慢 |

## 四、缓存经典问题

### 4.1 缓存穿透

**含义：** 查询一个缓存和数据库都不存在的数据，请求每次都会打到数据库。

**典型场景：** 恶意请求不存在的 ID，如 `user:-1`、`order:unknown`。

**解决方案：**
1. **缓存空值**：数据库查不到时缓存空对象，设置较短 TTL。
2. **布隆过滤器**：请求先经过布隆过滤器判断 Key 是否可能存在。
3. **参数校验**：拦截非法 ID、非法参数。
4. **接口限流**：避免恶意流量打穿数据库。

### 4.2 缓存击穿

**含义：** 某个热点 Key 过期瞬间，大量请求同时访问数据库。

**解决方案：**
1. 互斥锁重建缓存。
2. 逻辑过期。
3. 热点 Key 永不过期，配合主动更新。
4. 提前预热热点数据。

**互斥锁流程：**

```text
请求访问热点 Key
        │
        ▼
缓存未命中
        │
        ▼
尝试获取 Redis 锁
   ┌────┴────┐
   │成功      │失败
   ▼          ▼
查 DB       sleep 后重试缓存
重建缓存
释放锁
```

### 4.3 缓存雪崩

**含义：** 大量 Key 在同一时间过期，或者 Redis 整体不可用，导致请求集中打到数据库。

**解决方案：**
1. TTL 加随机值。
2. 热点数据逻辑过期或永不过期。
3. Redis 主从、哨兵、Cluster 保证高可用。
4. 本地缓存兜底。
5. 限流、熔断、降级。
6. 多级缓存架构。

### 4.4 缓存污染

**含义：** 大量低价值、低频数据进入缓存，占用内存，挤掉热点数据。

**解决方案：**
- 设置合理 TTL。
- 使用 LFU 淘汰策略。
- 大对象和低频对象不缓存。
- 缓存前增加访问频率判断。

### 4.5 缓存一致性问题

数据库和缓存双写时容易出现不一致。

| 策略 | 说明 | 问题 |
|------|------|------|
| 先更新 DB，再更新缓存 | DB 成功后写缓存 | 并发下旧值覆盖新值 |
| 先更新缓存，再更新 DB | 写缓存后写 DB | DB 失败导致缓存脏数据 |
| 先删除缓存，再更新 DB | 删除后写 DB | 并发读可能写回旧值 |
| 先更新 DB，再删除缓存 | 最常用 | 删除失败会短暂不一致 |

**推荐：先更新数据库，再删除缓存。**

### 4.6 删除缓存失败怎么办？

1. 删除失败后进行重试。
2. 删除失败消息写入 MQ。
3. 监听数据库 binlog，例如 Canal，异步删除缓存。
4. 设置 TTL 兜底，保证最终一致。

### 4.7 为什么不推荐更新缓存？

因为并发下可能旧值覆盖新值：

```text
线程 A 更新 DB 为 1，然后准备更新缓存
线程 B 更新 DB 为 2，并更新缓存为 2
线程 A 后更新缓存为 1
最终缓存是旧值
```

### 4.8 双删策略

双删策略通常指：

```text
删除缓存 -> 更新数据库 -> 延迟一段时间 -> 再次删除缓存
```

或者：

```text
更新数据库 -> 删除缓存 -> 延迟一段时间 -> 再次删除缓存
```

**目的：** 尽量删除并发读期间写回缓存的旧值。

**缺点：** 延迟时间不好确定，只能降低不一致概率，不能绝对保证一致。

## 五、Redis 分布式锁

### 5.1 分布式锁需要满足什么条件？

1. **互斥性**：同一时刻只有一个客户端持有锁。
2. **防死锁**：客户端崩溃后锁能自动释放。
3. **锁归属校验**：只能释放自己加的锁。
4. **可重入性**：同一线程可重复获取锁，视业务决定。
5. **高可用性**：Redis 节点故障时仍尽量可用。

### 5.2 正确加锁方式

```bash
SET lock:order:1001 requestId NX EX 30
```

含义：
- `NX`：Key 不存在才设置成功。
- `EX 30`：设置 30 秒过期时间。
- `requestId`：锁持有者唯一标识。

### 5.3 为什么不能用 SETNX + EXPIRE？

错误写法：

```bash
SETNX lock:order:1001 requestId
EXPIRE lock:order:1001 30
```

问题：如果 `SETNX` 成功后服务宕机，`EXPIRE` 没执行，锁会永久存在。

### 5.4 正确释放锁

释放锁必须判断锁是不是自己的，再删除。

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**为什么用 Lua？**
- `GET` 和 `DEL` 两步不是原子操作。
- Lua 脚本在 Redis 中会作为一个整体原子执行。

### 5.5 锁过期时间怎么设置？

锁过期时间应大于业务执行的最长时间，但不能过长。

如果业务执行时间不可控，可以使用 Redisson 的看门狗机制自动续期。

### 5.6 Redisson 分布式锁

Redisson 提供了更完善的分布式锁能力：

- 可重入锁
- 看门狗自动续期
- 公平锁
- 读写锁
- 信号量
- 闭锁
- RedLock

### 5.7 Redis 分布式锁有哪些坑？

- `SETNX` 和 `EXPIRE` 非原子导致死锁。
- 锁过期时间太短，业务没执行完锁就释放。
- 没有校验锁持有者，误删别人的锁。
- Redis 主从切换可能导致锁丢失。
- JVM STW 或 GC 停顿导致续期失败。

### 5.8 RedLock 是否一定可靠？

RedLock 是 Redis 官方提出的多节点分布式锁算法，但业界对其可靠性有争议。

**面试建议：**
- 普通业务互斥场景可以使用 Redis 锁。
- 强一致要求极高的场景，不建议只依赖 Redis 锁。
- 可以考虑数据库锁、ZooKeeper、etcd 等 CP 系统。

## 六、Redis 事务、Lua 与原子性

### 6.1 Redis 事务

Redis 事务通过 `MULTI`、`EXEC`、`DISCARD`、`WATCH` 实现。

```bash
MULTI
SET a 1
INCR b
EXEC
```

**特点：**
- 命令按顺序执行。
- 执行期间不会被其他客户端命令插入。
- 不支持传统数据库事务的自动回滚。

### 6.2 Redis 事务为什么不支持回滚？

Redis 认为命令错误通常是编程错误，应在开发阶段发现。

如果事务中某条命令运行时失败，其他命令仍然可能继续执行。

### 6.3 WATCH 乐观锁

`WATCH` 可以监听 Key，如果事务执行前 Key 被其他客户端修改，则事务失败。

```bash
WATCH stock:1001
GET stock:1001
MULTI
DECR stock:1001
EXEC
```

**适用场景：**
- 库存扣减
- CAS 更新
- 防并发覆盖

### 6.4 Lua 脚本

Lua 脚本可以把多个 Redis 命令组合成一个原子操作。

**典型场景：**
- 分布式锁释放
- 秒杀扣库存
- 限流
- 复杂缓存更新

扣库存示例：

```lua
local stock = tonumber(redis.call('get', KEYS[1]))
if stock == nil then
    return -1
end
if stock <= 0 then
    return 0
end
redis.call('decr', KEYS[1])
return 1
```

### 6.5 Lua 脚本注意事项

- 不要执行耗时逻辑，否则会阻塞 Redis。
- 脚本中访问的 Key 在 Cluster 模式下应位于同一个 Slot。
- Lua 脚本具备原子性，但不等于数据库事务。

## 七、高频面试题

### 7.1 Redis 为什么这么快？

基于内存、高效数据结构、单线程命令执行、IO 多路复用、协议简单、渐进式 rehash 等优化共同作用。

### 7.2 Redis 单线程为什么还能高并发？

Redis 的瓶颈通常不是 CPU，而是网络和内存。单线程避免锁竞争和线程切换，再结合 IO 多路复用，可以服务大量连接。

### 7.3 RDB 和 AOF 怎么选？

只做缓存可以使用 RDB；对数据安全要求更高建议开启 AOF everysec；生产中常用混合持久化。

### 7.4 缓存穿透、击穿、雪崩区别？

| 问题 | 含义 | 解决 |
|------|------|------|
| 穿透 | 查不存在的数据 | 空值缓存、布隆过滤器 |
| 击穿 | 热点 Key 过期 | 互斥锁、逻辑过期 |
| 雪崩 | 大量 Key 同时过期或 Redis 故障 | TTL 随机、高可用、限流降级 |

### 7.5 分布式锁如何安全释放？

使用 Lua 脚本先判断 Value 是否等于自己的唯一标识，匹配才删除，保证判断和删除原子执行。
