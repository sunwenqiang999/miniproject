# 操作系统性能优化与生产实战面试知识点

> 本文档聚焦操作系统在高并发系统中的性能优化技术与线上问题排查实战。基础知识看 [`操作系统面试知识点.md`](操作系统面试知识点.md)，底层原理看 [`操作系统原理机制面试知识点.md`](操作系统原理机制面试知识点.md)。

## 一、零拷贝（Zero Copy）

### 1.1 传统 IO 的问题：4 次拷贝 + 4 次上下文切换

以"读磁盘文件通过 Socket 发出去"（如文件下载、Kafka 发消息）为例，传统方式：

```text
read(file) + write(socket) 的完整过程：

磁盘 ──DMA拷贝①──► 内核缓冲区 ──CPU拷贝②──► 用户缓冲区
                                              │
Socket缓冲区 ◄──CPU拷贝③── 内核Socket缓冲区 ◄─┘（用户态）
   │
   └──DMA拷贝④──► 网卡
```

| 开销 | 次数 | 说明 |
|------|------|------|
| 数据拷贝 | 4 次 | 2 次 DMA + **2 次 CPU 拷贝（内核态↔用户态，纯浪费）** |
| 上下文切换 | 4 次 | read 调用陷入/返回 + write 调用陷入/返回 |

核心浪费：数据在内核空间和用户空间之间来回拷贝了两次，而用户程序**根本没有修改数据**。

### 1.2 三种零拷贝实现

#### 1.2.1 mmap + write

用 `mmap` 把文件映射到用户地址空间，用户缓冲区与内核缓冲区共享，省掉 read 时的那次 CPU 拷贝。

- 拷贝次数：3 次（DMA 读 + DMA 写 + 1 次 CPU 拷贝到 Socket 缓冲区）
- 上下文切换：仍是 4 次
- 应用：RocketMQ 的 MappedByteBuffer 消费消息

#### 1.2.2 sendfile（Linux 2.1+）

```c
sendfile(socket_fd, file_fd, offset, count);
```

一次系统调用，数据**全程在内核空间**从文件缓冲区直接拷到 Socket 缓冲区，不经过用户态。

- 拷贝次数：3 次（DMA 读 + CPU 内核内拷贝 1 次 + DMA 写）
- 上下文切换：**2 次**（一次系统调用的陷入与返回）
- 应用：Kafka 发送消息、Nginx 静态文件（`sendfile on;`）

#### 1.2.3 sendfile + DMA Scatter/Gather（Linux 2.4+，真·零拷贝）

网卡支持 SG-DMA 时，内核缓冲区的数据**连内核内的那次 CPU 拷贝都省掉**：只把数据的地址和长度描述符传给 Socket 缓冲区，DMA 控制器根据描述符直接从内核缓冲区收集数据发到网卡。

- 拷贝次数：**2 次**（只有 DMA 拷贝，CPU 完全不参与数据搬运）
- 上下文切换：2 次

### 1.3 零拷贝面试总结（必背模板）

> 传统文件传输需要 4 次数据拷贝和 4 次用户态/内核态切换，其中内核与用户空间之间的 2 次 CPU 拷贝是浪费。零拷贝的优化思路是减少拷贝次数和上下文切换次数：mmap 通过共享内核缓冲区省掉一次 CPU 拷贝；sendfile 让数据全程在内核空间流转，只需 2 次切换；配合 SG-DMA 网卡后可以做到 CPU 完全不参与数据拷贝。Kafka 用 sendfile 实现消息高效投递、Nginx 用 sendfile 发静态文件、RocketMQ 用 mmap 读写 CommitLog，都是零拷贝思想的工业级应用。

| 技术组件 | 使用的零拷贝技术 |
|----------|------------------|
| Kafka | sendfile（消费消息发数据） |
| Nginx | sendfile（`sendfile on` 指令） |
| RocketMQ | mmap（CommitLog/ConsumeQueue 读写） |
| Netty | CompositeByteBuf 合并 buffer、FileRegion 包装 sendfile |

## 二、epoll 生产实战

### 2.1 epoll 的三个系统调用

```c
int epfd = epoll_create(1024);                    // 创建 epoll 实例（内核建红黑树+就绪链表）
epoll_ctl(epfd, EPOLL_CTL_ADD, sockfd, &event);   // 注册/修改/删除监听的 fd 和事件
int n = epoll_wait(epfd, events, maxevents, timeout); // 阻塞等待就绪事件，只返回就绪的
```

核心编程要点：
- `epoll_ctl` 注册一次即可，不要每次循环都重新注册。
- 监听的 Socket 必须设为**非阻塞**，否则一个连接的处理会卡住整个事件循环。
- ET 模式下必须循环 `read` 直到返回 `EAGAIN`，否则会丢事件。

### 2.2 单机百万连接的瓶颈在哪？

面试常见追问：一台机器能撑多少 TCP 连接？

| 瓶颈 | 说明 | 调优方向 |
|------|------|----------|
| 文件描述符上限 | 默认 1024 | `ulimit -n` 调到百万级；内核 `fs.file-max`、`fs.nr_open` |
| 端口范围 | 客户端才有 65535 端口限制；**服务端 listen 一个端口可接无限连接** | 服务端不受限；客户端调 `net.ipv4.ip_local_port_range` |
| 内存 | 每个连接有读写缓冲区（几 KB ~ 几十 KB） | 调小 `net.ipv4.tcp_rmem/wmem`；百万连接需要数 GB 内存 |
| TIME_WAIT 堆积 | 主动关闭方进入 TIME_WAIT（60s），占用端口/fd | 让客户端主动关闭；`tcp_tw_reuse`；**不要**乱开 `tcp_tw_recycle`（NAT 环境会出问题） |

> 高频误区澄清：**"一台机器最多 65535 个连接"是错的**。TCP 连接由四元组（源IP、源端口、目标IP、目标端口）唯一标识，服务端监听一个端口，可以接收来自无数"不同源IP+源端口"组合的连接，上限只受 fd 数量和内存限制。

### 2.3 Reactor 线程模型（Netty/Nginx/Redis 的骨架）

基于 IO 多路复用的高并发服务器基本都是 Reactor 模型的变体：

| 模型 | 结构 | 特点 | 代表 |
|------|------|------|------|
| 单 Reactor 单线程 | 一个线程处理连接、读写、业务 | 简单，业务耗时阻塞全局 | Redis 6.0 之前 |
| 单 Reactor 多线程 | Reactor 管连接和 IO，业务丢线程池 | 业务不阻塞 IO | 早期 Netty 用法 |
| **主从 Reactor 多线程** | MainReactor 只管 accept，SubReactor 池管 IO 读写 | accept 与 IO 分离，多核利用 | **Netty（boss/worker 线程组）、Nginx** |

```text
                        ┌──────────────┐
        新连接 ────────► │ MainReactor  │ (accept，1个线程)
                        └──────┬───────┘
                               │ 分发
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
        ┌───────────┐   ┌───────────┐    ┌───────────┐
        │SubReactor │   │SubReactor │    │SubReactor │  (epoll 读写，N个线程)
        └─────┬─────┘   └─────┬─────┘    └─────┬─────┘
              └───────────────┼────────────────┘
                              ▼
                        业务线程池（可选）
```

**面试联想：** Netty 的 `bossGroup`（accept）+ `workerGroup`（IO 读写）就是主从 Reactor；Nginx 的 master + 多 worker 进程每个 worker 一个 epoll 也是同样思想。

### 2.4 惊群效应

**现象：** 多个进程/线程同时阻塞在 `accept`（或 `epoll_wait`）上，一个新连接到来时**所有等待者都被唤醒**，但最终只有一个能 accept 成功，其余白跑一趟，浪费 CPU。

**解决：**
- Linux 4.5+ 内核：`epoll` + `SO_REUSEPORT`，内核层面做连接负载均衡，每个进程独立的 Socket 队列，天然避免惊群（Nginx 1.9.1+ 支持）。
- Nginx 传统方案：`accept_mutex` 互斥锁，同一时刻只有一个 worker 抢 accept 资格。

## 三、CPU 相关生产实战

> 详细排查 SOP 见 [`../场景题/CPU飙高场景题排查思路.md`](../场景题/CPU飙高场景题排查思路.md)，这里讲面试问答套路。

### 3.1 CPU 飙高排查四板斧（必背）

```text
① top                  -> 找到 CPU 高的进程 PID
② top -Hp <pid>        -> 找到进程内 CPU 高的线程 TID
③ printf "%x\n" <tid>  -> 把线程 ID 转成 16 进制（jstack 里线程号是 16 进制）
④ jstack <pid> | grep <16进制tid> -A 30 -> 定位到具体代码堆栈
```

**常见根因分类（面试要会分类讨论）：**

| 现象 | 可能原因 | 验证方式 |
|------|----------|----------|
| us 高（用户态 CPU） | 业务死循环、正则灾难回溯、频繁序列化、大对象计算 | jstack 看业务堆栈 |
| sy 高（内核态 CPU） | 频繁系统调用、上下文切换过多、IO 密集 | `vmstat` 看 cs 列；`strace -c` 统计系统调用 |
| CPU 不高但 load 高 | 大量线程 D 状态（不可中断睡眠，多在等磁盘 IO） | `ps aux | grep " D "`；`iostat` |
| GC 线程 CPU 高 | Full GC 频繁、堆太小、内存泄漏导致疯狂 GC | `jstat -gcutil` 看 GC 频率和耗时 |

### 3.2 CPU 使用率和 Load 的关系（高频）

- **CPU 使用率**：CPU 忙碌时间占比（us 用户态 + sy 内核态 + ...）。
- **Load Average**：处于**运行态 + 不可中断睡眠态（D 状态）** 的平均任务数。

**结论：**
- Load 高 + CPU 高：任务太多 CPU 真忙不过来（或线程池开太大）。
- **Load 高 + CPU 低**：大量任务卡在 D 状态等 IO（磁盘/网络存储故障常见），CPU 其实在摸鱼。
- 经验值：Load / CPU 核数 < 1 健康；持续 > 2 需要关注。

### 3.3 上下文切换过多的排查与优化

```bash
vmstat 1        # cs 列 > 10万/s 就要警惕
pidstat -w 1    # cswch/s（自愿切换，等资源） nvcswch/s（非自愿，被抢占）
```

**常见原因：**
- 线程池开得太大（如几百上千个线程）。
- 锁竞争激烈，大量线程挂起/唤醒。
- 频繁的系统调用、IO。

**优化方向：** 按 `CPU 核数 × (1 + IO等待时间/计算时间)` 估算线程池；计算密集型任务线程数 ≈ 核数；减少锁粒度、用无锁结构。

## 四、内存相关生产实战

> 详细排查 SOP 见 [`../场景题/内存飙升场景题排查思路.md`](../场景题/内存飙升场景题排查思路.md)。

### 4.1 free 命令怎么看？（高频细节题）

```bash
$ free -h
              total    used    free    shared   buff/cache   available
Mem:           15G     6.0G    1.2G    500M        8.1G        8.5G
Swap:           0G      0G      0G
```

| 列 | 含义 |
|----|------|
| free | 完全空闲的内存 |
| buff/cache | PageCache + 块缓存，**可回收**，不是真被占用 |
| **available** | **真正可用的内存**（free + 可回收的 cache），看内存够不够看这列 |

> 面试陷阱：`free` 只剩 1G 不代表内存不够，Linux 会积极拿空闲内存做 PageCache，看 `available` 才准。

### 4.2 OOM 与 OOM Killer

Linux 默认开启**内存超发（Overcommit）**：malloc 可以先成功，实际物理内存不足时才出问题。当物理内存 + Swap 都耗尽时，内核触发 **OOM Killer**，按 `oom_score` 打分（内存占用越大、运行时间越短分越高）**杀死得分最高的进程**释放内存。

**排查与防护：**
```bash
dmesg | grep -i "killed process"   # 查 OOM Killer 杀人记录
cat /proc/<pid>/oom_score          # 查看某进程的 OOM 分数
echo -1000 > /proc/<pid>/oom_score_adj  # 保护关键进程（如 sshd）不被杀
```

**Java 服务特别注意：** 容器环境 JVM 若不感知 cgroup 内存限制（JDK8u191 之前默认不感知），堆可能按物理机内存算，导致**进程没 OOM 异常却被 cgroup/内核 OOM Killer 直接杀死**。生产上要用 `-XX:+UseContainerSupport`（新版本默认开启）并显式设置 `-Xmx` 和 `-XX:MaxRAMPercentage`。

**区分两种 OOM（面试必考）：**

| 类型 | 表现 | 本质 |
|------|------|------|
| JVM OOM | 抛 `java.lang.OutOfMemoryError`，进程可能还活着 | 堆/元空间不够，GC 无法回收 |
| Linux OOM Killer | 进程**直接消失**（kill -9 效果），无任何 Java 异常 | 物理内存耗尽，内核杀进程 |

### 4.3 Swap 的坑

Swap 把不活跃内存页换到磁盘，看似扩大了内存，但对延迟敏感的服务是灾难（磁盘 IO 比内存慢 4~5 个数量级）。

**生产实践：**
- Redis、Kafka、ES 等对延迟敏感的组件建议**关闭 Swap** 或 `vm.swappiness=1`（尽量不 swap）。
- MySQL、离线任务可以保留 Swap 作为缓冲。

### 4.4 堆外内存泄漏排查

Java 服务内存持续上涨但 `jmap` 看堆很正常 → 大概率**堆外内存泄漏**（Netty DirectByteBuffer、JNI、线程栈、metaspace）。

**排查三板斧：**
1. `-XX:NativeMemoryTracking=summary` + `jcmd <pid> VM.native_memory` 看 JVM 各区域占用。
2. Netty 场景：`-Dio.netty.leakDetectionLevel=advanced` 开泄漏检测。
3. `pmap -x <pid>` 找可疑的大块匿名内存段。

## 五、磁盘 IO 生产实战

### 5.1 磁盘 IO 高排查套路

```bash
iostat -x 1
# 重点看：
# %util  -> 磁盘繁忙度，持续接近 100% 说明磁盘是瓶颈
# await  -> 平均 IO 响应时间（ms），SSD 应 < 1ms，机械盘 < 10ms
# r/s w/s、rkB/s wkB/s -> IOPS 和吞吐量
```

定位到具体进程：

```bash
iotop -oP      # 只看正在做 IO 的进程
pidstat -d 1   # 按进程看 IO
```

**常见根因：**
- 日志狂刷（log4j 异步 Appender 也扛不住 DEBUG 级别海量输出）。
- 数据库慢查询导致大量磁盘扫描。
- 定期任务（备份、批处理）和业务争抢 IO。
- PageCache 刷盘风暴（大量脏页集中回写）。

### 5.2 磁盘满了的两种伪装（高频）

| 现象 | 真相 | 命令验证 |
|------|------|----------|
| `df` 显示磁盘没满，写入却报 No space left | **inode 耗尽**（海量小文件） | `df -i` |
| 删了大文件，磁盘空间没释放 | 文件仍被进程打开（fd 引用），inode 引用计数 > 0 | `lsof | grep deleted`，重启进程或清空文件 `: > file` 代替 rm |

## 七、生产实战高频问题速记

| 问题 | 一句话答案 |
|------|------------|
| 什么是零拷贝 | 数据不经过用户态、CPU 少参与拷贝的技术；Kafka sendfile、RocketMQ mmap |
| 传统 IO 几次拷贝 | 4 次拷贝 + 4 次上下文切换，2 次 CPU 拷贝是浪费 |
| epoll 在百万连接下表现 | O(1) 返回就绪事件，性能几乎不衰减 |
| 单机最大 TCP 连接数 | 不是 65535，受 fd 上限和内存限制，可到百万级 |
| TIME_WAIT 过多怎么办 | 客户端主动关闭、tcp_tw_reuse、连接池复用 |
| Reactor 模型 | 主从 Reactor：main 管 accept，sub 管 IO；Netty boss/worker |
| 惊群效应 | 多等待者被同时唤醒只有一个成功；SO_REUSEPORT 解决 |
| Load 高 CPU 低 | 大量 D 状态线程在等 IO，查磁盘 |
| free 内存很少是 OOM 前兆吗 | 不是，看 available，Linux 会拿空闲内存做 PageCache |
| 进程突然消失没日志 | 先 `dmesg` 查 OOM Killer，区分 JVM OOM 和内核 OOM |
| 删了文件空间没释放 | 进程还持有 fd，`lsof | grep deleted`，重启进程 |
| 磁盘报满但 df 有空间 | inode 耗尽，`df -i` 确认 |

## 八、与组件实战的联动（面试加分项）

把 OS 原理和业务组件串起来回答，是区分"背八股"和"真理解"的关键：

| 组件 | 用到的 OS 机制 | 联动文档 |
|------|----------------|----------|
| Kafka 高吞吐 | PageCache 顺序写 + sendfile 零拷贝 + 批量 | [`../消息队列/kafka面试知识点.md`](../消息队列/kafka面试知识点.md) |
| RocketMQ | mmap（MappedByteBuffer）+ 异步刷盘 | [`../消息队列/rocketmq面试知识点.md`](../消息队列/rocketmq面试知识点.md) |
| Redis 单线程快 | 内存操作 + epoll + 无锁；BGSAVE 依赖 COW | [`../redis/redis原理机制面试知识点.md`](../redis/redis原理机制面试知识点.md) |
| Nginx 高并发 | 多进程 + epoll + sendfile + SO_REUSEPORT | 本文第二、三章 |
| Netty | 主从 Reactor + epoll + 堆外内存（DirectBuffer 绕开 JVM 堆） | 本文第二、四章 |
| Docker 资源隔离 | namespace（隔离）+ cgroup（限 CPU/内存） | [`../docker/docker原理机制面试知识点.md`](../docker/docker原理机制面试知识点.md) |
| JVM | 虚拟内存、缺页、大页内存、cgroup 感知 | 本文第四章 |

**面试话术示例（被问"为什么 Kafka 快"时把 OS 讲进去）：**

> Kafka 的高吞吐离不开对操作系统特性的利用：写消息时先写 PageCache 由内核异步刷盘，把随机 IO 变顺序 IO；消费时用 sendfile 零拷贝，数据从 PageCache 直接进 Socket 不经过用户态，CPU 不参与数据搬运；再叠加分区内顺序读写和批量压缩，所以单机就能跑到几十万 TPS。这些优化的共同思想就是：减少系统调用、减少数据拷贝、让磁盘做它最擅长的顺序 IO。
