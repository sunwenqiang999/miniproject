## 一、Linux 内核架构

### 1.1 内核体系结构

Linux 采用**宏内核（Monolithic Kernel）**架构，进程管理、内存管理、文件系统、设备驱动、网络协议栈全部运行在内核态，通过函数调用直接通信，性能高。

```text
┌─────────────────────────────────────────────┐
│                用户态应用程序                 │  Ring 3
├─────────────────────────────────────────────┤
│   C 库（glibc）：封装系统调用、提供 printf 等  │
├─────────────  系统调用接口（SCI）  ───────────┤  ← 用户态/内核态分界线
│  ┌─────────┬─────────┬─────────┬─────────┐  │
│  │ 进程管理 │ 内存管理 │  VFS    │网络协议栈│  │
│  ├─────────┼─────────┼─────────┼─────────┤  │  Ring 0
│  │         设备驱动、中断处理              │  │
│  ├────────────────────────────────────────┤  │
│  │      体系结构相关代码（x86/ARM）         │  │
│  └────────────────────────────────────────┘  │
├─────────────────────────────────────────────┤
│                  硬件（CPU/内存/磁盘/网卡）     │
└─────────────────────────────────────────────┘
```

**宏内核 vs 微内核：**

| 对比项 | 宏内核（Linux） | 微内核（Minix、鸿蒙） |
|--------|-----------------|----------------------|
| 服务位置 | 全部在内核态 | 只有最小功能在内核态，文件系统等在用户态 |
| 通信方式 | 函数调用 | IPC 消息传递 |
| 性能 | 高 | 相对低 |
| 稳定性 | 一个驱动崩溃可能拖垮内核 | 服务隔离，单个崩溃不影响全局 |
| 代表 | Linux、Unix | QNX、Minix |

### 1.2 系统调用的执行过程（高频）

以 `read()` 为例，一次系统调用的完整过程：

```text
用户态                                          内核态
  │                                                │
  │  1. 调用 read()（glibc 封装）                   │
  │  2. 参数放入寄存器（rdi, rsi, rdx）             │
  │     系统调用号放入 rax（read=0）                │
  │  3. 执行 syscall 指令（老内核是 int 0x80） ─────►│  4. CPU 切到内核态
  │                                                │     保存用户态现场（寄存器、栈指针）
  │                                                │  5. 查系统调用表 sys_call_table
  │                                                │     找到 sys_read 执行
  │                                                │  6. 内核完成磁盘/缓存读取
  │  8. 从返回值寄存器 rax 取结果 ◄─────────────────│  7. 恢复用户态现场，切回用户态
  ▼                                                ▼
```

**关键点：**

- 系统调用是用户态进入内核态的**唯一合法入口**，本质是 CPU 软中断/特殊指令（`syscall`）。
- 一次上下文切换的开销：保存/恢复寄存器、刷新 TLB 部分缓存、可能的 CPU cache 污染，大约几百纳秒到几微秒。
- `strace -c command` 可以统计一个程序的系统调用次数和耗时，是性能分析利器。

**面试回答：**

> 系统调用是用户程序请求内核服务的接口。以 read 为例：glibc 把参数和系统调用号放入指定寄存器，执行 syscall 指令触发软中断，CPU 从用户态切换到内核态并保存现场，内核通过系统调用表找到对应的 sys_read 执行，完成后恢复现场切回用户态。整个过程涉及两次特权级切换和寄存器保存恢复，有一定开销，所以像日志批量写、内存映射文件 mmap 这些技术都在想办法减少系统调用次数。

### 1.3 硬中断与软中断（高频）

| 对比项 | 硬中断 | 软中断（softirq） |
|--------|--------|-------------------|
| 触发者 | 硬件设备（网卡、磁盘、时钟） | 内核自己（软中断守护线程） |
| 优先级 | 高，可打断一切 | 低，可被硬中断打断 |
| 执行内容 | 只做最紧急的事（如从网卡取数据） | 耗时工作（协议栈处理、数据拷贝） |
| 查看 | /proc/interrupts | /proc/softirqs |
| 典型类型 | 网卡收包中断、时钟中断 | NET_RX、NET_TX、TIMER、TASKLET |

**两阶段设计的原因：**

> 网卡收到数据包触发硬中断，硬中断处理函数必须极快返回，否则后续中断会丢失。所以硬中断只把数据从网卡取到内存，然后**触发软中断**立即返回；真正的协议栈解析（IP、TCP 处理）放在软中断里慢慢做。这就是"上半部（top half）快处理、下半部（bottom half）慢处理"的设计思想。

**生产关联：** `top` 中 `%si`（softirq）高通常意味着网络流量大或中断频繁，`/proc/softirqs` 中 NET_RX 增长快可确认。

## 二、文件系统原理

### 2.1 VFS 虚拟文件系统

VFS（Virtual File System）是内核的抽象层，向上提供统一的 `open/read/write` 接口，向下屏蔽 ext4、xfs、NFS、proc、tmpfs 等具体文件系统的差异。

```text
应用程序：open("/data/a.txt")        open("/proc/cpuinfo")
              │                            │
              ▼                            ▼
        ┌─────────────────────────────────────┐
        │            VFS 统一接口层             │   系统调用表
        ├─────────────────────────────────────┤
        │  ext4    xfs    nfs   proc   tmpfs  │   具体文件系统
        ├─────────────────────────────────────┤
        │  Page Cache（页缓存）                │   缓存层
        ├─────────────────────────────────────┤
        │  块设备层 / 驱动 / 磁盘               │   硬件层
        └─────────────────────────────────────┘
```

**VFS 四大核心对象：**

| 对象 | 含义 | 作用 |
|------|------|------|
| super_block | 超级块 | 记录文件系统整体信息（块大小、inode 总数），挂载时载入 |
| inode | 索引节点 | 记录文件元数据（大小、权限、时间、数据块指针），**不含文件名** |
| dentry | 目录项 | 记录文件名到 inode 的映射，构成目录树缓存（dcache） |
| file | 打开的文件 | 进程打开文件时创建，记录读写偏移量、f_flags |

### 2.2 inode（必考）

inode（索引节点）是文件系统为每个文件分配的元数据结构，存储**除文件名以外**的所有信息：

- 文件类型、权限（rwx）、属主属组
- 文件大小、时间戳（atime 访问、mtime 内容修改、ctime 元数据修改）
- **指向数据块的指针**（直接指针 + 一/二/三级间接指针）
- 硬链接计数（link count）

```bash
ls -i file.txt             # 查看文件的 inode 号
stat file.txt              # 查看完整 inode 信息（大小、权限、三个时间、链接数）
df -i                      # 查看各分区 inode 使用情况（inode 耗尽也会无法创建文件！）
```

**关键理解：**

1. **文件名不存在 inode 里**，存在目录文件的内容中。目录也是一个文件，其内容就是"文件名 → inode 号"的映射表。
2. `rm` 删除文件实际是删除目录中的映射项并让 inode 的硬链接计数减 1，计数为 0 且无进程打开时才真正释放数据块。
3. `mv` 在同一文件系统内只改目录映射，不动数据块，所以瞬间完成。
4. 每个文件系统的 inode 总数在格式化时固定，**小文件太多会导致磁盘空间没用完但 inode 耗尽**（`df -h` 有空间却无法创建文件，用 `df -i` 排查）。

**面试回答：**

> inode 是文件系统存储文件元数据的结构，包含权限、属主、大小、时间戳和数据块指针，但不包含文件名。文件名存放在目录文件的内容里，是"文件名到 inode 号"的映射。这种设计让硬链接成为可能——多个文件名指向同一个 inode。inode 数量在格式化时固定，所以小文件过多会造成磁盘有空间但 inode 耗尽，排查用 `df -i`。

### 2.3 硬链接与软链接（必考）

| 对比项 | 硬链接（hard link） | 软链接/符号链接（soft/symbolic link） |
|--------|---------------------|----------------------------------------|
| 本质 | 同一个 inode 的多个文件名 | 一个独立文件，内容是目标路径字符串 |
| inode 号 | 与源文件**相同** | **不同**（有自己的 inode） |
| 跨文件系统 | 不支持 | 支持 |
| 链接目录 | 不允许（普通用户） | 允许 |
| 源文件删除后 | 仍可通过链接访问（数据块还在） | 链接失效（ dangling link，变红闪烁） |
| 创建命令 | `ln source link` | `ln -s source link` |
| ls -l 标识 | 无特殊标识，硬链接数 +1 | 第一个字符 `l`，显示 `link -> source` |

```bash
ln /data/app.conf /data/app.conf.hard      # 硬链接
ln -s /data/app.conf /data/app.conf.soft   # 软链接
ls -li /data/app.conf*                     # 观察 inode 号是否相同
```

**一句话总结：**

> 硬链接是同一个 inode 的别名，删源文件数据不丢；软链接是存了目标路径的快捷方式，源文件删了就失效。判断依据看 inode 号是否相同。

### 2.4 ext4 文件系统布局

```text
磁盘分区
┌──────────┬──────────┬──────────┬──────────┐
│ 引导块    │ 块组 0   │ 块组 1   │  块组 ... │
└──────────┴────┬─────┴──────────┴──────────┘
                ▼
   ┌───────────────────────────────────────────┐
   │ 超级块 │ 块组描述符 │ 数据块位图 │ inode位图 │ inode表 │ 数据块区 │
   └───────────────────────────────────────────┘
```

- **超级块**：文件系统全局信息（总块数、inode 数、块大小），有多份备份防止损坏。
- **块位图 / inode 位图**：用 bit 位标记数据块 / inode 是否空闲。
- **inode 表**：连续的 inode 结构数组。
- **数据块区**：实际存放文件内容，默认块大小 4KB。

**ext4 关键特性：**

- **日志（Journaling）**：元数据先写日志再写实际位置，断电后可快速恢复，避免 fsck 全量扫描。
- **Extent（区段）**：用连续块区间代替 ext3 的逐个块指针，大文件效率高、碎片少。
- **延迟分配**：数据先在 Page Cache 攒着，真正落盘时才分配块，便于分配连续空间。

### 2.5 经典问题：文件删除后空间不释放（必考）

**现象：** `df -h` 显示磁盘满，但 `du -sh` 找不到大文件，或已经 `rm` 了大日志文件空间却不释放。

**原因：** 文件被某个进程打开着（持有文件描述符），`rm` 只删除了目录中的文件名映射，inode 引用计数和进程引用不为 0，内核不会真正释放数据块。

**排查与解决：**

```bash
# 1. 找出已删除但仍被进程占用的文件
lsof | grep deleted
# 2. 重启对应进程释放句柄，或对 nginx 等服务执行 reload
# 3. 紧急情况下可直接清空文件内容（进程还持有句柄，但数据块立即释放）
> /data/logs/app.log
```

**面试回答：**

> Linux 中删除文件只是移除目录里的文件名映射，只有当硬链接计数为 0 且没有进程持有文件描述符时，内核才真正释放数据块。如果一个大日志被进程打开着，rm 之后空间不会释放。用 `lsof | grep deleted` 能找出这类文件，解决方式是重启进程或直接用重定向清空文件。生产上规范做法是用 logrotate 的 copytruncate 模式切割日志而不是直接删除。

### 2.6 Page Cache 与读写流程（高频）

Linux 把空闲内存用作磁盘文件的缓存，大幅加速文件读写。

**读流程：**

```text
应用 read()
   │
   ▼
Page Cache 有数据？ ──命中──► 直接拷贝到用户态缓冲区（无磁盘 IO）
   │未命中
   ▼
发起磁盘 IO 读入 Page Cache，再拷贝给用户态
```

**写流程：**

```text
应用 write()
   │
   ▼
数据写入 Page Cache 对应的页，标记为脏页（dirty），write 立即返回
   │
   ▼（后台异步刷盘）
flusher 内核线程按策略把脏页写回磁盘
（vm.dirty_ratio、vm.dirty_background_ratio 控制阈值）
```

**关键点：**

- `free -h` 中 `buff/cache` 列就是 Page Cache，**它是可回收的**，应用需要内存时内核会释放，所以看可用内存要看 `available` 列而不是 `free` 列。
- `fsync()` / `fdatasync()` 强制把脏页刷到磁盘，MySQL、Redis 持久化都依赖它保证数据不丢。
- `O_DIRECT` 标志可绕过 Page Cache 直写磁盘，数据库常用（MySQL InnoDB）避免双缓冲。

## 三、进程管理原理

### 3.1 fork 与写时复制 COW（高频）

`fork()` 创建子进程的传统做法是完整复制父进程地址空间，代价极高。Linux 使用**写时复制（Copy-On-Write）**优化：

```text
fork 后：
父进程 ──┐
         ├──► 同一份物理内存页（全部标记为只读）
子进程 ──┘

任何一方写入时：
触发缺页异常 → 内核复制被写的这一页 → 双方各自拥有独立副本
```

**要点：**

- fork 本身只复制页表项（把页标记为只读共享），不复制物理内存，速度极快。
- 子进程紧接着 `exec()` 加载新程序时，原共享页面直接丢弃，几乎零浪费。
- **生产关联：** Redis RDB 持久化用 fork 子进程做快照，靠 COW 保证 fork 瞬间完成；但如果父进程在 fork 期间大量写内存，会触发大量页复制，内存可能翻倍——这就是 Redis 大内存实例 fork 风险和 `overcommit_memory` 参数的由来。

### 3.2 Linux 进程调度：CFS 完全公平调度器

Linux 对普通进程（`SCHED_OTHER`）使用 CFS（Completely Fair Scheduler）调度器。

**核心思想：**

- 不再使用固定时间片，而是给每个进程维护**虚拟运行时间 vruntime**（实际运行时间 × 权重系数）。
- 每次调度选择 **vruntime 最小**的进程运行，即"谁跑得少就让谁跑"。
- 用**红黑树**组织所有可运行进程，最左节点就是 vruntime 最小的进程，选进程 O(1)。
- 优先级通过 nice 值（-20 ~ 19）映射为权重，nice 越小权重越大，vruntime 增长越慢，获得 CPU 越多。

**调度类别：**

| 调度策略 | 适用 | 特点 |
|----------|------|------|
| SCHED_OTHER（NORMAL） | 普通进程 | CFS，默认 |
| SCHED_FIFO | 实时进程 | 先进先出，高优先级一直占 CPU |
| SCHED_RR | 实时进程 | 时间片轮转 |
| SCHED_BATCH / IDLE | 批处理 / 空闲任务 | 让位于交互式进程 |

**CFS 调度延迟：** 保证每个进程在 `sched_latency`（默认 6ms 左右）内至少运行一次。

### 3.3 上下文切换（高频）

**什么是上下文切换：** CPU 从一个进程/线程切换到另一个时，保存当前任务的寄存器、程序计数器、栈指针等现场，恢复目标任务的现场。

**三种触发场景：**

1. **进程上下文切换**：时间片用完、等待 IO、被高优先级抢占。开销最大，可能涉及地址空间切换（刷新 TLB）。
2. **线程上下文切换**：同进程线程切换共享地址空间，不用刷 TLB，开销小。
3. **中断上下文切换**：硬件中断打断当前进程，只保存必要寄存器，开销最小。

**查看与排查：**

```bash
vmstat 1          # cs 列：每秒上下文切换次数
pidstat -w 1      # cswch/s 自愿切换（等 IO），nvcswch/s 非自愿切换（被抢占）
```

**经验值：** 单核每秒上下文切换几千到一两万正常；如果 cs 数十万且 us（用户态 CPU）低、sy 高，说明线程过多或锁竞争激烈。

### 3.4 Linux 线程的实现（NPTL）

Linux 内核**没有真正的线程概念**，线程是用进程实现的：

- 内核调度单位是 **task**（task_struct），线程是共享地址空间、文件描述符表、信号处理的特殊 task。
- `pthread_create()` 底层调用 `clone()` 系统调用，通过 `CLONE_VM | CLONE_FILES | CLONE_SIGHAND` 等标志指定资源共享范围。
- 每个线程在用户态有独立栈，内核态有独立的 task_struct 和内核栈，都会被调度器独立调度。
- `getpid()` 返回线程组 ID（TGID，即主线程 PID），`ps -eLf`、`top -H` 可看到每个线程（LWP = Light Weight Process）。

```bash
top -H -p <pid>          # 查看进程内每个线程的 CPU 占用（排查 Java 线程飙高神器）
ps -eLf | grep java      # 列出线程
```

**面试回答：**

> Linux 用 clone 系统调用创建线程，通过标志位让子 task 共享父进程的地址空间、文件表和信号处理，内核调度器看到的都是 task_struct，所以线程被称为轻量级进程 LWP。一个进程的 PID 实际是线程组 ID，进程内每个线程有独立的 LWP ID，可用 `top -H` 查看。Java 的线程与 Linux 线程是 1:1 映射的 NPTL 模型，所以 Java 线程飙高可以直接在操作系统层用 top -H 定位。

### 3.5 僵尸进程与孤儿进程（必考）

**为什么子进程退出后会变僵尸：** 子进程调用 `exit()` 终止时，内核会释放其内存、文件描述符等几乎所有资源，但**保留进程表项（task_struct）中的退出状态码、运行时间、资源统计**等少量信息。保留的目的是让父进程能通过 `wait()`/`waitpid()` 读取子进程的死因。这段"子进程已死、父进程尚未收尸"的中间状态就是僵尸状态（`Z` / `defunct`）。

| 概念 | 产生原因 | 危害 | 处理 |
|------|----------|------|------|
| 僵尸进程（Zombie，状态 Z） | 子进程退出，父进程没有 wait()/waitpid() 回收其退出状态 | 占用 PID 和进程表项，大量僵尸会耗尽 PID 导致无法创建新进程 | kill 不掉（已死），只能 kill 其父进程让 init/systemd 接管回收 |
| 孤儿进程（Orphan） | 父进程先于子进程退出 | 无危害，被 init/systemd（PID 1）收养，退出时由其回收 | 无需处理 |

**僵尸进程产生的典型场景：**

| 场景 | 说明 |
|------|------|
| 父进程未处理 SIGCHLD | 子进程退出时内核给父进程发 SIGCHLD，父进程没注册处理函数也不主动 wait，子进程变僵尸 |
| 父进程死循环 / 阻塞 | 父进程忙于其他逻辑（如 while(1)、阻塞在 IO），永远没机会调用 wait |
| 代码缺陷 | 只 fork 创建子进程，压根没写回收逻辑 |

```c
// 典型产生僵尸的代码：父进程 fork 后不 wait
pid_t pid = fork();
if (pid == 0) {
    exit(0);          // 子进程立即退出 → 变成僵尸
} else {
    while(1);         // 父进程死循环，永远不 wait
}
```

**正确的回收方式（编程层面预防）：**

1. **捕获 SIGCHLD 及时回收**：信号处理函数中循环调用 `waitpid(-1, &status, WNOHANG)`。必须循环，因为多个子进程同时退出时 SIGCHLD 会合并，只 wait 一次会漏回收。
2. **显式忽略**：`signal(SIGCHLD, SIG_IGN)`，告诉内核自动回收退出的子进程（Linux 特有行为，标准 POSIX 未规定，可移植性差）。
3. **两次 fork 技巧**：父进程 fork 出子进程，子进程再 fork 出孙子进程后立即退出，孙子进程成为孤儿被 PID 1 收养，彻底避免僵尸（守护进程 daemonize 常用）。

**排查与处理：**

```bash
ps aux | awk '$8 ~ /Z/ {print}'       # 找出僵尸进程
ps -ef | grep defunct                  # 另一种找法
ps -o ppid= -p <僵尸PID>               # 找其父进程，然后处理父进程
cat /proc/sys/kernel/pid_max           # 查看 PID 上限（默认 32768/4194304）
```

**面试回答：**

> 子进程退出时会变成僵尸，保留退出状态等父进程通过 wait 系统调用读取。如果父进程不 wait 也不退出，僵尸就一直残留占用进程表项。僵尸进程 kill -9 也杀不掉，因为它已经死了，正确做法是杀掉它的父进程，让 PID 1 收养并回收。所以写多进程程序时必须处理 SIGCHLD 信号及时 wait，注意要在信号处理函数里循环调用 waitpid，因为多个子进程同时退出时信号会合并，只 wait 一次会漏。

## 四、内存管理原理

### 4.1 虚拟内存与地址空间

每个进程拥有独立的虚拟地址空间（64 位系统理论 2^64，x86_64 实际用 48 位），内核通过**页表**把虚拟地址映射到物理地址，CPU 中的 **MMU** 硬件完成转换，**TLB** 缓存最近转换结果加速。

```text
进程虚拟地址空间布局（从低到高）：
┌──────────────────┐ 低地址
│   代码段（text）   │  程序指令
├──────────────────┤
│   数据段（data）   │  已初始化全局变量
├──────────────────┤
│   BSS 段          │  未初始化全局变量
├──────────────────┤
│   堆（heap）       │  malloc 分配，向上增长（brk）
├──────────────────┤
│   内存映射区        │  mmap、共享库（如 libc.so）
├──────────────────┤
│   栈（stack）      │  局部变量、函数调用，向下增长
├──────────────────┤
│   内核空间         │  每个进程都映射同一份内核（用户态不可访问）
└──────────────────┘ 高地址
```

**虚拟内存的好处：**

1. **隔离**：进程互相看不到对方内存，一个崩溃不影响其他。
2. **超发**：总虚拟内存可超过物理内存，配合 Swap 换出不常用页。
3. **按需分配**：malloc 只分配虚拟地址，首次访问触发缺页中断才分配物理页。
4. **共享**：共享库（libc）在所有进程间共享同一份物理页；fork 的 COW 也基于此。

### 4.2 缺页中断（Page Fault）

CPU 访问的虚拟页不在物理内存时触发缺页中断，由内核处理：

| 类型 | 场景 | 开销 |
|------|------|------|
| 次缺页（minor fault） | 页已分配但未建立映射（如 malloc 后首次访问）、页在 Page Cache 中 | 小，只需更新页表 |
| 主缺页（major fault） | 页被换出到 Swap，需要从磁盘读回 | 大，一次磁盘 IO 毫秒级 |

```bash
ps -o min_flt,maj_flt -p <pid>     # 查看进程的缺页次数
```

**生产关联：** Redis、Java 服务如果发生 Swap，maj_flt 飙升，延迟毛刺明显——这就是生产环境对缓存、数据库服务器**关闭 Swap** 的原因。

### 4.3 内核内存分配：伙伴系统与 Slab

- **伙伴系统（Buddy System）**：管理以页（4KB）为单位的物理内存，把空闲页按 2^n 大小分组，分配时找合适大小的块，不够就拆分，释放时尝试与"伙伴"合并，减少外部碎片。
- **Slab 分配器**：在伙伴系统之上，为内核高频小对象（task_struct、inode、dentry）建立对象缓存池，避免频繁页分配，减少内部碎片。
- **SLUB**：Slab 的改进版，现代内核默认。

```bash
cat /proc/buddyinfo          # 看伙伴系统各阶空闲页数（判断内存碎片）
slabtop                      # 看 slab 缓存占用（排查内核内存泄漏）
```

### 4.4 内存超发 overcommit（与 Redis/MySQL 强相关）

Linux 默认允许分配的虚拟内存总量超过物理内存（因为 malloc 不等于实际使用）：

| vm.overcommit_memory | 行为 |
|----------------------|------|
| 0（默认） | 启发式超发，合理的小额超发允许，明显的巨额申请拒绝 |
| 1 | 永远允许，不管是否超发 |
| 2 | 严格不超发，虚拟内存总量 ≤ Swap + RAM × overcommit_ratio |

**面试关联：** Redis 官方建议设为 1，因为 RDB fork 时子进程需要与父进程同样大小的虚拟内存，默认模式下大内存实例 fork 可能因超发检查失败而 fork 失败报错 `Cannot allocate memory`。

### 4.5 Swap 与 swappiness

Swap 是磁盘上的一块区域，内存紧张时内核把不活跃的匿名页（堆、栈）换出到 Swap，腾出物理内存。

- **vm.swappiness**（0~100，旧默认 60）：控制换出倾向，0 表示尽量不换（除非 OOM），100 表示积极换。
- **生产实践：**
  - Redis、MySQL、Elasticsearch 等对延迟敏感的服务：`swappiness=1` 或直接关闭 Swap，避免内存被换出导致毫秒级磁盘 IO 毛刺。
  - 通用服务器：可保留小 swappiness（如 10），作为 OOM 前的缓冲。

```bash
swapoff -a && swapon -a      # 清空 Swap（把换出的页读回内存）
sysctl vm.swappiness=1       # 临时调整
```

### 4.6 OOM Killer（必考）

**触发：** 物理内存 + Swap 耗尽，内核必须杀掉进程释放内存。

**选谁杀：** 内核给每个进程计算 `oom_score`（基于占用内存比例、运行时间、是否 root 等），分数最高者被杀。可用 `oom_score_adj`（-1000 ~ 1000）人工调整，-1000 表示禁止被杀。

```bash
cat /proc/<pid>/oom_score                  # 查看得分
echo -500 > /proc/<pid>/oom_score_adj      # 降低被杀优先级（如保护 sshd、MySQL 主进程）
dmesg -T | grep -i "killed process"        # 查看 OOM 记录
grep -i "out of memory" /var/log/messages  # 系统日志确认
```

**面试回答：**

> 当内存耗尽触发 OOM 时，内核的 OOM Killer 会根据每个进程的 oom_score 选择分数最高的进程杀掉，得分主要看内存占用量，也可以通过 oom_score_adj 人工干预，比如把 MySQL 主进程调成负值保护。排查 OOM 用 `dmesg -T | grep -i "killed process"` 看内核日志。Java 服务被 OOM Killer 杀掉的特点是：进程消失但 JVM 没有输出任何 GC 日志或堆转储，因为是被 SIGKILL 干掉的，这时要去看系统日志而不是应用日志。

## 五、IO 模型与网络原理

### 5.1 五种 IO 模型（必考）

一次网络读分两个阶段：**等待数据到达内核缓冲区** + **把数据从内核拷贝到用户态**。

| 模型 | 等待数据阶段 | 拷贝数据阶段 | 特点 |
|------|--------------|--------------|------|
| 阻塞 IO | 阻塞 | 阻塞 | 一个连接一个线程，连接多了线程爆炸 |
| 非阻塞 IO | 轮询不阻塞 | 阻塞 | 忙轮询浪费 CPU |
| IO 多路复用 | select/poll/epoll 阻塞等待多个连接 | 阻塞 | **一个线程管万级连接，主流方案** |
| 信号驱动 IO | 信号通知，不阻塞 | 阻塞 | 少用 |
| 异步 IO（AIO） | 不阻塞 | **内核拷贝完才通知** | 真异步，Linux 原生支持不成熟，Java AIO 底层还是 epoll |

**一句话区分：** 前四种都是同步 IO（拷贝阶段都要自己等），只有 AIO 是真异步。

### 5.2 select / poll / epoll（必考）

| 对比项 | select | poll | epoll |
|--------|--------|------|-------|
| 数据结构 | fd_set 位图 | pollfd 数组 | 红黑树 + 就绪链表 |
| 连接数上限 | 1024（FD_SETSIZE） | 无 | 无 |
| 每次调用 | 全量 fd 集从用户态拷到内核态 | 全量拷贝 | 只在 epoll_ctl 注册一次，epoll_wait 不拷贝 |
| 内核查找就绪 fd | 轮询全部 O(n) | 轮询全部 O(n) | 回调机制，直接返回就绪链表 O(1) |
| 工作模式 | 水平触发 | 水平触发 | 水平触发（LT）+ 边缘触发（ET） |

**epoll 三个系统调用：**

```c
int epfd = epoll_create(1024);              // 创建 epoll 实例（红黑树 + 就绪链表）
epoll_ctl(epfd, EPOLL_CTL_ADD, sockfd, &ev); // 注册/修改/删除监听的 fd 和事件
int n = epoll_wait(epfd, events, max, timeout); // 阻塞等待，返回就绪事件数组
```

**epoll 为什么高效（面试回答）：**

> epoll 相比 select/poll 有三大改进：第一，用 epoll_ctl 把 fd 注册到内核红黑树中一次管理，epoll_wait 时不用每次全量拷贝 fd 集合；第二，网卡中断到来时通过回调机制把就绪 fd 挂到就绪链表，epoll_wait 直接取走就绪链表，不用 O(n) 轮询所有连接，单机十万连接也能快速返回；第三，支持边缘触发 ET 模式，只在状态变化时通知一次，配合非阻塞 IO 可以进一步减少唤醒次数。Nginx、Netty、Redis 的高并发都建立在 epoll 之上。

**LT vs ET：**

| 模式 | 行为 | 编程要求 |
|------|------|----------|
| LT 水平触发（默认） | 缓冲区还有数据就反复通知 | 简单，可只读一部分 |
| ET 边缘触发 | 只在数据到达的瞬间通知一次 | 必须循环 read 到 EAGAIN，且 fd 必须非阻塞，否则丢事件 |

### 5.3 零拷贝（高频）

**传统 read + write 发送文件（4 次拷贝 + 4 次上下文切换）：**

```text
磁盘 ──DMA──► 内核读缓冲区 ──CPU──► 用户态缓冲区
                                     │
磁盘/网卡 ◄──DMA── Socket缓冲区 ◄──CPU──┘
```

**sendfile 零拷贝（2 次拷贝 + 2 次上下文切换）：**

```c
sendfile(out_fd, in_fd, offset, count);   // 数据全程在内核态流转
```

- 数据从内核读缓冲区直接拷到 Socket 缓冲区，不经过用户态。
- 配合网卡 SG-DMA（scatter-gather）可做到真正的 0 次 CPU 拷贝：只把缓冲区地址和长度描述符传给网卡。
- **应用：** Kafka 用 sendfile 发送消息文件（消费者拉取时 page cache → 网卡），Nginx 静态文件、RocketMQ 也大量使用。

**mmap 零拷贝：** `mmap` 把文件映射到用户态地址空间，应用直接读写 Page Cache，省去 read/write 的用户态拷贝（RocketMQ 的 CommitLog 用它）。适合小文件高频读写；sendfile 适合大文件一次性发送。

### 5.4 网络收发包流程（简述）

**收包：**

```text
网卡收到帧 ──DMA──► 内核环形缓冲区（Ring Buffer）
   │
   ▼ 触发硬中断
硬中断处理函数：取包、触发 NET_RX 软中断后快速返回
   │
   ▼
ksoftirqd 处理软中断：驱动 → IP 层 → TCP 层 → 放入 Socket 接收缓冲区
   │
   ▼
唤醒阻塞在 read/recv 或 epoll_wait 的进程，数据拷贝到用户态
```

**发包：** 应用 write → 拷贝到 Socket 发送缓冲区 → TCP 层分段加头 → IP 层加头分片 → 邻居子系统（ARP）→ 网卡队列 → DMA 发出 → 完成后硬中断释放内存。

**相关排查命令：**

```bash
cat /proc/interrupts | grep eth0     # 网卡中断分布（是否单核热点，可用 RPS/多队列分散）
sar -n DEV 1                         # 每秒网卡流量
ethtool -S eth0                      # 网卡级统计（丢包、错误帧）
ss -s                                # Socket 汇总统计
```

## 六、Cgroup 与 Namespace（容器基石）

Docker/K8s 的隔离与资源限制完全构建在这两个内核特性之上。

### 6.1 Namespace：隔离视图

| Namespace | 隔离内容 | 系统调用标志 |
|-----------|----------|--------------|
| PID | 进程 ID，容器内 PID 1 是自己的 init | CLONE_NEWPID |
| NET | 网络设备、IP、端口、路由表 | CLONE_NEWNET |
| MNT | 文件系统挂载点 | CLONE_NEWNS |
| UTS | 主机名、域名 | CLONE_NEWUTS |
| IPC | System V IPC、POSIX 消息队列 | CLONE_NEWIPC |
| USER | UID/GID 映射（容器内 root 映射宿主机普通用户） | CLONE_NEWUSER |

```bash
lsns                       # 查看系统所有 namespace
ls -l /proc/<pid>/ns/      # 查看某进程的 namespace（软链接，ID 相同即同命名空间）
nsenter -t <pid> -n bash   # 进入某进程的网络命名空间（排查容器网络神器）
```

### 6.2 Cgroup：限制资源

Cgroup（Control Group）对进程组进行资源**限制、统计、隔离**，通过 `/sys/fs/cgroup/` 虚拟文件系统配置。

| 子系统 | 控制内容 | Docker 对应参数 |
|--------|----------|-----------------|
| cpu | CPU 使用率（cfs_quota/cfs_period） | `--cpus=1.5` |
| memory | 内存上限、OOM 控制 | `--memory=512m` |
| blkio | 磁盘 IO 带宽/IOPS | `--device-read-bps` |
| pids | 进程数上限 | `--pids-limit` |
| cpuset | 绑定 CPU 核、内存节点 | `--cpuset-cpus` |
| net_cls | 网络流量标记 | 配合 tc 限流 |

```bash
cat /sys/fs/cgroup/memory/docker/<cid>/memory.limit_in_bytes   # 看容器内存限制
cat /sys/fs/cgroup/cpu/docker/<cid>/cpu.cfs_quota_us           # 看容器 CPU 配额
```

**面试高频坑：** JVM 旧版本（JDK8u131 之前）不认识容器 cgroup 限制，按宿主机内存算堆，导致容器里 Java 进程超限制被 OOM Kill。新版本（JDK8u191+ / JDK10+）默认感知容器限制。

## 七、本章面试速记卡

1. **系统调用过程**：参数入寄存器 → syscall 指令 → 切内核态 → 查系统调用表 → 执行 → 恢复现场切回。
2. **中断两阶段**：硬中断只做最急的事，耗时工作交给软中断（NET_RX），top 的 %si 高说明网络繁忙。
3. **inode**：存元数据不含文件名，文件名在目录内容里；`df -i` 排查 inode 耗尽。
4. **硬链接 vs 软链接**：硬链接同 inode、删源文件可访问、不可跨文件系统；软链接是路径字符串、删源文件失效。
5. **删除文件空间不释放**：进程持有 fd → `lsof | grep deleted` → 重启进程或 `> file` 清空。
6. **Page Cache**：写文件先写缓存标记脏页异步刷盘，`fsync` 强制落盘；看可用内存看 available 别看 free。
7. **fork COW**：fork 只复制页表标记只读，写入时才复制页；Redis fork 风险与 overcommit_memory=1。
8. **CFS 调度**：按 vruntime 红黑树选最饿的进程，nice 值映射权重。
9. **线程实现**：clone + 共享标志，线程即 LWP，内核调度单位都是 task；Java 线程与 OS 线程 1:1。
10. **僵尸进程**：父进程不 wait 导致，kill 不掉，杀父进程让 PID 1 回收。
11. **OOM Killer**：按 oom_score 杀分最高者，oom_score_adj 可调，dmesg 查记录；Java 进程无故消失先查 OOM。
12. **epoll**：红黑树管理 fd + 回调收集就绪事件 + 就绪链表，O(1) 返回；ET 模式必须非阻塞 + 循环读到 EAGAIN。
13. **零拷贝**：sendfile 2 次拷贝 2 次切换（Kafka），mmap 共享 Page Cache（RocketMQ）。
14. **容器基石**：Namespace 做视图隔离（6 种），Cgroup 做资源限制（cpu/memory/blkio/pids）。
