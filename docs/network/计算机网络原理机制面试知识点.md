# 计算机网络原理机制面试知识点

> 本文档聚焦计算机网络底层原理：三次握手/四次挥手深挖、可靠传输机制、滑动窗口、拥塞控制、TLS 握手细节、HTTP/2 与 HTTP/3 原理。基础概念先看 [`计算机网络面试知识点.md`](计算机网络面试知识点.md)。

## 一、TCP 三次握手深入

### 1.1 初始序列号 ISN 为什么要随机？

三次握手中双方各自发送自己的初始序列号 ISN（Initial Sequence Number），它**不是从 0 开始，而是随机生成**的，原因有两个：

1. **防止历史连接的重复报文干扰**：如果每次连接的序列号都从 0 开始，旧连接中滞留在网络里的报文可能被新连接当成合法数据接收。随机 ISN 让旧报文的序号几乎不可能落在新连接的接收窗口内。
2. **防伪造攻击**：攻击者如果容易猜到序列号，就能伪造 TCP 报文（TCP 劫持）。随机 ISN 大大增加了伪造难度。

### 1.2 第三次握手可以携带数据吗？

可以。前两次握手（SYN 报文）不能携带应用数据，但**第三次 ACK 报文已经可以携带数据**——因为此时客户端已经确认了双方的收发能力，连接对客户端而言已建立。

### 1.3 半连接队列与全连接队列（高频）

```text
服务端收到 SYN      收到 ACK（三次握手完成）      accept() 取走
  ──────────► 半连接队列 ──────────► 全连接队列 ──────────► 应用程序
            (SYN queue)            (accept queue)
```

| 队列 | 存放内容 | 满了的后果 | 相关参数 |
|------|----------|------------|----------|
| 半连接队列 | 收到 SYN、回了 SYN+ACK，还没收到 ACK 的连接（SYN_RCVD） | 丢弃新 SYN 或开启 `tcp_syncookies` | `net.ipv4.tcp_max_syn_backlog`、`tcp_syncookies` |
| 全连接队列 | 三次握手完成、等待 accept() 的连接 | 丢弃 ACK 或直接 RST | `listen(fd, backlog)` 的 backlog、`net.core.somaxconn` |

**面试高频追问：全连接队列满了会怎样？**

> 客户端发来 ACK 时如果全连接队列已满，服务端默认会**忽略这个 ACK**（`tcp_abort_on_overflow=0`），客户端以为连接建立成功，但服务端没建，后续客户端发数据会被 RST。表现为"客户端连接成功但调用失败"。调大 `somaxconn` 和应用 listen 的 backlog 可缓解。

### 1.4 SYN 泛洪攻击（SYN Flood）

**原理：** 攻击者伪造大量源 IP 发送 SYN，服务端回 SYN+ACK 后永远等不到 ACK，半连接队列被占满，正常用户无法建立连接。

**防御手段：**

| 手段 | 原理 |
|------|------|
| `tcp_syncookies` | 半连接队列满时，不分配资源，把连接信息编码进 SYN+ACK 的序号里，收到合法 ACK 时再验证并建连（无状态验证） |
| 调大半连接队列 | `tcp_max_syn_backlog`，治标不治本 |
| 减少 SYN+ACK 重传次数 | `tcp_synack_retries`，加速无效连接释放 |
| 防火墙/网关层过滤 | 限速、黑名单、清洗（DDoS 高防） |

## 二、TCP 四次挥手深入

### 2.1 TIME_WAIT 为什么是 2MSL？（必考）

主动关闭方发出最后一个 ACK 后进入 TIME_WAIT，等待 **2MSL**（MSL = Maximum Segment Lifetime，报文最大生存时间，Linux 默认 30s，故 TIME_WAIT 通常 60s）才真正关闭。两个原因：

1. **保证最后一个 ACK 能到达对方**：如果最后的 ACK 丢了，被动方会超时重发 FIN，主动方在 TIME_WAIT 期间还能再次回复 ACK。等待 2MSL 足够"FIN 一来 + ACK 一回"。如果发完 ACK 立即关闭，这个 ACK 丢了对方就永远无法正常关闭。
2. **让本次连接的所有报文都在网络中消亡**：防止旧连接的迟到报文混进"四元组相同的新连接"里造成数据错乱。

**一句话模板：**

> TIME_WAIT 等 2MSL 是为了：一、万一最后的 ACK 丢失，对方重发 FIN 时我还能再确认一次，保证对方正常关闭；二、让本连接的报文在网络中彻底消失，避免旧报文串扰四元组相同的新连接。

### 2.2 为什么大量 TIME_WAIT 通常出现在"主动关闭方"？

只有**主动发起关闭的一方**才会进入 TIME_WAIT。所以：

- 高并发短连接的客户端（如爬虫、压测机）容易自己堆 TIME_WAIT，耗尽本地端口。
- 服务端如果用短连接主动关连接，也会堆 TIME_WAIT，占用 fd。

治理手段见 [`计算机网络生产实战面试知识点.md`](计算机网络生产实战面试知识点.md)。

### 2.3 CLOSE_WAIT 过多是什么问题？（线上高频）

CLOSE_WAIT 出现在**被动关闭方**：对方发了 FIN（说明对方已经关闭了写方向），本方回复 ACK 后就该调用 `close()` 发 FIN。**CLOSE_WAIT 堆积 = 应用程序有 Bug，忘了关闭连接**。

排查方向：
- 连接池/HTTP 客户端代码路径里有分支没 close（异常分支、return 提前）。
- 框架配置问题（如连接复用但服务端已关，客户端没处理）。
- `ss -antp | grep CLOSE_WAIT` 看是哪个进程、连的谁。

### 2.4 TCP 保活机制（Keepalive）

连接长时间无数据时，TCP 有保活探测（默认 2 小时首次探测，`tcp_keepalive_time`），但对应用层来说太久。实践中：

- 应用层自己做**心跳**（如 Netty 的 `IdleStateHandler`、RPC 框架心跳）。
- 防止 NAT 超时回收映射、防火墙断链、对端假死（断电/断网时 TCP 本身感知不到）。

## 三、TCP 可靠传输机制

### 3.1 可靠性的四大支柱

| 机制 | 解决的问题 | 原理 |
|------|------------|------|
| 序列号 + 确认应答（ACK） | 丢包感知、乱序排序、去重 | 每个字节编号；接收方按序确认；重复序号直接丢弃 |
| 超时重传 | 丢包恢复 | 发出后 RTO 时间内没收到 ACK 就重发；RTO 动态计算（RTT 加权） |
| 校验和 | 数据损坏 | 头部+数据一起校验，错了就丢弃等重传 |
| 流量控制 + 拥塞控制 | 别把接收方/网络打爆 | 见下文 |

**快速重传：** 发送方如果连续收到 **3 个相同的冗余 ACK**（说明中间有个包丢了，后面的包都到了），不等超时立即重发丢失的报文——比等 RTO 快得多。

### 3.2 滑动窗口（流量控制）

```text
发送方窗口：
[已发送已确认 | 已发送未确认 | 可发送未发送 | 不可发送 ]
                              ◄── 窗口大小 = 接收方通告的 rwnd ──►

接收方通过 ACK 报文中的窗口字段（rwnd）告诉发送方：
"我的接收缓冲区还剩多少空间，你最多还能发多少"
```

- **窗口为 0**：发送方停止发送，定期发**窗口探测报文**，等接收方缓冲区腾出空间后通告新窗口。
- **糊涂窗口综合症**：接收方每次只通告很小的窗口，导致大量小报文浪费带宽。解法：接收方攒够一定大小再通告（Clark 算法）；发送方用 **Nagle 算法**攒小数据一起发。

> **Nagle vs TCP_NODELAY**：Nagle 减少小包数量提升效率，但引入延迟。对时延敏感的应用（SSH、游戏、RPC）常设置 `TCP_NODELAY` 关闭 Nagle。面试联动：Redis 客户端、RPC 框架默认开 `TCP_NODELAY`。

### 3.3 拥塞控制（必考）

拥塞控制解决的是"**别把网络打爆**"，核心是发送方维护一个**拥塞窗口 cwnd**，实际发送窗口 = `min(rwnd, cwnd)`。

```text
cwnd
  │      拥塞发生
  │        │  ssthresh 减半，cwnd 降为 1
  │  ▲     ▼  重新慢启动
  │  │╲    ▲
  │  │ ╲  ╱ ╲        ╱── 拥塞避免（线性增长）
  │  │  ╲╱   ╲      ╱
  │  │  ↑     ╲    ╱
  │  │ ssthresh  ╲╱
  │  ╰────────────────────────► 轮次
  慢启动（指数增长）
```

| 阶段 | 行为 | 增长方式 |
|------|------|----------|
| **慢启动** | cwnd 从 1 开始，每收到一个 ACK 就 +1（每轮翻倍） | **指数增长**，直到超过 ssthresh（慢启动门限） |
| **拥塞避免** | cwnd ≥ ssthresh 后，每轮只 +1 | **线性增长**，谨慎探测 |
| **快重传** | 收到 3 个冗余 ACK，立即重发丢失包，不等超时 | —— |
| **快恢复** | 快重传后：ssthresh = cwnd/2，cwnd = ssthresh（**不回到 1**），直接进入拥塞避免 | 认为只是个别丢包，网络没那么糟，温和降速 |

**超时 vs 3 个冗余 ACK 的区别对待：**
- **超时重传**：认为网络严重拥塞 → ssthresh 减半，cwnd 打回 1，重新慢启动（剧烈）。
- **3 个冗余 ACK**：认为只是个别丢包 → 快恢复，cwnd 减半后继续线性增长（温和）。

**现代拥塞控制算法：**

| 算法 | 思路 | 应用 |
|------|------|------|
| Reno / New Reno | 上述经典四件套 | 传统默认 |
| CUBIC | 用三次函数建模窗口增长，丢包后快速逼近上次窗口 | **Linux 默认** |
| BBR | 不基于丢包，而是测量**带宽和 RTT**，主动控制发送速率逼近瓶颈带宽 | Google 提出，高丢包网络下吞吐显著提升 |

**面试一句话：**

> TCP 拥塞控制通过慢启动快速试探、拥塞避免线性增长逼近网络容量；丢包时区分对待：超时说明拥塞严重，cwnd 打回 1 重新慢启动；3 个冗余 ACK 只是个别丢包，触发快重传快恢复，cwnd 减半后继续。现代算法如 BBR 不再以丢包为拥塞信号，而是测量瓶颈带宽和最小 RTT 主动调速，在高丢包链路上吞吐远超 CUBIC。

## 四、HTTPS / TLS 原理深入

### 4.1 TLS 1.2 握手完整流程（以 ECDHE 为例）

```text
客户端                                              服务端
  │                                                    │
  │ ── ① ClientHello ────────────────────────────────► │
  │     （TLS版本、随机数 Random1、加密套件列表）          │
  │                                                    │
  │ ◄─ ② ServerHello ───────────────────────────────── │
  │     （选定套件、随机数 Random2）                      │
  │ ◄─ ③ Certificate ──────────────────────────────── │
  │     （服务器证书：含公钥/ECDHE参数、CA签名）            │
  │ ◄─ ④ ServerKeyExchange（ECDHE 参数+签名）────────── │
  │ ◄─ ⑤ ServerHelloDone ──────────────────────────── │
  │                                                    │
  │  客户端：验证证书（CA链、域名、有效期）                │
  │ ── ⑥ ClientKeyExchange（自己的 ECDHE 公钥）────────► │
  │                                                    │
  │  双方各自计算：pre_master = ECDHE(对方公钥, 自己私钥)   │
  │  会话密钥 = PRF(pre_master, Random1, Random2)       │
  │                                                    │
  │ ── ⑦ ChangeCipherSpec + Finished（加密）──────────► │
  │ ◄─ ⑧ ChangeCipherSpec + Finished（加密）────────── │
  │                                                    │
  │ ══════ 之后全部用会话密钥对称加密传输 ══════            │
```

**三个关键设计点：**

1. **两个随机数 + ECDHE 临时密钥**共同生成会话密钥：即使某个随机数泄露也无法算出密钥。
2. **ECDHE 的前向安全性（Forward Secrecy）**：每次握手生成临时的 DH 密钥对，用完即弃。即使服务器私钥未来泄露，历史通信也无法解密（对比：RSA 握手中 pre_master 用服务器公钥加密传输，私钥一旦泄露历史流量全部可解密——**这是 TLS 1.3 废掉 RSA 密钥交换的原因**）。
3. **证书 + 签名**：ServerKeyExchange 用服务器私钥签名，防止中间人替换 ECDHE 参数。

### 4.2 TLS 1.3 的改进

| 改进点 | 说明 |
|--------|------|
| **1-RTT 握手** | ClientHello 直接带上密钥共享信息，一轮往返完成握手（TLS 1.2 要 2-RTT） |
| **0-RTT 恢复** | 会话恢复时可随第一条消息直接发加密数据（有重放风险，只适合幂等请求） |
| 废掉不安全算法 | 移除 RSA 密钥交换（无前向安全）、CBC 模式、SHA-1、MD5、RC4、3DES |
| 更多握手信息加密 | ServerHello 之后的消息都加密，减少明文暴露 |

### 4.3 中间人攻击与证书 pinning

**没有证书会怎样：** 中间人可以在握手时替换公钥，同时与客户端、服务端各建一条加密通道，两端都以为在跟对方通信，实际内容全被中间人看穿。

**证书链验证（客户端做什么）：**

```text
服务器证书（example.com）
   │ 由谁签发？用签发者公钥验签
中间 CA 证书
   │ 由谁签发？继续向上验签
根 CA 证书 ←── 浏览器/OS 内置信任库里有，直接信任
同时检查：域名匹配、有效期、吊销状态（CRL/OCSP）
```

**证书 pinning（证书固定）：** App 内置服务器的证书或公钥指纹，不信任系统 CA 库，防止用户设备被装了恶意根证书后遭中间人攻击（银行类 App 常用；代价是换证书必须发版）。

## 五、HTTP 协议演进原理

### 5.1 HTTP/1.1 的队头阻塞

HTTP/1.1 长连接上，请求必须**排队串行**处理（管道化要求响应按序返回，一个慢响应堵住后面所有，浏览器实际都禁用了管道化）。浏览器的绕法：**对同一域名开 6~8 个 TCP 连接**并行请求。

- 队头阻塞发生在 **HTTP 层**：即使 TCP 层数据已到齐，HTTP 也必须等前一个响应完成。

### 5.2 HTTP/2 详解

#### 5.2.1 设计目标与二进制分帧层

HTTP/2 的三个设计目标：**解决 HTTP/1.1 队头阻塞、压缩头部开销、不改变 HTTP 语义**（方法、状态码、Header 全部兼容，应用层无感知）。

核心手段是在 HTTP 和 TCP 之间插入一个**二进制分帧层（Binary Framing Layer）**：不再传输文本报文，而是把请求/响应拆成一个个二进制**帧（Frame）**。

**帧结构（9 字节固定头部 + 变长载荷）：**

```text
┌─────────────────────────────────────────────┐
│ Length (24 bit)        载荷长度，默认上限 16KB  │
│ Type (8 bit)           帧类型（见下表）          │
│ Flags (8 bit)          标志位（END_STREAM 等）  │
│ R + Stream ID (31 bit) 所属流的编号             │
│ Frame Payload ...      载荷内容                │
└─────────────────────────────────────────────┘
```

**常见帧类型：**

| 帧类型 | 作用 | 面试关注点 |
|--------|------|------------|
| HEADERS | 携带 HTTP 头部（HPACK 压缩后） | 头部过大的用 CONTINUATION 帧续传 |
| DATA | 携带 body 数据 | 受流控窗口限制 |
| SETTINGS | 建连时交换配置（最大并发流数、初始窗口大小等） | 连接建立后双方必须先发 |
| WINDOW_UPDATE | 增大流控窗口 | HTTP/2 流控的载体 |
| RST_STREAM | 立即终止某个流 | 单流中止不影响连接（HTTP/1.1 只能断整条连接） |
| PING | 测量 RTT、保活 | —— |
| GOAWAY | 优雅关闭连接，告知对方"别再开新流" | 滚动发布/连接 draining 的关键 |
| PRIORITY | 携带流优先级信息 | —— |
| PUSH_PROMISE | 服务器推送时预告资源 | 配合推送缓存 |

#### 5.2.2 Stream 与多路复用

- **Stream（流）**：一条 HTTP/2 连接上的双向字节流，承载一次完整的"请求-响应"交换。每条流有唯一 **Stream ID**（**客户端发起的流用奇数，服务端推送的流用偶数**）。
- **多路复用**：多个流的帧在**一条 TCP 连接上交错传输**，接收方按 Stream ID 重组。请求不再需要排队等前一个响应——这就是 HTTP/2 解决队头阻塞的原理。
- **流并发上限**：由服务端 `SETTINGS_MAX_CONCURRENT_STREAMS` 通告（常见 100~1000），避免单连接把服务端打爆。

```text
HTTP/1.1（串行）：  请求A ──► 响应A ──► 请求B ──► 响应B
HTTP/2（多路复用）： 请求A ─┐
                    请求B ─┼─► 同一条连接上帧交错 ─► 响应B帧、响应A帧按ID重组
                    请求C ─┘
```

**流状态机（了解即可）：**

```text
                 发送/接收 HEADERS
        idle ──────────────────────► open ──发送/接收 END_STREAM──► half-closed
         │                              │  （对方已结束，本方还可发）
         │ 接收 PUSH_PROMISE            │
         └────────► reserved ───────────┘
                              发送/接收 RST_STREAM
                   open/half-closed ────────────► closed
```

#### 5.2.3 HPACK 头部压缩（高频）

HTTP/1.x 的痛点：每次请求都重复携带 Cookie、User-Agent 等几百上千字节的头部，**头部开销常常超过 body**。HPACK 用三招压缩：

| 手段 | 原理 |
|------|------|
| **静态表** | 协议内置 61 个常见头部名/值（如 `:method: GET` 索引 2），直接传索引号 |
| **动态表** | 连接两端各自维护一张表，把本次连接中出现过的头部存进去，后续只传索引（两端同步更新） |
| **Huffman 编码** | 对不命中表的字符串值做哈夫曼编码，高频字符用短编码，再省 20%~30% |

**面试一句话：**

> HPACK 的本质是"用连接级别的状态换带宽"：静态表覆盖常见头部，动态表记住本连接发过的头部（所以连续请求的 Cookie 只传一次原文，之后只传索引），再加上 Huffman 编码压值。头部压缩率通常能到 80% 以上。

#### 5.2.4 流量控制：连接级 + 流级两层

HTTP/2 在 TCP 滑动窗口之外**自己又做了一层流控**（因为多路复用后，TCP 的单一窗口无法区分"哪条流该慢点"）：

- **两级窗口**：每条流有自己的流控窗口，整条连接也有一个总窗口，DATA 帧受两者同时约束。
- **接收方**通过 `WINDOW_UPDATE` 帧告知窗口增量；窗口为 0 的流暂停发送 DATA（HEADERS 不受限）。
- **初始窗口**由 SETTINGS 帧协商（默认 64KB），可针对大文件场景调大。

**与 TCP 流控的关系：** TCP 窗口控制"这条连接整体能发多少"，HTTP/2 窗口控制"这条流/这个连接在应用层该发多少"——两层叠加，实际可发量取各层最小值。

#### 5.2.5 流优先级

客户端可以给流设置**依赖树 + 权重**（1~256）：父流优先于子流，同级按权重分配带宽。浏览器借此实现"CSS/JS 优先、图片靠后"。

> 现实备注：优先级机制实现复杂、各服务端支持不一，HTTP/2 的优先级方案后来被证明效果有限，HTTP/3 换成了更简单的 `Priority` 头部方案（Extensible Priorities）。

#### 5.2.6 服务器推送（Server Push）

服务端可以"未请求先推送"：解析到 HTML 后，主动用 PUSH_PROMISE 帧预告并推送 CSS/JS，省去浏览器解析后再请求的 RTT。

**为什么失败了（面试可能追问）：** 推送资源与浏览器缓存无法协同（重复推送浪费带宽）、实现复杂、收益不稳定——**Chrome 已于 2022 年移除 HTTP/2 推送支持**，实践上用 `103 Early Hints` 状态码（提前告知预加载，让浏览器自己拉）替代。

#### 5.2.7 HTTP/2 的遗留问题

1. **TCP 层队头阻塞（核心遗留问题）**：多个流共享一条 TCP，一旦某个 TCP 段丢失，**所有流都要等它重传**（TCP 必须按序交付）。丢包率 2% 以上的网络中，HTTP/2 单连接可能跑不过 HTTP/1.1 的 6 条连接。
2. **TLS + TCP 握手仍要 2~3 RTT**：建连慢的问题没解决。
3. **单连接单点故障**：一条 TCP 连接中断（网络切换、NAT 超时），所有流全部失败。

### 5.3 HTTP/3 与 QUIC 详解

#### 5.3.1 协议栈与"为什么偏偏是 UDP"

```text
HTTP/1.1 & HTTP/2：                HTTP/3：
┌──────────────┐                  ┌──────────────┐
│    HTTP      │                  │    HTTP/3    │ （语义层，复用 HTTP 语义）
├──────────────┤                  ├──────────────┤
│   TLS 1.2+   │                  │ QUIC（用户态） │ ← 可靠传输+流+TLS1.3 全在这层
├──────────────┤                  │  ├ 流多路复用   │
│     TCP      │                  │  ├ 可靠传输/拥塞 │
├──────────────┤                  │  └ 内建 TLS 1.3 │
│     IP       │                  ├──────────────┤
└──────────────┘                  │     UDP      │
                                  ├──────────────┤
                                  │     IP       │
                                  └──────────────┘
```

**为什么选 UDP 而不是重新设计一个传输层协议？**

> 一是**可部署性**：TCP 实现在操作系统内核里，改 TCP 要等所有 OS、所有中间设备（防火墙/NAT）升级，历史证明新传输协议（如 SCTP）几十年都推不动；UDP 几乎所有网络设备都放行，QUIC 跑在**用户态**，升级只改应用库，几周就能全量。二是**绕过 TCP 的固化**：把可靠传输、拥塞控制、多路复用全部在用户态自己实现，不再受内核 TCP 协议栈的约束。

#### 5.3.2 彻底解决队头阻塞：流真正独立

TCP 按"字节流全局有序"交付，丢一个包卡全部；QUIC 把**交付单位换成流（Stream）**：

- 每条流内部保序，**流与流之间完全独立**。
- 某个包丢了，只有携带该包数据的那条流等待重传，其他流的数据照常交付给应用。

```text
TCP（HTTP/2）：  流A数据 | 流B丢失包X | 流C数据
                 流A、流C 已到也得等 X 重传 ← 全局队头阻塞

QUIC（HTTP/3）： 流A数据 | 流B丢失包X | 流C数据
                 流A、流C 直接交付，只有流B 等 X ← 只堵一条流
```

#### 5.3.3 1-RTT 与 0-RTT 握手

QUIC 把传输层握手和 TLS 1.3 握手**合并**：

| 场景 | RTT 消耗 | 对比 |
|------|----------|------|
| 首次连接 | **1-RTT**（ClientHello 同时完成密钥协商，服务端一轮响应即建好） | TCP+TLS1.2 要 3-RTT，TCP+TLS1.3 要 2-RTT |
| 会话恢复 | **0-RTT**：客户端用缓存的票据和密钥，**第一个报文就带应用数据** | TCP 会话复用最快也要 1-RTT |

**0-RTT 的重放风险（高频追问）：** 0-RTT 数据没有交互随机性保护，攻击者抓到 0-RTT 报文可以**原样重放**。

**防御：**
- 只允许**幂等请求**（GET/HEAD）走 0-RTT，下单/转账类必须等 1-RTT 完成后发。
- 服务端做 0-RTT 去重（记录已处理的早期数据标识）。
- 业务侧幂等设计兜底（唯一请求号）。

#### 5.3.4 连接迁移（Connection Migration）

TCP 连接由四元组（源IP、源端口、目的IP、目的端口）标识，手机从 Wi-Fi 切到 4G，源 IP 变了，连接必断（表现为视频卡顿、游戏掉线重连）。

QUIC 连接由 **Connection ID（CID）** 标识，与四元组解耦：

```text
Wi-Fi:  手机(10.0.0.2:5001) ──CID=abc123──► 服务器
            │ 切到 4G，IP 变为 100.x.x.x
4G:     手机(100.x.x.x:5001) ──CID=abc123──► 服务器
        报文里 CID 不变，服务器认出"还是那条连接"，通信无感继续
```

**细节：** 为防被动观察关联追踪，CID 池里有多个备选 CID 可轮换；服务端会通过 NEW_CONNECTION_ID 帧下发。NAT rebinding 场景同样受益。

#### 5.3.5 可靠传输机制的改进（相对 TCP）

| 改进点 | TCP 的做法 | QUIC 的做法 | 收益 |
|--------|------------|-------------|------|
| **包号语义** | 序列号表示字节序号，重传包用**原序号** | Packet Number **单调递增**，重传也用新包号（数据靠 Stream 内 offset 定位） | TCP 重传包和原包 ACK 无法区分（重传二义性），RTT 计算失真；QUIC 天然区分，RTT 更准 |
| **ACK 精度** | 最多 3 个 SACK 块 | ACK 帧可携带 256 个 ACK Block | 高丢包环境下丢包定位更准，减少无效重传 |
| **ACK Delay** | 无此概念 | ACK 显式携带"收到包后延迟多久才回 ACK" | RTT 估算剔除接收端延迟，更精确 |
| **RTO 计算** | 同经典算法 | 单调包号使重传事件清晰 | 避免伪重传（spurious retransmission） |
| **拥塞控制** | 内核固化（CUBIC） | 用户态可插拔，CUBIC/BBR 随意换甚至按业务定制 | 迭代快 |

#### 5.3.6 QUIC 的流量控制

与 HTTP/2 类似的两级结构，但更严格（**强制开启**，防慢消费者拖垮连接）：

- **Stream 级**：每条流有 `MAX_STREAM_DATA` 上限，接收方通过 `MAX_STREAM_DATA` 帧扩容。
- **Connection 级**：整条连接有 `MAX_DATA` 总上限，所有流共享。
- 发送方超窗发送属于**协议违规**，对方可以直接断开（FLOW_CONTROL_ERROR）。

#### 5.3.7 QPACK：适配 QUIC 的头部压缩

HPACK 要求**压缩状态全局有序**（动态表按序更新），在 TCP 保序交付下没问题；但 QUIC 流独立、乱序交付，如果沿用 HPACK，动态表更新要等前面的流——**压缩本身又引入队头阻塞**。

QPACK 的解法：
- 压缩状态走**两条专用的单向流**（Encoder Stream / Decoder Stream）与数据流分离。
- 允许"风险自负"模式：编码方可以选择不引用尚未确认的动态表项，宁可多传几个字节也不等待。
- 用 Reference 计数跟踪表项是否被对端确认，避免引用未同步的表项。

#### 5.3.8 加密程度对比（QUIC vs TCP+TLS）

| 内容 | TCP + TLS | QUIC |
|------|-----------|------|
| 应用数据 | 加密 | 加密 |
| 协议头部（包号等） | **明文**（TCP 头裸奔） | **也加密**（仅首包必要字段明文） |
| 传输层元数据 | 中间设备可见可改（导致协议僵化） | 不可见，中间设备无法插手 |

> "协议僵化"是面试加分点：TCP 头部明文暴露几十年，中间设备（防火墙、NAT）学会了基于 TCP 头做各种干预，导致任何 TCP 扩展都可能被中间设备丢弃；QUIC 把传输层也加密，等于把协议的演进权从中间设备手里夺回来。

#### 5.3.9 部署挑战与现状

| 挑战 | 说明 |
|------|------|
| 运营商/QoS 对 UDP 限速 | 部分网络对 UDP 不友好，需要 TCP 回退兜底（浏览器同时竞速 HTTP/2 和 HTTP/3） |
| CPU 开销 | 用户态协议栈 + 逐包加密，CPU 消耗高于内核 TCP（可用 UDP GSO、内核旁路等优化） |
| 内核生态 | UDP 收发包系统调用效率低于 TCP（sendmmsg/GSO/GRO 缓解） |
| 服务端生态 | Nginx 1.25+ 官方支持、Envoy/Cloudflare 全面支持；Google、Meta、快手、抖音已大规模部署 |

**现状：** 全球约 30% 的网站流量已支持 HTTP/3，移动端弱网（高丢包、频繁切网）场景收益最大。

**面试一句话：**

> HTTP 的演进主线是"解决队头阻塞和握手时延"：HTTP/1.1 用长连接避免重复握手但请求串行；HTTP/2 用二进制分帧在一条连接上多路复用解决了 HTTP 层队头阻塞，但多个流共享一条 TCP，丢包时仍有 TCP 层队头阻塞；HTTP/3 换用基于 UDP 的 QUIC，流之间相互独立彻底解决队头阻塞，握手合并成 1-RTT（会话恢复 0-RTT），并用 Connection ID 实现连接迁移，还把可靠传输做到用户态获得快速迭代能力，代价是 UDP 受限和更高的 CPU 开销。

## 六、输入 URL 到页面展示全链路深挖

> 这道题是网络知识点的"串联器"，深挖版按阶段拆解每一步的技术细节。

```text
① URL 解析与缓存检查
   ├─ 解析协议/域名/端口/路径；HSTS 列表命中则强制改 HTTPS
   ├─ 查浏览器缓存（强缓存命中直接用，不发请求）
② DNS 解析
   ├─ 浏览器缓存 → OS 缓存 → hosts → 本地 DNS（递归）
   ├─ 本地 DNS 迭代查询：根 → 顶级域 → 权威 DNS
   └─ 有 CDN 时 CNAME 到 CDN，GSLB 按地理位置返回最近节点 IP
③ TCP 建连
   ├─ 三次握手；目的端口 443/80
   └─ 途中经过 NAT、防火墙、运营商网络、负载均衡（LVS DR/NAT）
④ TLS 握手（HTTPS）
   ├─ TLS 1.2：2-RTT；TLS 1.3：1-RTT（会话复用 0-RTT）
   └─ 验证证书链 → 协商出会话密钥
⑤ 发送 HTTP 请求
   ├─ 报文经 TCP 分段（MSS）→ IP 分片/路由 → 帧（ARP 找下一跳 MAC）
   └─ 服务端网卡收包 → 中断/协议栈 → epoll 通知 → Nginx accept
⑥ 服务端处理
   ├─ Nginx 反代 → 网关（鉴权/限流）→ 应用服务
   ├─ 应用：查 Redis → 穿透则查 MySQL → 组装响应
   └─ 可能涉及 RPC 调用、消息队列
⑦ 浏览器渲染
   ├─ HTML → DOM；CSS → CSSOM；合成渲染树 → 布局 → 分层 → 绘制 → GPU 合成
   ├─ JS 阻塞解析（async/defer 优化）；预加载扫描器提前拉资源
   └─ 协商缓存：If-None-Match/If-Modified-Since → 304
⑧ 连接收尾
   └─ HTTP/1.1 Keep-Alive 复用；闲置超时后四次挥手
```

**回答技巧：** 不必每步都展开，按"DNS → TCP → TLS → HTTP → 服务端 → 渲染"的主线讲，面试官追问哪步再深挖哪步——每个环节都能对应到本文档前面的原理章节。

## 七、原理机制高频问题速记

| 问题 | 一句话答案 |
|------|------------|
| ISN 为什么随机 | 防旧连接报文串扰 + 防伪造劫持 |
| 第三次握手能带数据吗 | 能，前两次 SYN 不能 |
| 半连接队列 | 存 SYN_RCVD 连接；SYN Flood 就是打满它；syncookies 防御 |
| 全连接队列满了 | 服务端忽略 ACK，客户端以为连上但数据被 RST；调大 somaxconn/backlog |
| TIME_WAIT 为什么 2MSL | 保证最后 ACK 可达（对方重发 FIN 能再确认）+ 让旧报文消亡 |
| CLOSE_WAIT 堆积 | 被动方忘了 close()，应用代码 Bug |
| TCP 靠什么保证可靠 | 序号+ACK+超时重传+快速重传+校验和+滑动窗口+拥塞控制 |
| 快速重传 | 收到 3 个冗余 ACK 立即重发，不等 RTO |
| 流量控制 vs 拥塞控制 | 前者防打爆接收方（rwnd），后者防打爆网络（cwnd），实际窗口取 min |
| 慢启动/拥塞避免 | 指数增长到 ssthresh 后线性增长 |
| 超时 vs 冗余 ACK 的处理 | 超时：cwnd 归 1 慢启动；冗余 ACK：快恢复，cwnd 减半线性增 |
| BBR 算法 | 测量瓶颈带宽+最小 RTT 主动调速，不以丢包为拥塞信号 |
| Nagle 算法 | 攒小报文一起发；时延敏感场景用 TCP_NODELAY 关闭 |
| HTTPS 混合加密 | 非对称换会话密钥 + 对称加密传数据，兼顾安全与性能 |
| TLS 1.3 vs 1.2 | 1-RTT/0-RTT 握手；废 RSA 密钥交换（强制前向安全）；更多加密 |
| 前向安全性 | 临时密钥（ECDHE）每次握手重新生成，私钥泄露不危及历史流量 |
| 证书链验证 | 服务器证书→中间 CA→内置根 CA 逐级验签 + 域名/有效期检查 |
| HTTP/2 多路复用 | 二进制分帧+Stream ID，一条连接交错传多个请求，解决 HTTP 队头阻塞 |
| HTTP/2 帧结构 | 9 字节固定头：Length、Type、Flags、Stream ID + 变长载荷 |
| HTTP/2 Stream ID 规律 | 客户端发起用奇数，服务端推送用偶数 |
| HPACK 怎么压缩 | 静态表（61 项内置）+ 动态表（连接级缓存）+ Huffman 编码，压缩率 80%+ |
| HTTP/2 流量控制 | 连接级 + 流级两级窗口，WINDOW_UPDATE 帧扩容 |
| HTTP/2 推送为什么失败 | 与浏览器缓存冲突、重复推送浪费带宽；Chrome 已移除，用 103 Early Hints 替代 |
| HTTP/2 还有什么阻塞 | TCP 层队头阻塞：一个丢包所有 Stream 等重传 |
| HTTP/3 为什么用 UDP | QUIC 在用户态实现可靠传输+多路复用+0-RTT+连接迁移，绕开 TCP 层队头阻塞 |
| QUIC 怎么解决队头阻塞 | 交付单位是流不是字节流：丢包只堵一条流，其他流照常交付 |
| QUIC 握手几个 RTT | 首连 1-RTT（传输+TLS1.3 合并），会话恢复 0-RTT |
| 0-RTT 有什么风险 | 报文可被重放；只允许幂等请求走 0-RTT + 服务端去重 + 业务幂等 |
| 连接迁移 | QUIC 用 Connection ID 标识连接，网络切换（Wi-Fi→4G）不断连 |
| QUIC 包号为什么单调递增 | 重传用新包号，消除 TCP 重传二义性，RTT 计算更准（数据靠 Stream offset 定位） |
| QPACK vs HPACK | HPACK 要求全局有序会在 QUIC 下引入压缩队头阻塞；QPACK 用专用单向流同步压缩状态 |
| QUIC 为什么抗协议僵化 | 传输层头部也加密，中间设备看不见改不了，协议演进权收回端侧 |
| HTTP/3 落地难点 | 运营商 UDP 限速、用户态 CPU 开销高、UDP 收发包效率低；浏览器 H2/H3 竞速兜底 |
