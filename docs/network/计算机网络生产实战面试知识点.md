> 本文档聚焦计算机网络在分布式系统中的生产问题排查与架构实战。基础知识看 [`计算机网络面试知识点.md`](计算机网络面试知识点.md)，底层原理看 [`计算机网络原理机制面试知识点.md`](计算机网络原理机制面试知识点.md)。

## 一、网络排查命令工具箱（必背）

### 1.1 连通性与延迟排查

| 排查目标 | 命令 | 关键看点 |
|----------|------|----------|
| 网络通不通 | `ping <host>` | 丢包率、RTT（基于 ICMP，注意有些机器禁 ping） |
| 端口通不通 | `telnet <ip> <port>` / `nc -zv <ip> <port>` | 区分"网络不通"和"端口没监听" |
| 路由路径 | `mtr <host>`（ping+traceroute 结合） | 哪一跳丢包/延迟飙升，定位网络段问题 |
| DNS 解析 | `dig <domain>` / `nslookup <domain>` / `host` | 解析结果、TTL、各层级响应时间 |
| HTTP 层验证 | `curl -v <url>` | DNS 耗时、TCP 握手耗时、TLS 耗时、首字节时间（TTFB） |
| 接口耗时分解 | `curl -w "@curl-format.txt" -o /dev/null -s <url>` | time_namelookup / time_connect / time_starttransfer |

```bash
# 实用的 curl 耗时分解（curl-format.txt 内容）：
#     time_namelookup:  %{time_namelookup}s   -> DNS 解析耗时
#        time_connect:  %{time_connect}s     -> TCP 握手完成耗时
#     time_appconnect:  %{time_appconnect}s  -> TLS 握手完成耗时（HTTPS）
#   time_starttransfer:  %{time_starttransfer}s -> 收到首字节耗时（TTFB）
#          time_total:  %{time_total}s       -> 总耗时
```

### 1.2 连接状态与端口排查

| 排查目标 | 命令 | 关键看点 |
|----------|------|----------|
| 连接状态统计 | `ss -s` | 各状态连接数概览（timewait、estab 等） |
| 查看 TCP 连接 | `ss -antp` | 状态、收发队列（Recv-Q/Send-Q 堆积说明处理不过来）、进程 |
| 谁监听端口 | `ss -lntp` / `lsof -i :8080` | 端口冲突排查 |
| 某状态连接数 | `ss -ant \| awk '{print $1}' \| sort \| uniq -c` | TIME_WAIT/CLOSE_WAIT 是否堆积 |
| 网卡流量 | `sar -n DEV 1` / `iftop` / `nload` | 带宽是否打满、PPS |
| TCP 重传率 | `sar -n TCP,ETCP 1` | retrans/s 高 = 网络质量差 |
| 丢包统计 | `netstat -s \| grep -i retrans` | 重传段数、超时次数 |

### 1.3 抓包分析

```bash
# 抓指定主机和端口的包，写入文件供 Wireshark 分析
tcpdump -i eth0 host 10.0.0.1 and port 8080 -nn -w capture.pcap

# 只看 TCP 标志位（排查握手挥手问题）
tcpdump -i eth0 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0' -nn

# 抓 HTTP 请求内容（调试用，HTTPS 抓不到明文）
tcpdump -i eth0 port 80 -A -s 0
```

| 抓包关注点 | 说明 |
|------------|------|
| 三次握手是否成功 | SYN → SYN+ACK → ACK 缺哪一环，定位客户端/网络/服务端问题 |
| 谁发的 RST | RST 来源 = 谁拒绝了连接（端口没监听、全连接队列满、超时） |
| 重传报文 | 大量重传 = 网络丢包 |
| Window Size | 窗口长期很小 = 接收方处理慢 |
| TLS 握手 | 证书交换、协商版本/套件是否匹配 |

**Wireshark 实用过滤表达式：**
- `tcp.flags.syn==1` 只看握手；`tcp.analysis.retransmission` 看重传
- `tcp.stream eq 5` 跟踪某条连接；`http.response.code >= 400` 看错误响应

## 二、TCP 连接状态生产实战

### 2.1 TIME_WAIT 过多怎么治理？（高频实战题）

**现象：** `ss -s` 显示 timewait 几万甚至十几万，机器端口耗尽、新建连接失败（`Cannot assign requested address`）。

**先判断出现在哪一侧：**

| 场景 | 谁是主动关闭方 | 治理方向 |
|------|----------------|----------|
| 高并发短连接客户端（爬虫/压测机/网关调下游） | 客户端自己 | 客户端侧治理 |
| 服务端用短连接响应（HTTP/1.0、主动 close） | 服务端 | 改长连接为主 |

**治理手段（按优先级）：**

1. **治本：改短连接为长连接 / 连接池复用**——HTTP 开启 Keep-Alive、RPC 用长连接、DB 用连接池，连接复用了自然没有频繁挥手。
2. **让对端主动关闭**：TIME_WAIT 只出现在主动关闭方。例如 Nginx 反代场景配置 `proxy_http_version 1.1` + keepalive，由上游保持连接。
3. **客户端侧内核参数（谨慎使用）：**
   - `net.ipv4.tcp_tw_reuse = 1`：允许将 TIME_WAIT 状态的端口**用于新的出方向连接**（1 秒后可复用，配合 `tcp_timestamps` 保证安全），**对客户端有效，对服务端 listen 端口无效**。
   - `net.ipv4.ip_local_port_range`：扩大客户端可用端口范围。
   - **不要乱开 `tcp_tw_recycle`**：NAT 环境下同一出口 IP 的不同用户时间戳乱序，会导致连接被丢弃，Linux 4.12 已移除该参数。
4. **增加资源上限**：`ulimit -n`（fd 上限）、`net.ipv4.tcp_max_tw_buckets`（超过则直接销毁 TIME_WAIT，属于保底手段）。

**面试话术：**

> TIME_WAIT 是主动关闭方的正常状态，少量没有问题。治理思路是分层：先问"为什么有这么多短连接"——能改长连接/连接池就改，这是治本；客户端场景可以开 tcp_tw_reuse 复用端口、扩大端口范围；tcp_tw_recycle 在 NAT 环境会导致用户连不上，坚决不用。堆 TIME_WAIT 的本质是"建拆连接太频繁"，跟堆 GC 问题先看"为什么对象创建太多"是一个道理。

### 2.2 CLOSE_WAIT 过多怎么排查？

**现象：** CLOSE_WAIT 持续增长不下降。

**本质：** 对端已经关闭连接（发了 FIN），本端应用收到后**没有调用 close()**，连接泄漏。

**排查 SOP：**

```text
① ss -antp | grep CLOSE_WAIT      -> 看是本机哪个进程、连的哪个对端
② 确认对端角色                     -> 是 MySQL？Redis？下游 HTTP 服务？
③ 对照代码检查连接使用              -> 常见漏关闭场景：
   - HTTP 客户端 response 没 close（异常分支没走 finally/try-with-resources）
   - 连接池配置错误（如拿连接不复用不还）
   - 流式读取中断但没关连接
④ 修复后重启，观察 CLOSE_WAIT 是否回落
```

### 2.3 Connection Reset（RST）常见原因

线上日志常见 `Connection reset by peer` / `Broken pipe`，RST 的常见来源：

| 场景 | 原因 |
|------|------|
| 连到没监听的端口 | 内核直接回 RST |
| 全连接队列满 | 见 [`计算机网络原理机制面试知识点.md`](计算机网络原理机制面试知识点.md) |
| 对端进程崩溃/强杀 | 未走的连接被内核 RST |
| 向已关闭的连接写数据 | 对端已 close，再写就 RST（Broken pipe 是写了 RST 之后再写） |
| 连接空闲太久被中间设备回收 | NAT/防火墙会话超时（常见 5~30 分钟），之后发包收到 RST → **这就是应用层心跳存在的意义** |
| 读缓冲区还有数据时 close | 内核认为有未读数据被丢弃，发 RST 而非正常 FIN |

## 三、超时与重试体系（分布式经典问题）

### 3.1 超时设置的层次（必考）

一次 RPC/HTTP 调用涉及的超时层次：

```text
业务超时（整个调用链预算，如 800ms）
   └─ RPC/HTTP 客户端超时（如 500ms）
        ├─ 连接超时 ConnectTimeout（建 TCP，如 200ms）
        ├─ 读超时 ReadTimeout（等响应，如 450ms）
        └─ 写超时 WriteTimeout
   └─ 线程池等待超时 / 信号量超时
   └─ 网关超时（如 Nginx proxy_read_timeout 60s）
   └─ DB 超时（socketTimeout、query 超时）
```

**黄金法则：**
- **超时必设**：不设超时的客户端 = 把线程池拖死的定时炸弹（下游挂了 → 本服务线程全部阻塞在 read → 服务雪崩）。
- **外层超时 > 内层超时**：调用方超时要大于被调方的处理超时，否则"上游已放弃，下游还在算"白耗资源。
- **全链路超时预算**：入口 800ms 预算，调 A 花 300、调 B 花 300，剩下给 C 的只有 200——预算要逐级扣减传递（gRPC 的 deadline 机制）。

### 3.2 重试的正确姿势（高频）

| 问题 | 错误做法 | 正确做法 |
|------|----------|----------|
| 重试次数 | 无限重试 | 一般 2~3 次，且区分错误类型（连接超时可重试，业务错误不重试） |
| 重试间隔 | 立即重试（打爆下游） | **指数退避**（100ms、200ms、400ms）+ **随机抖动**（防惊群） |
| 幂等性 | 不管接口性质直接重试 | 非幂等接口（下单/扣款）重试前先做幂等设计：唯一请求号、防重表、状态机 |
| 重试风暴 | 每层都重试 3 次 = 放大 3^n 倍 | **只在最靠近调用源头的一层重试**，或全链路约定总重试预算 |

**面试话术（重试风暴）：**

> 一次用户请求链路 A→B→C，如果每层都配置重试 3 次，C 抖动一次最底层会收到 3×3=9 倍流量，可能直接把 C 打挂——这就是重试风暴，是雪崩的常见放大器。治理：只在一层重试（通常是入口或客户端 SDK）、重试加指数退避和抖动、非幂等接口禁止盲目重试、配合熔断器（失败率超阈值直接快速失败，不再放流量过去）。

### 3.3 超时相关的经典线上问题

| 现象 | 根因 | 解法 |
|------|------|------|
| 偶发大量超时但下游监控正常 | **TCP 重传**：丢包后 RTO 最小 200ms，跨机房链路偶发丢包 | 抓包看重传；调 `tcp_retries2`；客户端超时不要太短 |
| 连接池获取连接超时 | 池子太小 / 连接泄漏没还 / 下游慢导致占用时间变长 | `pool exhausted` 先查是不是下游 RT 变长 |
| 高峰期超时集中爆发 | 下游容量不足，排队导致 RT 飙升 | 限流、扩容、降级 |
| 明明设了超时线程还是堆满 | 超时只覆盖 read，没覆盖连接池排队/序列化/DNS | 全链路梳理超时点 |

## 四、HTTP 连接池实战

### 4.1 为什么需要连接池？

每次 HTTP 调用都新建 TCP 连接的代价：**三次握手 1 RTT + TLS 握手 1~2 RTT**，跨机房场景一次调用光建连就要几十上百 ms。连接池复用长连接，调用时直接拿现成连接发数据。

### 4.2 连接池核心参数（以 Apache HttpClient / OkHttp 为例）

| 参数 | 作用 | 常见坑 |
|------|------|--------|
| maxTotal | 池最大连接数 | 太小：高峰期排队；太大：下游被打爆 |
| maxPerRoute | 单域名最大连接数 | **默认往往很小（如 2~5）**，只调一个下游时必须调大 |
| connectTimeout | 建连超时 | 不设 = 死等 |
| readTimeout/socketTimeout | 读响应超时 | 不设 = 线程堆积雪崩 |
| connectionRequestTimeout | 从池里拿连接的超时 | 和 readTimeout 是两回事 |
| keepAliveDuration / timeToLive | 连接空闲多久回收 | **必须比对端/中间设备的空闲超时短** |

### 4.3 经典坑：连接复用 vs 对端空闲超时（生产事故高发）

**事故模型：**

```text
服务端空闲超时 30s（到点主动 FIN 关连接）
客户端连接池 keepAlive 60s（以为连接还能用）
        │
30s 时服务端 FIN，但 FIN 报文丢失 / 被中间设备吞了 / 客户端没及时处理
        │
40s 时客户端从池里拿出这条"死连接"发请求
        │
收到 RST → IOException: Connection reset → 偶发诡异报错（低峰期尤其多）
```

**解法（三管齐下）：**
1. 客户端连接的 keepAlive 时间**小于**服务端/中间设备的空闲超时（如服务端 60s，客户端设 50s），让客户端先主动回收。
2. 客户端发请求前**校验连接活性**（stale connection check，有轻微性能成本）或对幂等请求允许重试。
3. 对偶发的 `Connection reset` 类异常，对**幂等请求做一次自动重试**。

> 面试加分句：这类问题在低峰期更高发（连接在池里躺得久），高峰期反而复用率高遇不到——所以"低流量时段偶发报错"要优先怀疑连接复用问题。

## 五、负载均衡与反向代理

### 5.1 四层 vs 七层负载均衡（必考）

| 对比项 | 四层（L4） | 七层（L7） |
|--------|------------|------------|
| 工作层次 | 传输层（IP+端口） | 应用层（HTTP 头、URL、Cookie） |
| 典型实现 | **LVS**、F5、NLB | **Nginx**、HAProxy、API 网关、ALB |
| 性能 | 极高（直接转发报文，DR 模式回程不过 LB） | 较低（要解析协议、建两条 TCP 连接） |
| 功能 | 只按 IP/端口转发 | URL 路由、灰度、限流、鉴权、改写 |
| 典型组合 | LVS 在最前面扛流量 → 后面挂 Nginx 集群做七层 | —— |

### 5.2 常见负载均衡算法

| 算法 | 原理 | 适用场景 |
|------|------|----------|
| 轮询（Round Robin） | 依次分配 | 节点性能均等 |
| 加权轮询 | 按权重分配 | 节点性能不均 |
| 最少连接 | 给当前连接数最少的节点 | 长连接、请求耗时不均 |
| 一致性 Hash | 相同 key 路由到相同节点 | 缓存亲和、会话亲和；节点上下线只影响小部分 key |
| 源 IP Hash | 按客户端 IP 固定路由 | 简单会话保持（注意 NAT 后大量用户同 IP） |

### 5.3 Nginx 反向代理生产配置要点

```nginx
upstream backend {
    server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;  # 被动健康检查：30s 内失败 3 次摘除
    server 10.0.0.2:8080;
    keepalive 32;                      # 与上游保持长连接，避免反复握手 + 减少 TIME_WAIT
}
server {
    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;        # 配合上游 keepalive 必须用 1.1
        proxy_set_header Connection "";# 清除 Connection 头，启用长连接
        proxy_connect_timeout 2s;      # 连上游超时
        proxy_read_timeout 10s;        # 等上游响应超时
        proxy_next_upstream error timeout http_502;  # 这些失败换下一台上游重试
    }
}
```

**生产关注点：**
- **被动摘除 vs 主动探测**：开源 Nginx 只有被动健康检查（max_fails），主动探测需要 nginx-plus 或 Tengine/自研网关。
- `proxy_next_upstream` 要谨慎：**非幂等 POST 默认不重试**，避免重复下单。
- 网关超时（如 60s）要大于上游接口 P99，小于客户端可忍受时间。

### 5.4 客户端负载均衡 vs 服务端负载均衡

| 对比项 | 服务端 LB（Nginx/LVS） | 客户端 LB（Ribbon/Dubbo/gRPC LB） |
|--------|------------------------|-----------------------------------|
| 负载决策位置 | 集中式中间设备 | 每个调用方进程内 |
| 服务发现 | 不感知，静态配置/动态 upstream | 从注册中心（Nacos/ZK）拉节点列表 |
| 单点/瓶颈 | LB 自身要高可用 | 无中间跳点，少一跳延迟 |
| 典型场景 | 入口流量（南北向） | 微服务间调用（东西向） |

## 六、DNS 与 CDN 实战

### 6.1 DNS 生产问题

| 问题 | 说明 | 解法 |
|------|------|------|
| DNS 劫持/污染 | 运营商/恶意节点返回假 IP（弹广告、钓鱼） | HTTPDNS（绕开本地 DNS，走 HTTP 接口拿 IP）、DoH/DoT |
| TTL 与容灾的矛盾 | TTL 太长：故障切换慢；太短：解析压力大 | 核心域名 TTL 设 1~5 分钟；变更前提前调小 TTL |
| 本地 DNS 不准 | 用户跨网访问（联通用户拿到电信 IP） | HTTPDNS 按真实出口 IP 调度 |
| JVM 的 DNS 缓存 | JVM 默认**永久缓存**解析结果（security 配置），域名切 IP 后不生效 | 设置 `networkaddress.cache.ttl=30` 或注意连接池复用下的解析时机 |

### 6.2 CDN 工作原理（一张图说清）

```text
用户 → 本地 DNS → 权威 DNS（CNAME 到 CDN 厂商）
                     │
              CDN GSLB 智能调度（按地域/运营商/节点负载）
                     │
              返回最近的边缘节点 IP
                     │
用户 → 边缘节点：缓存命中 → 直接返回（静态资源秒开）
              │ 未命中
              ▼
       回源：边缘节点 →（可能经过父节点/中间源）→ 源站拉取 → 缓存并返回
```

**面试关注点：**
- **CNAME 是 CDN 接入的关键**：域名 CNAME 到 CDN 厂商域名，调度权交给 CDN。
- **命中率是核心指标**：合理的 Cache-Control、URL 去参（忽略无关 query）、预热（大文件提前推送到边缘）。
- **动态加速（DCDN）**：动态内容不缓存，但走 CDN 的优化链路（就近接入 + 骨干网回源 + TCP 优化），见项目中的 [`../腾讯云EdgeOne_DCDN域名监控调研.md`](../腾讯云EdgeOne_DCDN域名监控调研.md)。

## 七、网络架构演进与面试串联

### 7.1 一次请求在网络架构中的旅程（架构图）

```text
用户
  │  ① DNS/HTTPDNS 解析
  ▼
CDN 边缘节点（静态资源命中直接返回）
  │  ② 回源（动态请求）
  ▼
SLB / LVS（四层，扛大流量）
  │
  ▼
Nginx / API 网关（七层：SSL 卸载、限流、鉴权、路由、灰度）
  │
  ▼
微服务（客户端 LB + 注册中心，服务间 RPC 长连接）
  │
  ├─► Redis（TCP，RESP 协议）
  ├─► MySQL（TCP，连接池）
  └─► MQ（TCP 长连接 + 零拷贝）
```

**每一层都有网络考点：**
- CDN：DNS 调度、缓存、回源超时
- LB：四层 vs 七层、健康检查、会话保持
- 网关：TLS 卸载（证书终结在网关，内网走 HTTP）、超时重试
- 微服务：RPC 连接池、序列化、心跳保活
- 存储：连接池打满、慢查询拖垮

### 7.2 高频场景问答模板

**Q：用户反馈页面打开慢，你怎么排查？**

> 分层定位：先用 `curl -w` 分解耗时——DNS 慢查解析；TCP 握手慢查网络和 LB；TTFB 慢说明服务端处理慢（继续看应用监控：DB 慢查询、下游 RPC 慢）；下载慢查带宽和 CDN 命中率。多个用户同时反馈看是不是某个地域/运营商的问题（CDN 节点故障、运营商线路抖动）。服务端侧配合 `ss -s` 看连接状态、`sar -n TCP` 看重传率。

**Q：大促前网络层要做哪些准备？**

> ①容量评估：LB 带宽、连接数上限（fd、somaxconn、端口范围）；②参数调优：TIME_WAIT 治理（长连接复用、tw_reuse）、全连接队列 backlog；③超时重试梳理：全链路超时预算、去掉多层重试；④依赖梳理：CDN 预热、DNS TTL 提前调小便于切换；⑤预案：限流降级开关、网关一键切流。

## 八、生产实战高频问题速记

| 问题 | 一句话答案 |
|------|------------|
| 端口不通怎么查 | ping（网络层）→ telnet/nc（传输层）→ ss -lnt（确认监听）→ curl（应用层） |
| TIME_WAIT 过多 | 治本：短连接改长连接/连接池；客户端：tw_reuse + 扩端口范围；禁用 tw_recycle |
| 谁会产生 TIME_WAIT | 主动关闭连接的一方 |
| CLOSE_WAIT 过多 | 应用收到 FIN 后没 close()，代码 Bug，ss 定位进程和对端 |
| 偶发 Connection reset | 池里的连接被对端/中间设备超时关了；keepAlive 要比对端短 + 幂等重试 |
| 超时怎么设 | 必设；外层 > 内层；全链路预算逐级扣减 |
| 重试注意什么 | 指数退避+抖动；只在一层重试防风暴；非幂等接口先幂等设计 |
| 连接池 maxPerRoute | 只调一个下游时必须调大，默认很小是坑 |
| 四层 vs 七层 LB | LVS 按 IP+端口转发性能高；Nginx 按 URL/Header 路由功能强；常组合使用 |
| Nginx 与上游 TIME_WAIT | `keepalive` + `proxy_http_version 1.1` + 清 Connection 头，复用长连接 |
| DNS 变更不生效 | JVM 永久缓存 DNS（networkaddress.cache.ttl）、TTL 未到期、本地 DNS 缓存 |
| 抓包看握手 | tcpdump 抓 tcpflags，缺 SYN+ACK 查服务端/网络，缺 ACK 查客户端/全连接队列 |
| 页面慢怎么定位 | curl -w 分解 DNS/握手/TTFB/下载各段耗时，逐段归因 |
| 网关 502/504 | 502 上游挂了或返回非法；504 上游超时——查上游健康和 RT |

**面试话术示例（被问"为什么 RPC 比 HTTP 快"时把网络讲进去）：**

> 核心差距不在协议魔法而在开销控制：RPC 框架用 TCP 长连接 + 连接池，省掉了每次调用的三次握手和 TLS 握手开销；用紧凑的二进制序列化（Protobuf/Hessian）替代 HTTP 文本报文，报文体积和解析成本都更小；头部没有 HTTP 那么多冗余字段。但反过来说，HTTP/2 之后多路复用、头部压缩补齐了很多短板，所以现在的差距主要在序列化效率和治理生态，选型时不能简单说"RPC 一定比 HTTP 快"。
