# 自定义传输层协议设计指南

> 本文从工程实践角度说明：如果需要自行设计传输层协议，应如何确定服务语义、设计报文与状态机，并处理可靠性、流量控制、拥塞控制、安全、网络兼容性和可运维性等问题。除非存在明确业务诉求，生产环境应优先采用 TCP、TLS、QUIC、HTTP/2 或 HTTP/3 等成熟协议；自定义协议的成本主要在于长期兼容、调优和安全维护，而不是“把数据发出去”。

---

## 一、先定义服务模型，而不是先设计报文

传输层协议是建立在不可靠网络之上的通信约定。设计前必须先写清楚它向应用提供什么**交付语义**，否则可靠性、延迟和复杂度没有可验证的边界。

### 1.1 关键设计问题

| 问题 | 可选设计 | 影响 |
|------|----------|------|
| 是否可靠交付 | 尽力而为、可靠、部分可靠 | 决定是否需要 ACK、重传、接收缓存 |
| 是否有序交付 | 全连接有序、按流有序、无序 | 决定乱序缓存与队头阻塞行为 |
| 数据抽象 | 字节流、保消息边界的消息、多个流 | 决定应用 API、分帧及重组规则 |
| 延迟与吞吐优先级 | 低延迟、高吞吐、平衡 | 决定确认策略、聚合、重传和拥塞算法 |
| 是否支持多路复用 | 单逻辑流、连接内多 Stream | 决定流标识、流级流控、优先级 |
| 连接形态 | 无连接、面向连接、可迁移连接 | 决定握手、状态管理、NAT 适配 |
| 安全边界 | 仅校验、认证、端到端加密 | 决定密钥交换、报文保护、重放防护 |

### 1.2 常见场景的取舍

| 场景 | 推荐语义 | 原因 |
|------|----------|------|
| 文件、订单、数据库复制 | 可靠、有序、可恢复 | 少量错误会造成业务数据不一致 |
| RPC / Web 请求 | 可靠、按流有序、多路复用 | 请求需要完整响应，连接复用可降低握手成本 |
| 实时音视频 | 部分可靠、允许无序或过期丢弃 | 迟到的视频帧通常比丢失更没有价值 |
| 在线游戏状态同步 | 关键消息可靠；位置等状态可丢弃旧值 | 优先保证实时性，避免历史状态阻塞当前状态 |
| 遥测、日志 | 可按重要级别区分可靠性 | 在网络异常时优先保留关键事件 |

**原则：** 可靠、有序、低延迟、高吞吐、低 CPU 和低内存不能同时无限制满足。协议必须显式规定优先级和降级策略。

## 二、选择承载方式与协议边界

### 2.1 基于 TCP、UDP 还是 QUIC

| 承载方式 | 适用情况 | 主要优点 | 主要限制 |
|----------|----------|----------|----------|
| TCP | 普通可靠字节流业务 | 成熟、兼容性好、内核实现完善 | 固有字节流语义；单连接存在传输层队头阻塞 |
| TCP + TLS | 需要安全的可靠传输 | 安全性与生态成熟 | 连接迁移、多流隔离能力有限 |
| UDP | 需要自定义交付语义或极低延迟 | 无连接、保留消息边界、实现自由度高 | 可靠性、拥塞控制、防攻击均需自行完成 |
| QUIC | Web、多路复用、弱网与移动网络 | TLS 1.3 集成、多流、连接迁移、用户态迭代 | 实现复杂；部分网络可能限制 UDP |

若业务只需要“可靠安全地传一个请求”，通常不应重复实现 TCP/QUIC 已解决的问题。更合理的做法是基于成熟承载层，在应用层设计消息帧和业务语义。

### 2.2 明确分层职责

建议按层划分，避免协议把业务逻辑、传输控制和安全机制混在一起：

```text
应用层：请求、响应、业务错误码、幂等键、业务压缩
会话层：认证上下文、Stream、优先级、会话恢复
传输层：编号、确认、重传、流控、拥塞控制、连接生命周期
安全层：密钥协商、加密、完整性、重放防护、密钥更新
网络层：IP 路由、MTU、NAT、防火墙、中间网络设备
```

## 三、报文与帧格式设计

报文格式既是协议的“公开接口”，也是后续兼容的基础。必须明确字节序、字段长度、字段合法范围、未知字段的处理方式及最大包长。

### 3.1 一个可扩展的逻辑帧结构

```text
+----------------+----------------------------------------------+
| 字段           | 说明                                         |
+----------------+----------------------------------------------+
| Version        | 协议主版本或版本协商信息                     |
| Packet Type    | Initial / Data / ACK / Close / Reset 等      |
| Flags          | 加密、确认、探测、结束流等标志               |
| Connection ID  | 逻辑连接标识，用于迁移和负载均衡路由         |
| Packet Number  | 单调递增的包号，用于确认、丢失检测和防重放   |
| Stream ID      | 多路复用时标识逻辑流                         |
| Offset         | 某流内数据偏移量，用于重组                   |
| Length         | 载荷或帧长度，必须校验上限                   |
| Flow Control   | 接收窗口或最大可接收偏移                     |
| ACK Ranges     | 已接收包号区间，用于选择确认                 |
| Payload        | 应用数据或控制帧内容                         |
| Auth Tag       | 加密认证标签，防篡改和伪造                   |
+----------------+----------------------------------------------+
```

并非每个包都应携带所有字段。实际实现中可将公共头、长头、短头和不同类型帧拆开，以减少数据包开销。

### 3.2 字段设计的注意事项

1. **长度必须先校验再分配内存。** 不可信网络输入中的 `Length` 不能直接用于数组、缓冲区或解压操作，否则会产生内存耗尽与整数溢出漏洞。
2. **序列号与包号需考虑回绕。** 可使用足够宽的单调递增整数；若会回绕，必须严格规定模运算下的大小比较规则。
3. **变长字段要有上限。** 防止畸形包造成超长解析、递归解析或 CPU 消耗。
4. **未知扩展应可跳过。** 扩展帧可采用 `type + length + value` 编码；未知且非关键帧可跳过，未知关键帧应拒绝连接或协商降级。
5. **不要把地址信息当作唯一连接身份。** 四元组会因 NAT 重绑定或移动网络切换而变化；需要迁移时应使用独立的 `Connection ID`。
6. **统一网络字节序和错误码。** 文档要明确定义多字节整数编码、字符集、错误码类别和关闭原因。

### 3.3 消息边界与分片

TCP 提供字节流，不保留发送端的 `write()` 边界；自定义消息协议必须使用长度前缀、分隔符或固定长度帧定义边界。若协议基于 UDP，虽然 UDP 保留单个数据报边界，仍要处理应用消息大于路径 MTU 的情况。

推荐做法：

- 在传输层或会话层对大消息切片；
- 以 `Stream ID + Offset + Length` 进行重组；
- 单片丢失时只重传该片，而不是重传整个消息；
- 限制单消息大小、乱序重组缓存和未完成消息数量；
- 尽量避免依赖 IP 分片，因为任一分片丢失都会使整个 IP 包失效，且部分网络会直接丢弃分片流量。

## 四、连接建立、协商与状态机

### 4.1 握手需要解决什么问题

面向连接协议的握手至少应完成：

1. 确认双方具备收发能力；
2. 协商协议版本、加密套件、最大包大小、初始流量窗口和扩展能力；
3. 为本次连接建立不可预测的连接标识、初始包号或密钥材料；
4. 验证客户端地址的可达性，避免服务端被伪造源地址消耗资源或利用为反射放大器；
5. 明确失败、超时、重试和版本不兼容时的行为。

### 4.2 一个简化的状态机

```text
客户端：IDLE → INITIAL_SENT → HANDSHAKING → ESTABLISHED → DRAINING → CLOSED
服务端：IDLE → INITIAL_RECEIVED → VALIDATING → HANDSHAKING → ESTABLISHED
                                                     ↓
                                                   CLOSED
```

状态机文档应逐项列明：每个状态允许接收哪些帧、收到非法帧是忽略还是关闭、状态超时多久、资源何时释放。不能只描述正常流程；异常报文、重复报文、乱序报文和超时报文更容易产生线上故障与安全漏洞。

### 4.3 初始编号与旧包隔离

初始序列号、包号空间或连接 ID 必须具备足够随机性和唯一性，以降低以下风险：

- 历史连接的延迟包被误认为新连接数据；
- 攻击者猜测编号后伪造确认或注入数据；
- 会话恢复或连接迁移时不同路径的旧包混入。

### 4.4 地址验证与抗状态耗尽

如果服务端收到第一个请求就创建完整连接对象、分配大缓冲区或执行昂贵密码学计算，攻击者可伪造大量源地址请求消耗资源。

可采用：

- **Retry Token / Cookie：** 服务端将经过认证的、带有效期的令牌发给客户端；客户端回传令牌前，服务端保持最少状态。
- **未验证地址前限制响应：** 服务端在确认对端能收到包前，发送的字节数不应显著大于接收字节数，避免反射放大攻击。
- **分级限流与配额：** 按源地址、账号、连接 ID、网段等维度限制建连频率和并发量。
- **推迟昂贵操作：** 地址验证成功后再做大内存分配、证书验证或复杂业务初始化。

## 五、可靠传输：确认、乱序、丢包与重传

可靠交付至少意味着：接收方能发现数据缺失、重复和乱序；发送方能知道哪些数据已被确认；丢失的数据能在合理时间内重传；两端不会因为无限缓存而耗尽资源。

### 5.1 编号与确认

常见两种编号模型：

- **字节偏移编号：** 类似 TCP。每个字节在逻辑流中有位置，适合连续字节流。
- **包号 + 流偏移：** 类似 QUIC。包号用于确认、丢失检测和 RTT 测量；流内 offset 用于识别数据位置。重传的数据放进新包并使用新包号，可避免“一个包号对应原包还是重传包”的歧义。

确认方式包括：

| 方式 | 含义 | 特点 |
|------|------|------|
| 累计 ACK | 确认某编号之前的连续数据均已收到 | 开销小，但无法准确表达中间缺失后的已收数据 |
| 选择确认 SACK / ACK Range | 报告多个已收到区间 | 能减少不必要重传，适合乱序与高带宽网络 |
| 延迟 ACK | 稍等一小段时间后批量确认 | 减少 ACK 包，但会增加交付与丢失恢复延迟 |

ACK 本身也可能丢失。只要后续 ACK 覆盖了已确认范围，通常无需专门重传 ACK；但协议必须限制 ACK 频率，防止确认风暴。

### 5.2 接收窗口与乱序缓存

接收端应维护一个有限窗口：

- 已连续收到的数据可立即交付上层；
- 窗口内但不连续的数据暂存，等待缺口补齐；
- 过旧数据通常视为重复并丢弃；
- 远超窗口的数据应丢弃或触发受控错误；
- 每连接、每流、全局都需有内存上限与超时清理机制。

若应用允许部分可靠或无序消费，可以将“收到”与“交付”分开：控制消息仍保持顺序，过期的媒体帧则可直接丢弃，避免旧数据永久阻塞新数据。

### 5.3 RTT 与重传超时（RTO）

固定重传超时会在不同网络中表现很差：值太小会误重传，值太大会在真实丢包时恢复过慢。应根据往返时间 RTT 的平滑估计和波动估计动态得到 RTO，并设置最小、最大阈值。

```text
发送数据 → 收到对应 ACK → 采样 RTT → 更新平滑 RTT 与抖动 → 计算 RTO
```

关键规则：

- 重传后收到的 ACK 难以判断对应原包还是重传包，传统实现通常不拿这类样本更新 RTT；
- 超时后应进行指数退避，避免网络已拥塞时继续增加发送压力；
- RTO 只是兜底机制，主要丢包恢复应尽量依赖快速丢失检测。

### 5.4 快速重传与丢失判定

若接收方反复确认较新的包而某个较早包持续未确认，发送方可推断中间包很可能丢失，并提前重传，不必等待 RTO。

在采用包号的协议中，通常可结合两类信号判定丢失：

1. **报文阈值：** 已有足够多更新包被确认，而旧包仍未确认；
2. **时间阈值：** 某包发送后超过与 RTT 相关的时间仍未确认。

阈值不可过激，否则乱序会被误判为丢包，导致无效重传；也不可过保守，否则恢复延迟会很高。

## 六、流量控制：保护接收端与应用

流量控制解决的是“发送端速度超过接收端处理能力”的问题。接收端可通告剩余接收能力 `rwnd`，发送端未确认在途数据不能超过该限制。

```text
允许发送的在途数据 ≤ min(接收窗口 rwnd, 拥塞窗口 cwnd)
```

### 6.1 建议使用双层流控

多流协议至少要区分：

- **连接级窗口：** 防止所有流合计占满接收端内存；
- **流级窗口：** 防止单一流垄断缓冲区，影响其他流。

窗口更新应表示“允许发送到的最大偏移量”或“新增可用额度”，并保证更新不会因乱序、重复或旧包而倒退。

### 6.2 零窗口与背压

当接收端缓冲区满时可以通告零窗口。发送端需要停止发送新数据，但不能永远沉默：应以受控频率发送窗口探测，防止窗口恢复通知丢失后形成死锁。

真正健康的系统还要让背压传递到应用层：网络缓冲积压时，应限制应用继续无界写入，而不是仅在协议层无限排队。

## 七、拥塞控制：保护共享网络

流量控制保护接收端；**拥塞控制保护网络路径及其他连接**。没有拥塞控制的 UDP 自定义协议在高负载下会制造大量排队、丢包和重传，最终导致拥塞崩溃，也会不公平地抢占 TCP/QUIC 的带宽。

### 7.1 基本能力

协议应具备：

1. **慢启动：** 初始发送窗口较小，通过 ACK 逐渐探测可用带宽；
2. **拥塞避免：** 接近容量后降低增长速度；
3. **拥塞响应：** 丢包、ECN 标记或持续 RTT 上升时降低发送速率；
4. **快速恢复：** 对非超时丢包进行温和恢复，避免完全回到起点；
5. **Pacing：** 将一个窗口内的数据按节奏平滑发送，避免微突发撑爆交换机队列；
6. **公平性：** 在共享链路中不应长期以不合理方式压制标准 TCP/QUIC 流。

### 7.2 丢包不是唯一拥塞信号

传统算法常以丢包作为主要拥塞信号；但在 Wi-Fi、蜂窝网络中，丢包也可能由无线误码导致。可结合：

- RTT 持续增长，作为排队延迟信号；
- ECN（显式拥塞通知），由网络设备在拥塞时打标而不是丢包；
- 瓶颈带宽和最小 RTT 的测量结果。

无论选择何种算法，都要在真实弱网、突发流量和混合 TCP/QUIC 环境中验证，而非只使用实验室吞吐结果。

## 八、多路复用、队头阻塞与调度

### 8.1 为什么需要 Stream

单一可靠有序字节流中，较早数据缺失时，后面的数据即使已经到达也不能按序交付，这称为队头阻塞（Head-of-Line Blocking）。

多 Stream 方案将连接拆成多个逻辑流：每条流独立编号、重组和交付；某流的丢包只阻塞该流，不阻塞其他已完整的流。连接仍可共享安全上下文和拥塞控制。

### 8.2 Stream 设计点

需要明确定义：

- `Stream ID` 的分配规则及最大并发流数；
- 双向流、单向流的语义；
- 每流独立的顺序、流控和关闭状态；
- 取消、重置、超时、优先级和依赖关系；
- 防止对端创建海量空流造成状态耗尽；
- 调度策略：控制帧、交互流、批量流在拥塞窗口有限时谁优先。

多流只能避免**应用数据交付层面**的相互阻塞；它不能让总带宽无限增加。所有流共享路径容量和连接级拥塞窗口。

## 九、安全设计

安全不能作为“传输完成后再加的一层”。一旦协议上线，修改握手和报文格式的成本极高。

### 9.1 基础安全目标

| 目标 | 防护的问题 | 常见机制 |
|------|------------|----------|
| 机密性 | 被动窃听 | AEAD 加密 |
| 完整性 | 报文被篡改 | 认证标签 / MAC |
| 对端认证 | 连接到伪造服务端或客户端 | 证书、公钥、预共享密钥 |
| 防重放 | 旧请求被重复执行 | 包号、nonce、重放窗口、幂等设计 |
| 前向安全 | 长期私钥泄露导致历史流量泄露 | 临时密钥交换，如 ECDHE |
| 密钥更新 | 长连接密钥长期使用 | 定期或按数据量轮换密钥 |

建议使用成熟 TLS 1.3 或成熟密码库，不应自行设计加密算法、nonce 构造或密钥派生函数。

### 9.2 0-RTT 的风险

会话恢复中的 0-RTT 可降低首包延迟，但早期数据可能被攻击者复制并重放。它只应承载满足以下条件的请求：

- 业务天然幂等，例如读取或查询；
- 服务端可按幂等键去重；
- 即使被重放也不会产生资金、库存、权限或状态变更副作用。

下单、扣款、发券、修改权限等操作不应仅依赖 0-RTT 保护。

### 9.3 解析与资源安全

必须把所有网络输入视为不可信：

- 检查长度、范围、状态合法性和帧组合关系；
- 对解压、解密、重组、错误响应设置 CPU 与内存配额；
- 不在错误回包中泄露内部状态、密钥材料或详细栈信息；
- 对畸形包、认证失败和无效 token 限速；
- 连接关闭后进入有限的 draining 期，处理迟到包但不无限保留状态。

## 十、MTU、NAT、中间盒与连接迁移

### 10.1 MTU 与路径 MTU

实际可发送包大小取决于整条路径中最小 MTU，而不是本机网卡 MTU。过大的包可能导致分片或被丢弃。

设计要求：

- 探测并缓存 Path MTU（PMTU），在路径变化时重新评估；
- 预留 IP、UDP/TCP、加密和协议头的开销；
- 单个 UDP 数据报不要超过已确认的安全大小；
- 正确处理“需要分片但禁止分片”等 ICMP 反馈，同时避免完全依赖可能被过滤的 ICMP；
- 分片和重组必须受内存、超时和数量限制保护。

### 10.2 NAT 与保活

NAT 或防火墙会维护映射表项，空闲一段时间后可能删除映射。需要长连接时可使用保活，但保活间隔应在连接存活性、移动端耗电、网络成本与 NAT 超时之间权衡。

不要把“发送成功”误认为“对端仍在线”。UDP 尤其需要应用层 ACK、心跳或探测来确认路径可用。

### 10.3 连接迁移

移动端从 Wi-Fi 切换到蜂窝网络时，IP 与端口可能变化。若协议以独立 `Connection ID` 标识会话，可支持迁移，但必须：

1. 在新路径上执行挑战—响应验证，确认新地址真实可达；
2. 未验证前限制向新地址发送的流量，防止被利用反射；
3. 按新路径重新探测 RTT、PMTU 和拥塞状态；
4. 防止攻击者伪造地址变化劫持会话。

### 10.4 负载均衡部署

服务端集群需要让同一连接稳定落到能处理其状态的实例。可依据 `Connection ID` 做一致性哈希或在共享会话层维护路由。迁移、扩缩容和后端重启时还需考虑连接状态转移、优雅下线与客户端重连策略。

## 十一、关闭、异常与恢复语义

协议应区分以下情况：

| 类型 | 含义 | 处理要点 |
|------|------|----------|
| 正常关闭 | 双方已完成发送并确认必要数据 | 支持半关闭，明确尾部数据是否已交付 |
| 流关闭 | 一个 Stream 不再发送或接收 | 不应影响连接内其他流 |
| 重置 | 立即中止，未确认数据可能丢失 | 给上层明确错误码，及时回收资源 |
| 空闲超时 | 长期无有效通信 | 通过保活/探测判断，避免误杀活连接 |
| 网络切换 | 路径失效而非会话失效 | 尝试迁移或受控重连 |
| 服务端重启 | 会话状态丢失或密钥变更 | 客户端应识别错误并进行幂等重试或恢复 |

特别需要明确“发送成功”的定义：数据进入本地缓冲区、发到网卡、收到传输层 ACK、被对端应用消费，分别代表不同层级的成功。涉及金融、消息投递等场景时，仍需要业务层幂等键、去重与事务语义，传输层 ACK 不能替代业务确认。

---

## 十二、版本演进与兼容性

协议发布后会经过多版本客户端、服务端、代理和网络设备长期共存。第一版就应具备演进机制：

- 版本协商与版本拒绝；
- 扩展帧和能力协商；
- 关键扩展与可忽略扩展的明确区分；
- 特性灰度开关、回滚路径和兼容窗口；
- 旧版本的弃用计划；
- 对未知字段、重复字段、字段顺序的严格且安全的解析规则。

现实网络存在 NAT、防火墙、DPI、代理和负载均衡等中间盒。新协议应在家庭宽带、企业网、移动网、跨境链路等环境做兼容性验证，并提供降级方案，例如在 UDP 被阻断时回退到 TCP/TLS。

---

## 十三、可观测性、调试与运维

没有观测能力的自定义协议在弱网问题出现时几乎无法定位。建议按连接、路径、流和错误类别暴露指标。

### 13.1 推荐指标

- 建连总量、成功率、握手耗时、失败阶段与错误码；
- 活跃连接数、连接时长、空闲超时、迁移次数；
- RTT、最小 RTT、抖动、路径 MTU；
- 发送/接收字节数、有效载荷比例、吞吐量；
- 丢包率、乱序率、重复包率、重传率、RTO 次数；
- `cwnd`、`rwnd`、流控阻塞时间、拥塞阻塞时间；
- 每连接和每流的缓冲区占用、丢弃次数；
- 认证失败、重放拦截、地址验证失败、限流命中；
- 版本、扩展能力和网络类型的分布。

### 13.2 调试原则

- 为每个连接、流和关闭事件提供可关联的匿名标识；
- 记录状态迁移和关键控制事件，不记录明文敏感数据、会话密钥或完整认证令牌；
- 高并发环境采用采样、聚合与分级日志，避免日志本身拖垮服务；
- 错误码应稳定、分层、可统计：例如解析错误、认证错误、流控错误、拥塞错误、版本错误、应用错误。

---

## 十四、测试清单

自定义传输协议不能仅依赖单元测试，必须做状态机、互操作、安全和网络仿真验证。

### 14.1 功能与状态机测试

- 正常建连、数据传输、半关闭、正常关闭；
- 重复帧、乱序帧、延迟帧、过期帧、未知帧；
- 所有非法状态迁移和边界值；
- 流创建、流取消、流重置、最大并发流；
- 版本协商、能力协商、升级与降级。

### 14.2 弱网与性能测试

- 固定和随机丢包、突发丢包；
- 双向乱序、重复、损坏、延迟突增；
- 带宽骤降、RTT 抖动、队列积压；
- 高带宽长肥网络、移动弱网、Wi-Fi 切换；
- 多连接公平性，与 TCP/QUIC 混跑时的影响；
- 高并发建连、海量小包、超大消息、慢接收端。

### 14.3 安全与鲁棒性测试

- 模糊测试（Fuzzing）帧解析器与状态机；
- 长度溢出、整数溢出、压缩炸弹、重组缓存耗尽；
- 伪造源地址、放大攻击、重放、包注入、连接迁移劫持；
- 密钥更新、证书轮换、认证失败、token 过期；
- 服务端重启、实例迁移、网络分区和时钟异常。

---

## 十五、落地实施顺序

建议采用渐进方式，而不是一次实现所有高级能力：

1. **写协议规范：** 服务语义、帧格式、状态机、错误码、限制条件和兼容策略；
2. **完成最小闭环：** 编解码、基本握手、数据帧、长度校验、连接超时；
3. **补齐正确性：** 包编号、ACK、乱序重组、重传、接收窗口；
4. **补齐网络友好性：** RTT/RTO、拥塞控制、Pacing、PMTU；
5. **补齐安全性：** 地址验证、TLS/AEAD、重放防护、资源限额；
6. **扩展高级能力：** 多 Stream、迁移、会话恢复、优先级；
7. **压测与灰度：** 先在可控环境验证，再按网络、地域、客户端版本灰度；
8. **保留回退能力：** 发生兼容性或稳定性问题时可回退到成熟承载协议。

---

## 十六、面试回答模板

> 如果让我设计一个传输层协议，我会先根据场景明确可靠性、有序性、消息边界、延迟和多路复用语义，再决定基于 TCP、UDP 还是 QUIC 实现。协议报文需要具备版本、连接 ID、包号、流 ID、长度、确认和流控等字段，并预留安全扩展能力。可靠性依靠编号、ACK 区间、乱序缓存、动态 RTO 与快速重传实现；接收端通过连接级和流级窗口做流控，发送端通过慢启动、拥塞避免、ECN 与 Pacing 避免压垮网络。安全上要做身份认证、加密完整性、防重放、地址验证和抗放大；工程上还要处理 MTU、NAT、连接迁移、中间盒兼容、版本演进、指标观测和弱网测试。若无特殊需求，优先使用 TCP/TLS 或 QUIC，而不是重复造一个不完整的 TCP。

## 十七、核心结论

自定义传输层协议最难的不是发送和接收，而是长期正确地处理以下问题：

1. **交付语义：** 可靠、顺序、消息边界和过期数据如何定义；
2. **网络适应：** 丢包、乱序、重传、流控、拥塞与 MTU；
3. **安全边界：** 加密认证、重放、放大攻击、资源耗尽与畸形输入；
4. **生产现实：** NAT、移动网络、负载均衡、中间盒、版本兼容；
5. **可运营性：** 状态机可验证、指标可观测、故障可回退、协议可演进。

只有这些部分一起成立，协议才不是实验性质的“能通信”，而是可在生产环境长期运行的传输系统。
