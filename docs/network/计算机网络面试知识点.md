## 一、网络分层模型

### 1.1 OSI 七层 vs TCP/IP 四层（高频开场题）

| OSI 七层 | TCP/IP 四层 | 典型协议 | 数据单位 | 核心职责 |
|----------|-------------|----------|----------|----------|
| 应用层 | 应用层 | HTTP、HTTPS、DNS、FTP、SMTP、RPC | 报文 | 为应用程序提供网络服务 |
| 表示层 | 应用层 | SSL/TLS（部分）、序列化 | 报文 | 数据格式转换、加密解密、压缩 |
| 会话层 | 应用层 | —— | 报文 | 建立、管理、终止会话 |
| 传输层 | 传输层 | **TCP、UDP** | 段（Segment） | 端到端通信、可靠传输、端口寻址 |
| 网络层 | 网络层 | **IP、ICMP、ARP**、OSPF、BGP | 包（Packet） | 路由寻址、跨网络转发 |
| 数据链路层 | 网络接口层 | Ethernet、PPP、Wi-Fi | 帧（Frame） | 相邻节点传输、MAC 寻址、差错检测 |
| 物理层 | 网络接口层 | 网线、光纤、集线器 | 比特（Bit） | 传输 0/1 电信号 |

**面试回答：**

> OSI 是理论上的七层模型，实际互联网用的是 TCP/IP 四层模型。从下到上：网络接口层负责相邻节点间的帧传输（MAC 寻址）；网络层负责跨网络的路由寻址（IP 协议）；传输层负责进程到进程的端到端通信（TCP/UDP，端口寻址）；应用层直接为应用程序服务（HTTP、DNS 等）。OSI 把应用层又细分为应用、表示、会话三层，实际开发中这三层的工作（序列化、加密、会话管理）都由应用层自己实现。

### 1.2 各层的关键设备与寻址方式

| 层次 | 寻址方式 | 典型设备 |
|------|----------|----------|
| 应用层 | URL / 域名 | 网关、Nginx（七层负载均衡） |
| 传输层 | **端口号（0~65535）** | 四层负载均衡（LVS） |
| 网络层 | **IP 地址** | 路由器 |
| 数据链路层 | **MAC 地址** | 交换机、网桥 |
| 物理层 | —— | 集线器、中继器、网线 |

**一句话总结：**

> IP 地址定位到"哪台机器"，端口号定位到"机器上的哪个进程"，MAC 地址定位到"链路上的下一跳网卡"。

### 1.3 数据封装与解封装

```text
发送方（自顶向下封装）：
应用层   [HTTP 报文]
传输层   [TCP头 | HTTP 报文]                    <- 加上源端口/目的端口、序列号
网络层   [IP头 | TCP头 | HTTP 报文]             <- 加上源IP/目的IP
链路层   [帧头 | IP头 | TCP头 | HTTP 报文 | 帧尾] <- 加上源MAC/目的MAC、CRC校验

接收方（自底向上解封装）：逐层剥离头部，还原出 HTTP 报文
```

> 面试联想：MTU（链路层最大传输单元，以太网默认 1500 字节）限制了 IP 包大小，TCP 的 MSS（通常 1460 = 1500 - 20 IP头 - 20 TCP头）又限制了单个 TCP 段的应用数据大小。报文超过 MTU 会在 IP 层分片，分片丢失会导致整个报文重传，所以 TCP 用 MSS 在传输层就做好分段避免 IP 分片。

## 二、TCP 与 UDP

### 2.1 TCP 是什么？

TCP（Transmission Control Protocol）是面向连接的、可靠的、基于字节流的传输层协议。

**四大核心特性：**
1. **面向连接**：通信前必须三次握手建立连接，通信后四次挥手释放连接。
2. **可靠传输**：通过序列号、确认应答、超时重传、去重排序保证数据不丢、不重、不乱序。
3. **流量控制**：滑动窗口机制，接收方告诉发送方自己还能收多少，防止把接收方打爆。
4. **拥塞控制**：慢启动、拥塞避免、快重传、快恢复，防止把网络打爆。

### 2.2 TCP vs UDP（必考对比题）

| 对比项 | TCP | UDP |
|--------|-----|-----|
| 连接 | 面向连接（握手/挥手） | 无连接，直接发 |
| 可靠性 | 可靠：不丢、不重、不乱序 | 不保证，尽力而为 |
| 数据形式 | 字节流（无边界，可能粘包） | 数据报（有边界，一个一个发） |
| 传输效率 | 低（头部 20 字节起，机制复杂） | 高（头部仅 8 字节） |
| 流量/拥塞控制 | 有 | 无 |
| 通信方式 | 一对一（单播） | 一对一、一对多（广播/组播） |
| 首部开销 | 20~60 字节 | 8 字节 |
| 适用场景 | 文件传输、HTTP、RPC、数据库 | 音视频通话、直播、DNS 查询、游戏 |

**面试回答：**

> TCP 是面向连接的可靠字节流协议，通过确认重传、滑动窗口、拥塞控制保证数据可靠有序，代价是头部开销大、时延高；UDP 是无连接的不可靠数据报协议，头部只有 8 字节，发出去就不管，时延低、支持广播组播。可靠性要求高的场景用 TCP（HTTP、RPC、MySQL），对实时性敏感、能容忍少量丢包的场景用 UDP（音视频会议、直播、DNS）。现在也有基于 UDP 实现可靠传输的方案，比如 HTTP/3 底层的 QUIC 协议，就是在 UDP 上自己实现了可靠传输和多路复用。

### 2.3 TCP 三次握手（基础版）

```text
客户端                                        服务端
  │                                             │
  │ ──── SYN（seq=x）────────────────────────►  │  客户端：SYN_SENT
  │                                             │  服务端：LISTEN → SYN_RCVD
  │ ◄─── SYN+ACK（seq=y, ack=x+1）────────────  │
  │                                             │
  │ ──── ACK（ack=y+1）──────────────────────►  │  双方进入 ESTABLISHED
  │                                             │
```

| 报文 | 携带信息 | 作用 |
|------|----------|------|
| 第一次 SYN | 客户端初始序列号 x | 客户端请求建立连接，告知自己的起始序号 |
| 第二次 SYN+ACK | 服务端初始序列号 y、确认号 x+1 | 服务端确认收到，同时告知自己的起始序号 |
| 第三次 ACK | 确认号 y+1 | 客户端确认收到服务端序号，连接建立 |

**为什么是三次而不是两次？（必考）**

> 核心原因有两个：①三次握手才能让**双方都确认彼此的收发能力正常**——两次握手只能证明客户端能发、服务端能收能发，服务端无法确认客户端能收；②**防止历史失效的连接请求突然到达**造成资源浪费——如果客户端发出的 SYN 因网络拥堵滞留，客户端早已超时重发并完成通信，旧 SYN 之后又到达服务端，两次握手下服务端会直接建立连接白白等待，三次握手下客户端不会对旧 SYN 回复确认，服务端就不会误建连接。

> 深入版（ISN、半连接队列、SYN 泛洪）见 [`计算机网络原理机制面试知识点.md`](计算机网络原理机制面试知识点.md)。

### 2.4 TCP 四次挥手（基础版）

```text
主动关闭方（如客户端）                    被动关闭方（如服务端）
  │                                             │
  │ ──── FIN ────────────────────────────────►  │  主动方：FIN_WAIT_1
  │                                             │  被动方：CLOSE_WAIT
  │ ◄─── ACK ─────────────────────────────────  │  主动方：FIN_WAIT_2
  │      （被动方可能还有数据要发，继续发数据）      │
  │ ◄─── FIN ─────────────────────────────────  │  被动方：LAST_ACK
  │                                             │
  │ ──── ACK ────────────────────────────────►  │  被动方：CLOSED
  │                                             │
  │ 主动方进入 TIME_WAIT，等待 2MSL 后关闭        │
```

**为什么握手三次、挥手四次？**

> 握手时服务端的 SYN 和 ACK 可以合并成一次发送（因为收到 SYN 时服务端没有待发数据，可以立即响应）；挥手时收到 FIN 只代表对方"不再发数据"，但**被动方可能还有数据没发完**，所以 ACK 先回（告诉对方我知道了），等数据发完再单独发 FIN，ACK 和 FIN 无法合并，因此多了一次。

### 2.5 TCP 常见状态总结

| 状态 | 含义 | 生产关注点 |
|------|------|------------|
| LISTEN | 服务端等待连接 | 端口是否正常监听 |
| SYN_SENT | 客户端已发 SYN 等待响应 | 大量出现 = 网络不通/对端不响应 |
| SYN_RCVD | 服务端收到 SYN 回了 SYN+ACK | 大量出现 = SYN 泛洪攻击嫌疑 |
| ESTABLISHED | 连接已建立，正常通信 | 正常状态 |
| FIN_WAIT_1/2 | 主动关闭方等待对方确认/FIN | FIN_WAIT_2 堆积 = 对端不发 FIN |
| **TIME_WAIT** | 主动关闭方等 2MSL 后彻底关闭 | **过多占用端口和 fd，高频考点** |
| **CLOSE_WAIT** | 被动方收到 FIN，等自己 close() | **过多 = 代码忘记关连接，Bug** |
| LAST_ACK | 被动方发了 FIN 等最后 ACK | 一般短暂 |

> TIME_WAIT 和 CLOSE_WAIT 的治理是生产实战高频题，详见 [`计算机网络生产实战面试知识点.md`](计算机网络生产实战面试知识点.md)。

## 三、HTTP 协议

### 3.1 HTTP 是什么？

HTTP（HyperText Transfer Protocol）是应用层的**无状态、明文、请求-响应**协议，基于 TCP（HTTP/3 之前），是 Web 通信的事实标准。

**三大特点：**
- **无状态**：服务器不记忆之前的请求，每次请求独立（所以才需要 Cookie/Session 来维持状态）。
- **明文传输**：内容不加密，可被窃听篡改（所以才需要 HTTPS）。
- **请求-响应模型**：客户端主动发请求，服务端响应，HTTP/1.1 之前服务端不能主动推送。

### 3.2 HTTP 报文结构

```text
请求报文：                              响应报文：
┌─────────────────────────┐          ┌─────────────────────────┐
│ POST /login HTTP/1.1    │ 请求行    │ HTTP/1.1 200 OK         │ 状态行
│ Host: example.com       │          │ Content-Type: text/html │
│ Cookie: sessionid=abc   │ 请求头    │ Set-Cookie: token=xyz   │ 响应头
│ Content-Length: 28      │          │ Content-Length: 1024    │
│                         │ 空行      │                         │ 空行
│ username=zs&password=12 │ 请求体    │ <html>...</html>        │ 响应体
└─────────────────────────┘          └─────────────────────────┘
```

### 3.3 常见请求方法

| 方法 | 语义 | 幂等性 | 典型用途 |
|------|------|--------|----------|
| GET | 获取资源 | 幂等 | 查询数据 |
| POST | 提交数据/创建资源 | 非幂等 | 提交表单、下单 |
| PUT | 全量更新资源 | 幂等 | 修改用户信息（整体替换） |
| PATCH | 部分更新资源 | 非幂等 | 修改部分字段 |
| DELETE | 删除资源 | 幂等 | 删除记录 |
| HEAD | 只获取响应头 | 幂等 | 检查资源是否存在、获取大小 |

> **幂等性**：同一个请求执行一次和执行 N 次效果相同。面试常结合"重试"考：非幂等接口（如 POST 下单）重试可能产生重复数据，需要**幂等设计**（唯一请求号、防重表、状态机）。

### 3.4 GET vs POST（经典题）

| 对比项 | GET | POST |
|--------|-----|------|
| 语义 | 获取资源（安全、幂等） | 提交/处理数据（非幂等） |
| 参数位置 | 拼在 URL query 上 | 放在请求体（也可带 query） |
| 长度限制 | 浏览器/服务器对 URL 长度有限制（非协议限制） | 理论上无限制 |
| 缓存 | 可被浏览器缓存 | 默认不缓存 |
| 安全性 | 参数暴露在 URL，不适合敏感信息 | 相对不暴露，但明文 HTTP 都不安全 |
| 数据包 | 产生 1 个 TCP 包（一般） | 产生 2 个 TCP 包（先发 header 再发 body，视实现） |

**面试回答：**

> 从语义上讲 GET 用于获取资源、是安全且幂等的，POST 用于提交数据、非幂等；从表现上讲 GET 参数在 URL 上能被缓存、能被浏览器收藏，POST 参数在请求体里。从本质上讲，两者都是基于 TCP 的 HTTP 请求，技术上 GET 也可以带 body、POST 也可以把参数放 URL，区别主要来自 HTTP 语义约定和浏览器/服务器的实现差异。真正的安全要靠 HTTPS，而不是把参数藏在 body 里。

### 3.5 HTTP 状态码（必背）

| 分类 | 含义 | 常见状态码 |
|------|------|------------|
| 1xx | 信息提示 | 100 Continue |
| 2xx | 成功 | **200 OK**、201 Created、204 No Content |
| 3xx | 重定向 | **301 永久重定向**、**302 临时重定向**、304 Not Modified（协商缓存命中） |
| 4xx | 客户端错误 | **400 请求参数错误**、**401 未认证**、**403 无权限**、**404 资源不存在**、405 方法不允许、**429 请求太频繁（限流）** |
| 5xx | 服务端错误 | **500 服务器内部错误**、**502 网关错误（上游挂了/无响应）**、**503 服务不可用（过载/下线）**、**504 网关超时（上游响应慢）** |

**高频追问：**
- **301 vs 302**：301 永久重定向，浏览器会缓存并直接跳转新地址，SEO 权重转移；302 临时重定向，每次都要访问原地址再跳转。
- **401 vs 403**：401 是"没登录/凭证无效"（Unauthorized），403 是"登录了但没权限"（Forbidden）。
- **502 vs 504**：502 是网关连不上上游或上游返回非法响应（上游挂了），504 是上游响应太慢网关等超时了（上游慢）。

### 3.6 HTTP 各版本演进（概览）

| 版本 | 核心特性 | 解决的问题 |
|------|----------|------------|
| HTTP/1.0 | 短连接：每个请求建一次 TCP 连接 | —— |
| HTTP/1.1 | **长连接（Keep-Alive）**、管道化（实际不好用）、更多缓存控制 | 避免重复握手，连接复用 |
| HTTP/2 | **二进制分帧、多路复用**、HPACK 头部压缩、服务器推送 | 解决 HTTP 层队头阻塞、头部冗余 |
| HTTP/3 | 基于 **UDP 的 QUIC** 协议，解决 TCP 队头阻塞、0-RTT 建连 | TCP 层队头阻塞、握手时延 |

> 详细原理（多路复用怎么实现、QUIC 为什么快）见 [`计算机网络原理机制面试知识点.md`](计算机网络原理机制面试知识点.md)。

### 3.7 HTTP 缓存（高频）

| 缓存类型 | 机制 | 关键头部 |
|----------|------|----------|
| 强缓存 | 未过期直接用本地缓存，**不发请求** | `Cache-Control: max-age=3600`、Expires（旧） |
| 协商缓存 | 发请求问服务端"变了没"，没变返回 304 用缓存 | `Last-Modified` / `If-Modified-Since`；`ETag` / `If-None-Match` |

**优先级：** 强缓存 > 协商缓存；ETag > Last-Modified（ETag 更精确，能解决"1 秒内多次修改"和"文件变了内容没变"的问题）。

## 四、HTTPS 基础

### 4.1 为什么需要 HTTPS？

HTTP 明文传输有三大风险：

| 风险 | 说明 | 对策 |
|------|------|------|
| 窃听 | 链路上任何人都能看到内容（如公共 Wi-Fi 抓包看密码） | **加密**（对称+非对称混合加密） |
| 篡改 | 中间人可以改内容（如运营商劫持插广告） | **摘要/签名**保证完整性 |
| 冒充 | 无法确认对面是不是真的目标服务器（假银行网站） | **数字证书 + CA** 验证身份 |

**HTTPS = HTTP + TLS（加密 + 完整性校验 + 身份认证）**，端口 443（HTTP 是 80）。

### 4.2 对称加密 vs 非对称加密（必考）

| 对比项 | 对称加密 | 非对称加密 |
|--------|----------|------------|
| 密钥 | 同一把密钥加密解密 | 公钥加密、私钥解密（或私钥签名、公钥验签） |
| 速度 | **快**（AES 有硬件指令加速） | **慢**（比对称慢几个数量级） |
| 密钥分发 | 难题：怎么把密钥安全给到对方？ | 公钥可以公开，天然解决分发问题 |
| 典型算法 | AES、ChaCha20、DES（已淘汰） | RSA、ECC（ECDH/ECDSA） |

**HTTPS 的混合加密思路（核心设计）：**

> 用**非对称加密**交换"会话密钥"（只用在握手阶段，数据量小，慢的缺点可接受），之后的业务数据全部用**对称加密**传输（速度快）。兼顾安全与性能。

### 4.3 数字证书与 CA

```text
证书信任链：
浏览器/操作系统内置根 CA 证书
        │ 签发
   中间 CA 证书
        │ 签发
   服务器证书（包含：域名、公钥、有效期、CA 的数字签名）
```

**验证过程：** 客户端收到服务器证书后，用 CA 的公钥验证证书上的签名，确认证书确实是 CA 签发的且没被篡改；再检查域名是否匹配、是否在有效期内。

**面试一句话：**

> 证书解决的是"公钥怎么证明是这个网站的"的问题。没有证书，攻击者可以把自己的公钥冒充服务器的公钥发给客户端（中间人攻击）；有了 CA 背书，客户端只信任内置根 CA 签发的证书，攻击者伪造的证书验签不过。

> TLS 握手的完整流程（RSA 握手 vs ECDHE 握手、为什么 ECDHE 有前向安全性）见 [`计算机网络原理机制面试知识点.md`](计算机网络原理机制面试知识点.md)。

## 五、Cookie、Session 与 Token（经典必考题）

### 5.1 为什么需要 Cookie？

HTTP 是**无状态**协议：服务端默认记不住"刚才登录的是你"。但购物车、登录态等功能要求服务端能识别用户身份，于是需要一种机制在多次请求之间维持状态——这就是 Cookie 的诞生背景。

**Cookie 的本质：** 服务端通过响应头 `Set-Cookie` 种到浏览器里的一小段文本（一般 ≤ 4KB），浏览器**之后每次请求该域名都会自动在请求头 `Cookie` 中带上**它，服务端借此识别用户。

```text
首次登录：
客户端 ── POST /login ──────────────────► 服务端
客户端 ◄── Set-Cookie: sessionid=abc123 ── 服务端（浏览器存下 Cookie）

后续请求（浏览器自动携带）：
客户端 ── GET /cart ────────────────────► 服务端
          Cookie: sessionid=abc123          服务端根据 sessionid 认出"是他"
```

### 5.2 Cookie 的重要属性（面试高频）

| 属性 | 作用 | 面试关注点 |
|------|------|------------|
| `Expires` / `Max-Age` | 过期时间；不设置则是**会话 Cookie**，浏览器关闭即失效 | 持久登录设置长过期时间 |
| `Domain` / `Path` | 生效的域名/路径范围 | 子域名共享 Cookie 实现单点登录 |
| `HttpOnly` | **禁止 JS 读取该 Cookie** | 防 **XSS** 偷 Cookie |
| `Secure` | 仅 HTTPS 下发送 | 防明文窃取 |
| `SameSite` | 限制跨站携带（Strict/Lax/None） | 防 **CSRF** 攻击 |
| `Size` | 单个 Cookie ≤ 4KB，一个域名下数量有限（几十上百个，浏览器而异） | 别把大对象塞 Cookie |

### 5.3 Session 机制

Session 是**服务端**保存用户会话数据的机制：

1. 用户登录成功后，服务端创建 Session 对象（存用户 ID、权限等），生成唯一 `sessionId`。
2. 通过 `Set-Cookie: sessionid=xxx` 把 sessionId 种到浏览器。
3. 后续请求浏览器自动带 Cookie，服务端用 sessionId 找到对应 Session，识别用户。

**存储介质：** 单机内存（Tomcat 默认）、Redis（分布式会话标配）、数据库。

### 5.4 Cookie vs Session（必考对比）

| 对比项 | Cookie | Session |
|--------|--------|---------|
| 存储位置 | **客户端**（浏览器） | **服务端**（内存/Redis） |
| 安全性 | 低（可见可改，敏感信息不能放） | 高（数据在服务端，只暴露 sessionId） |
| 容量 | 小（4KB，数量有限） | 理论上只受服务端存储限制 |
| 服务端开销 | 无 | 每个用户一份数据，量大要考虑分布式存储 |
| 有效期 | 可长期持久化 | 一般较短（如 30 分钟无操作过期） |
| 跨域 | 受 Domain 限制，跨域携带麻烦 | 本身不跨域，靠 Cookie/Token 传递 sessionId |

**面试回答：**

> Cookie 是客户端存储机制，Session 是服务端存储机制，两者是配合关系而不是对立关系：Session 通常借助 Cookie 来传递 sessionId。Cookie 数据在客户端不安全、容量小；Session 数据在服务端安全，但用户量大时有存储和分布式共享问题。如果浏览器禁用了 Cookie，可以通过 URL 重写（把 sessionId 拼在 URL 上）来传递 sessionId。

### 5.5 Token 与 JWT

**为什么有了 Session 还要 Token？**

Session 方案的痛点：
- **服务端要存状态**：集群环境下 Session 需要共享（Redis 集中存储 /  Session 复制 / 粘滞会话），增加复杂度。
- **CSRF 风险**：基于 Cookie 自动携带，容易被跨站请求伪造利用。
- **多端不友好**：App、小程序没有 Cookie 机制。

**Token 方案：** 登录成功后服务端签发一个**自包含的令牌**（Token），客户端自己存（localStorage / App 本地），每次请求放在 `Authorization: Bearer <token>` 头中，服务端**只验签不存储**，天然无状态、可水平扩展。

**JWT（JSON Web Token）结构：**

```text
xxxxx.yyyyy.zzzzz
  │      │      └─ Signature 签名：用服务端密钥对前两部分签名，防篡改
  │      └──────── Payload 载荷：用户ID、角色、过期时间等（Base64 编码，≠加密，别放敏感信息）
  └─────────────── Header 头部：算法、类型
```

**JWT vs Session 对比：**

| 对比项 | Session（Cookie 传递） | JWT（Token 传递） |
|--------|------------------------|-------------------|
| 状态 | 服务端有状态（要存 Session） | 服务端无状态（只验签） |
| 水平扩展 | 需要分布式 Session（Redis） | 天然支持，任意节点都能验 |
| 注销/踢人 | 删 Session 即可，立即生效 | **难**：签发后有效期内都有效，需黑名单/短过期+刷新令牌 |
| 存储位置 | 浏览器 Cookie（自动携带） | 客户端手动管理（localStorage 等），**不受同源策略自动携带，天然防 CSRF** |
| XSS 风险 | HttpOnly Cookie 可防 | localStorage 存 JWT 可被 JS 读取，XSS 风险更高 |

**面试回答模板：**

> Cookie、Session、Token 都是为解决 HTTP 无状态而生的。Cookie 是客户端存储，Session 是服务端存储、靠 Cookie 传 sessionId 识别用户；Token（典型实现 JWT）把用户信息签名后自包含在令牌里，服务端不存状态、只验签，天然支持分布式和多端。Session 方案胜在可控性强（可随时踢人下线），JWT 胜在无状态易扩展，代价是签发后难以主动失效，实践中常用"短过期 AccessToken + 长过期 RefreshToken + 黑名单"来平衡。安全方面：基于 Cookie 的方案要防 CSRF（SameSite、Token 校验），基于 localStorage 存 JWT 的方案要防 XSS。

### 5.6 分布式 Session（集群下登录态共享）

| 方案 | 原理 | 优缺点 |
|------|------|--------|
| Session 复制 | 各节点互相同步 Session | 节点多时任步流量大，只适合小集群 |
| 粘滞会话（Session Sticky） | 负载均衡按 IP hash 把同一用户固定打到同一台 | 节点宕机会话丢失，负载不均 |
| **集中存储（主流）** | Session 统一存 **Redis**，所有节点共享 | 高可用、易扩展，Redis 本身要做高可用 |
| **JWT 无状态（主流）** | 根本不存 Session，令牌自包含 | 见上节对比 |

## 六、DNS 与其他应用层协议

### 6.1 DNS 域名解析过程（高频）

```text
浏览器输入 www.example.com：
1. 查浏览器 DNS 缓存
2. 查操作系统缓存（hosts 文件优先）
3. 查本地 DNS 服务器（LDNS，如运营商 DNS）
4. LDNS 迭代查询：根 DNS（.）→ 顶级域 DNS（.com）→ 权威 DNS（example.com）
5. 拿到 A 记录（IP），逐级缓存后返回
```

| 概念 | 说明 |
|------|------|
| 递归查询 | 客户端 → 本地 DNS：必须给出最终结果（本地 DNS 代为跑腿） |
| 迭代查询 | 本地 DNS → 根/顶级/权威 DNS：每层只告诉下一层去哪查 |
| 常见记录 | A（域名→IPv4）、AAAA（→IPv6）、CNAME（→另一个域名）、MX（邮件）、NS（域名服务器） |
| DNS 传输 | 默认走 **UDP 53**（快），响应过大或区域传输时用 TCP 53 |

**DNS 的作用不止解析：**
- **负载均衡**：一个域名配多个 A 记录轮询返回。
- **CDN 调度**：CNAME 到 CDN 厂商，CDN 按用户地理位置返回最近的边缘节点 IP。

### 6.2 其他常见协议速览

| 协议 | 作用 | 端口 | 面试一句 |
|------|------|------|----------|
| ARP | IP → MAC 地址解析 | 链路层 | 同网段通信靠它找下一跳 MAC |
| ICMP | 网络诊断 | 网络层 | `ping` 基于它；不可达/超时报文 |
| DHCP | 自动分配 IP | UDP 67/68 | 设备入网自动获取 IP/网关/DNS |
| NAT | 内网 IP ↔ 公网 IP 转换 | 路由器 | 解决 IPv4 枯竭；NAPT 靠端口区分内网主机 |
| WebSocket | 全双工长连接 | 复用 80/443 | HTTP 握手升级，服务端可主动推（IM、弹幕） |

## 七、一次 HTTP 请求的完整过程（串联大题）

> "浏览器输入 URL 回车后发生了什么？" 这道题几乎必考，按以下脉络回答可以覆盖 80% 的网络知识点，深挖版见 [`计算机网络原理机制面试知识点.md`](计算机网络原理机制面试知识点.md)。

```text
1. URL 解析：浏览器解析协议、域名、端口、路径
2. DNS 解析：缓存 → hosts → 本地 DNS → 根/顶级/权威，拿到服务器 IP
3. TCP 连接：三次握手（HTTPS 还有 TLS 握手）
4. 发送 HTTP 请求：浏览器构造请求报文发出
5. 服务器处理：Nginx 反代 → 应用服务 → 可能查缓存/数据库 → 返回响应
6. 浏览器渲染：解析 HTML → DOM 树、CSSOM → 渲染树 → 布局 → 绘制
   （期间遇到 JS/CSS/图片资源再发请求）
7. 连接收尾：HTTP/1.1 长连接可复用，闲置后四次挥手关闭
```

**一句话版本：**

> DNS 解析域名拿 IP，三次握手建 TCP（HTTPS 加 TLS 握手），发送 HTTP 请求，服务端处理返回响应，浏览器解析渲染页面，连接复用或挥手关闭。

## 八、计算机网络面试高频问题速记

| 问题 | 一句话答案 |
|------|------------|
| OSI 七层/TCP/IP 四层 | 接口层（MAC）、网络层（IP）、传输层（端口）、应用层（HTTP/DNS） |
| TCP 和 UDP 区别 | TCP 面向连接可靠字节流，UDP 无连接不可靠数据报、快、支持广播 |
| 三次握手为什么三次 | 双方确认收发能力 + 防止历史失效连接误建 |
| 四次挥手为什么四次 | 被动方收到 FIN 后可能还有数据要发，ACK 和 FIN 不能合并 |
| TIME_WAIT 作用 | 保证最后的 ACK 能到达 + 让旧报文在网络中消亡，等 2MSL |
| HTTP 特点 | 无状态、明文（HTTPS 前）、请求-响应 |
| GET 和 POST 区别 | 语义（获取 vs 提交）、幂等性、参数位置、缓存；本质都是 TCP 上的 HTTP |
| 状态码 301/302 | 永久重定向（缓存） vs 临时重定向 |
| 状态码 502/504 | 上游挂了/返回非法 vs 上游超时 |
| HTTPS 怎么保证安全 | 非对称加密交换会话密钥 + 对称加密传数据 + CA 证书验身份 + 摘要防篡改 |
| 对称/非对称加密 | 同密钥快但分发难；公私钥慢但分发易；HTTPS 混合使用 |
| Cookie 是什么 | 服务端 Set-Cookie 种到浏览器的小段文本，之后请求自动携带 |
| Cookie 和 Session 区别 | 客户端存 vs 服务端存；Session 靠 Cookie 传 sessionId，配合关系 |
| Cookie 禁用怎么办 | URL 重写，把 sessionId 拼在 URL 参数里 |
| JWT 结构 | Header.Payload.Signature；Payload 是 Base64 编码不是加密 |
| JWT vs Session | 无状态易扩展但难注销 vs 有状态可控性强但要集中存储 |
| 分布式 Session 方案 | Redis 集中存储（主流）、JWT 无状态、粘滞会话、Session 复制 |
| HttpOnly 作用 | 禁止 JS 读 Cookie，防 XSS 偷登录态 |
| SameSite 作用 | 限制跨站携带 Cookie，防 CSRF |
| DNS 解析过程 | 浏览器缓存 → hosts → 本地 DNS → 根 → 顶级 → 权威，递归+迭代 |
| HTTP/1.1 vs HTTP/2 | 文本、队头阻塞 vs 二进制分帧、多路复用、头部压缩 |
| 输入 URL 全过程 | DNS → TCP 握手 → (TLS 握手) → 发请求 → 服务端处理 → 渲染 → 挥手 |
